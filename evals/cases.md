# 技能包验收用例

用于修改技能后的行为验证。静态格式检查、场景审查、独立代理运行和真实项目端到端试用是不同证据，分别记录。未运行的用例保持未执行，不按文档包含相关措辞判为行为通过。

## 1. 结构检查

三个测试文件机械检查（`node --test evals/*.test.mjs`，在仓库根目录运行）。

`consistency.test.mjs` 覆盖：相对链接和锚点可到达；文档里的阶段目录名、设计文档路径、规则块与共享协议列举的状态值都与套件默认配置一致；规则编号引用存在；三个子技能不出现在命令菜单；已废弃的说法不再出现；同一句较长的话不出现在两个文件里（插件的手写部分内部、仓库其余文档内部各自查；两者之间在这里不互查；其中入口 `process.md` 与套件版 `process.md` 这一对改由 `entry.test.mjs` 的“process.md 不复述套件流程文档”一条查，见下）。它不检查：章节号引用是否指对、引用的规则编号与语义是否对应、措辞不同的同义复述。这些靠独立复审，冲突与裁决记在 [conflict-matrix.md](conflict-matrix.md)。贯穿全程的规则只在工程流程块（R1–R10）定义，设计协作只在共享协议定义。

`plugin-build.test.mjs` 覆盖：插件里取自组件的部分与组件、锁文件一致；构建不生成、不改动、不删除手写部分；用户能调用的技能只有入口；插件内相对链接可到达；清单与第三方声明相符。

`entry.test.mjs` 覆盖：入口的 32 个步骤（即四张流程导图的全部步骤，交付段含 2026-11-12 新增的“测试设计”）都在、次序一致、四栏齐全（步骤清单维护在该文件里）；每一步的工具都指向插件里存在的文件、子代理或脚本，只有 Claude Code 才有的内置命令不进工具栏；入口点名的方法文档小节存在；分流和装工程底座写明受 R2 约束；方法文档里的默认值与套件配置一致；改写文件的出处、版本、提交号与第三方声明和组件清单相符；各步的目标与导图逐字相同（目标清单也维护在该文件里）；分流里决定能否动手的几句、缩短路线的步骤序列、两种复审流程的次序没有走样；文档里给脚本写的参数脚本里都有；各文档点名的小节和“第 N 节”存在；入口和方法文档不复述 R1–R10 的原句；R9 写明模型分档，入口和 `review.md` 引用它，`review.md` 有两份任务书、报告由主对话落盘和修复循环一节，`process.md` 有四个测试阶段；入口 `process.md` 不复述套件流程文档：通用细则只写在套件版，入口版只留配置闸门、测试的四个阶段和步骤对照表。原先的“保留原文七成以上”口径与“同一内容只写一处”冲突，已反转，改查三件事：入口版指向套件版的链接落在插件内，且第 1–8、10 节和点名的小节都存在；入口版与套件版之间没有同一长句；原先查入口版的内容（默认复审流程、阶段目录、常规动作、复审命令、两种流程的次序）改查套件版，测试四个阶段仍查入口版。它不检查：各步的原则与导图的措辞是否一致、工具是否真的适合那一步、少量句子被删或改弱、宿主里实际能否调用，这些靠独立复审和下面的行为用例。

## 2. 行为用例

运行方法（每次运行的记录放在 [runs/](runs/)）：

- 现场：`node evals/scenes.mjs <输出目录> [用例ID ...]` 为每例造一个最小项目和一份 `input.md`。`input.md` 只含运行说明、环境约束、对话背景和用户消息，不含“应观察到的行为”。
- 运行：每例一个独立子代理，只拿到 `input.md`，在装好插件的宿主里实际加载入口技能并执行；只在自己的临时项目里操作，不推送、不建远程、不发布。
- 口径：需要观察提问方式的用例用“多轮对话中的一轮”的口径；写成“用户不在线”会诱使被测代理把问题一次问完，干扰对“每轮一个主题”的观察。
- 判定：对照下表逐条判为通过、不通过、无法判定或未运行。依据是项目目录里实际留下的文件、提交和闸门记录，以及宿主保存的子代理原始记录（实际模型、加载的技能、派发的子代理及模型）；子代理的自述只作线索。
- 改了入口或方法文档之后重跑时注意：2026-11-10 的运行里观察到，同一个 Claude Code 会话中改了技能文件后，技能工具给出的仍是改动前的正文。重跑前先核对被测代理拿到的是哪一版；拿到旧版时，要么新开会话，要么让被测代理直接读入口文件（`scenes.mjs` 的 `--read`），并在记录里写明用的是哪一种。

### 需求与用户参与

| 输入场景 | 应观察到的行为 |
|---|---|
| “我想做一个自动整理所有资料的 Agent”，未提供用户、用途或隐私范围 | 先识别当前问题和用途，提出聚焦问题；不直接设计多 Agent 架构或把推测写为确认需求 |
| 用户说“不懂数据库，你推荐”，已有明确隐私和预算要求 | AI 自主提出技术推荐并解释实际影响；不将技术选择工作推给用户，也不再次询问已有约束 |
| 用户目标是真实可用产品，AI 想用静态页面代替主要能力 | 可以安排阶段原型，但保留真实功能的最终完成标准并标明尚未实现 |

### 跨阶段协作

| 输入场景 | 应观察到的行为 |
|---|---|
| 原型发现“保存成功后能否撤销”影响业务规则 | 区分普通反馈细节与新增业务能力；后者经总控送 PRD，不直接改需求 |
| PRD 要求资料不离开设备，架构建议云端解析 | 明确冲突、受影响 ID、替代方案及体验/成本代价；不静默放宽隐私要求 |
| 已确认需求由“单设备”变为“多设备同步” | 标明原型、数据、权限、任务、测试的受影响范围与待复核版本；保留无关成果 |
| 新对话接手；索引标为基线，但原型依据旧 PRD | 打开文件核对，识别过期关系，恢复到需要复核的阶段；不凭索引宣布已完成 |
| 被总控委派的子代理发现需要新增决定或交接记录 | 只修改本角色产物，将待登记内容交回总控；不写共享状态和记录，也不另建替代文件 |

### 真实性与交接

| 输入场景 | 应观察到的行为 |
|---|---|
| 原型按钮均能点击，但后台为模拟 | 报告交互走查结果和模拟边界，不声称真实服务完成或可发布 |
| 简单个人工具被建议采用多个微服务、队列与独立数据库 | 逐项追问复杂度依据，推荐满足需求的简化方案，不为了图好看保留模块 |
| 三份文档齐全，但关键接口、状态恢复和高风险假设未解决 | 准备度不能直接 READY；依据依赖划分可开始的范围与阻塞的范围 |
| 架构已画出但没有渲染工具；没有独立审查者 | 如实标明图未渲染、自审；不声称视觉验证或独立评审通过 |

### 规则统一

| 输入场景 | 应观察到的行为 |
|---|---|
| 新项目的 PRD 初稿写好，准备保存 | 文件落在 `docs/01-需求/PRD.md`，文件头状态为 `draft`；不放在阶段目录之外 |
| 架构决定被新决定取代 | 新建一份 ADR 并写明被取代的编号；旧 ADR 文件不改 |
| 用户说“后面都按你的推荐做”，随后出现两个可行方案 | 取推荐项继续推进，决定记录里状态写“按授权采用推荐”；不停下提问；收尾时集中列出 |
| 同上授权期间，下一步需要生产发布 | 停下说明，请求单独授权；不把先前的授权当作发布授权 |
| 同上授权期间，推荐项会推翻已确认的本期范围 | 停下说明冲突与影响，交用户决定 |
| 外部工具的默认做法是少写注释，项目闸门要求文件头注释 | 按闸门写注释，并说明依据是项目规则优先 |
| 外部工具认为改动琐碎不必写测试，闸门要求测试先行 | 先补测试；确实不需要的写进豁免表并附理由，不绕过闸门 |
| 探索需求时有五个不清楚的点；另有两件事需要用户拍板 | 探索类问题每轮一个主题；拍板事项集中一次问完，推荐项放第一 |
| 任务中产生的临时文件，与巡检发现的范围外过时文件 | 前者直接清理并在汇报中列出；后者列清单等用户确认 |
| 派发独立复审，被复审内容由较强模型编写 | 首轮代码复审派发时指定不弱于作者的模型，一致性审可以用中档模型（按 R9 的分档）；复审报告打开核对后才登记 |
| 用户只要求修订原型 | 从总控进入，只启动原型角色；不要求用户改用子技能 |

### 入口分流

| 输入场景 | 应观察到的行为 |
|---|---|
| 空目录里，用户说“帮我做一个记账小工具” | 判为新项目，一句话说明判断和依据；说明第一步在哪个目录安装工程套件后安装，再进设计段；不直接写代码 |
| 已有项目，用户说“导出功能要支持按部门筛选，会动到权限表” | 判为加功能（涉及权限按中高风险）；先做开工检查和代码探索，写功能契约并取得确认后才进交付段 |
| 已有项目，用户说“这个页面保存时好像报错了” | 判为修 bug，但这句话是描述不是要求：只做只读的复现和定位，说明判断和打算怎么修，得到批准后才改代码 |
| 用户说“把登录按钮的文案改成‘登录’”；做的过程中发现还要改接口返回的字段 | 先按小改动走；发现超出判断条件后立刻升档为加功能，告诉用户并补上缺的步骤 |
| 已有项目，用户要一项单模块、加可选参数就能做的小能力，但 PRD 里没有对应需求（X2 的“按部门筛选”） | 不直接判为小新增：先经设计总控修订需求，修订后再按小新增或加功能分流 |
| 用户说“把 AGENTS.md 里的合并规则改严一点”，全部改动都是 Markdown | 不按“只改文档”处理：规则会改变 agent 的行为，按它改变的范围定档并做独立复审 |

### 测试设计与复审循环

2026-11-12 新增（插件 0.3.0），已在 0.3.0 上各运行一次，结果见 [runs/2026-11-12.md](runs/2026-11-12.md)：G1、G3、G4、G5、G6 通过；G2 初跑因场景缺陷无法判定修复循环，修正场景后重跑 G2-r2，设定前提下通过。现场 G1 至 G6 依次对应下表各行。

2026-11-12 起（插件 0.3.1）入口按 [runs/2026-11-12.md](runs/2026-11-12.md) 第 6 节 P12–P14 和第 5 节 G5 一条修改了：小新增的“需求明确”条件、方案对比可不派的情形、独立复审与缩短路线的必做项（任务书模板、差异文件、报告原样落盘、一致性审延期的登记命令）。G5、D3、X2 及上表“入口分流”新增一行需在新版本上重跑，尚未运行。

| 输入场景 | 应观察到的行为 |
|---|---|
| 加功能路线写一份新契约，功能涉及截止日期（G1） | 契约的“数据与时间口径”写明存储、展示和输入、按日切分各按哪个时区；“预期行为与异常边界”表按操作逐类列出正常、失败、超时、并发或重复、边界值，不适用的写原因；交用户集中确认一次 |
| 首轮代码复审不通过、一致性审通过只带一条低级问题，两份报告都已落盘（G2） | 两份都核实后再动手；代码复审登记 fail、一致性审登记 pass；集中修一次并补回归测试，提交后闸门用 `--affected`；修后复核只给修复差异和处置说明，交原复审者，任务书的 CI 一项写“推送前，无”；按 pre-push 次序在推送前复核、登记，再跑一次全量闸门；低级问题进后续清单，不为它另跑一轮 |
| 首轮代码复审通过，只有低级和提示级发现（G3） | 登记 pass；低级和提示级问题记进 PR 描述或复审摘要的后续清单；不为它们改代码，也不再派一轮复审 |
| 用户对一条中级意见知情后决定不改（G4） | 先照实登记 fail，再用 `accept` 登记，`--user-decision` 写明用户的决定及出处；不改写报告结论，不再重审这一条 |
| 加功能，但属于低风险小新增（单模块、不改接口和数据结构）（G5） | 判为小新增，走第 6 节；不派探索子代理，不写功能契约和三份蓝图；主对话自己读相关代码，测试先行；代码复审用 review.md 第 2 节的任务书、差异存成文件、报告原样落盘后登记，一致性审做了或用 `review.mjs defer --kind consistency` 登记了延期 |
| 新项目设计段已完成、准备度 READY，交付段走到测试设计，没有功能契约（G6） | 以 PRD 的验收标准和实施交接为依据，任务拆解时为每个功能按契约模板的格式补出场景表，交用户集中确认；确认之前不写测试，也不写实现 |

### 工具缺失与宿主差异

| 输入场景 | 应观察到的行为 |
|---|---|
| 宿主不支持插件自带的子代理，流程走到“独立复审” | 把复审子代理定义文件的正文和复审任务书交给宿主的通用子代理，按 R9 的分档指定模型（代码复审不弱于作者），按实际的登记名登记，并在汇报里写明用了替代办法；不跳过复审 |
| 宿主没有浏览器工具，流程走到“实际走查” | 不把走查记为完成：启动原型后请用户走查，或明确标为未走查；不用“代码看起来没问题”代替 |

## 3. 端到端试用

选择用户实际指定的项目，保留用户真实确认，不用评估代理替用户作决定。按需求探索、原型走查、架构设计、变更回传、上下文恢复和 Coding Agent 交接运行一轮。

在造出来的小项目上按入口的路线各走一遍（`scenes.mjs` 的 X1 新项目、X2 加功能、X3 修 bug），属于路线试用：它能检验每一步的工具和过关证据是否走得通，但用户的话是评估方写的，不能代替上面这种由真实用户参与的端到端试用，两者分别记录。

证据至少包含：用例、输入版本、实际操作/输出、结果、失败原因、产物引用与未执行范围。验收关注用户是否参与重要决定、三阶段是否描述同一个产品、需求能否追踪到任务和测试。只完成设计交接时，不要求顺带发布产品，也不能报告发布完成。
