# 工程流程（完整版）

本文是工程能力包的完整流程，按需读取。项目的 AGENTS.md 里是流程地图和规则 R1–R10（engineering-kit 标记块）。
命令中的 `<kit>` 指本技能的 `kit/` 目录，`<项目>` 指项目根目录。

## 0. 原则

贯穿全程的规则（优先级、授权、提问、标准、状态与证据、文档、分支与合并、删除、子代理、排程与收工）只写在项目 AGENTS.md 的工程流程块里，编号 R1–R10；本文只写各步怎么做，引用编号，不复述。能用脚本或钩子强制的，就不靠自觉。

## 1. 开工

1. 从最新主干新建分支。主干没有远程时，以本地主干为准。
2. 列出分支与工作树（`git branch`、`git worktree list`），确认没有遗留的未提交改动（WIP）。遗留的先提交、归档或清理，再开新任务；不属于本任务的遗留工作按 R8 先问用户。
3. 读项目 AGENTS.md 的流程地图与目录地图；项目另有专用流程文档的一并读，按 R1 它优先于本文。
4. 按下面的“执行位置与排程”定好本任务的执行位置和顺序。

### 执行位置与排程

目的：用户在场的时间和本机的资源，留给需要用户参与、需要判断的工作；不需要人参与的重复性工作不占用这段时间，也尽量不占用本机。

前提：排程只决定同一流程里各项工作在哪里做、先做哪项，不改变流程本身。第 2–5 节规定的步骤、先后顺序、检查范围和通过标准一项不省、一项不降；排程与流程冲突时，按流程办。不为了方便调度而跳过、缩小、推迟到合并之后，或用较弱的检查代替。

工作分两类：

| 类别 | 包括 | 排在什么时候 |
|---|---|---|
| 创造性工作 | 需求澄清、方案、编码、处理复审意见、修复失败、需要用户决定的事 | 优先完成，排在用户在场的时段 |
| 重复性工作 | 全量测试、回归、端到端、构建、巡检、批量机械改动、跑闸门 | 攒成整块，在用户这一阶段要做的事做完、可以去忙别的之后一次跑完 |

“整块时段”是相对的，不指固定的钟点：凡是需要用户参与的事已经做完、用户可以离开的那一段，就是跑重复性工作的整块时段，白天、夜间都可以。一个任务可以分成几轮：创造 → 重复 → 再创造 → 再重复。每一轮先把需要用户的部分集中做完，再把这一轮的重复性工作集中跑完，下一轮的创造性工作以上一轮的结果为依据。

- 执行位置：开发和测试凡是能在云端会话执行的，都放到云端。云端不占本机资源，本机休眠时照常运行。
- 能放云端的条件：代码已推送到远程；不依赖只在本机才有的东西（未推送的文件、本机的数据库或服务、本机凭据、图形界面、硬件）。不满足条件的才留在本机，并在汇报里说明原因。
- 开工时定顺序：列出本任务的创造性部分和重复性部分。先做完创造性部分并提交快照；重复性部分排队，不穿插在中间打断。互不依赖的重复性任务合成一批。
- 用户在场时，本机只跑小范围的快速检查（与改动直接相关的单元测试、静态检查），供写代码时即时反馈。全量和耗时的检查放云端，或留到整块时段。
- 与闸门的关系：推送仍须有与当前代码一致的通过测试记录，复审、CI 与合并的先后照第 4 节，都不因排程而改变。在云端会话里开发的，闸门在云端跑、从云端推送；留在本机的，把“跑闸门、推送”放进本轮的整块时段。
- 每一轮整块跑完后集中汇报一次：通过与失败、失败的具体项、需要用户决定的事。失败不自行降低标准，修复属于创造性工作，放进下一轮用户在场的时段。
- 启动云端会话和定时任务属于有费用的外部动作，按 R2 执行。

## 2. 需求与方案

- 低风险改动直接做。中高风险（跨模块、新接口、数据库结构、权限、费用、服务器配置）先澄清需求，写功能契约，取得用户确认。
- 澄清按 R3：先查已有资料和确认记录，查得到的不问；剩下的归成一张清单一次问完，每个问题给出选项，推荐项放第一并写一句理由。
- 契约放在 `docs/04-开发/`，模板见 `docs/_templates/feature-contract.md`。契约定义“怎样证明正确”，验收标准不得擅自弱化。涉及日期、时间字段的，在契约里写明时区口径（存储、展示和输入、按日切分的边界各按哪个时区）。契约的“预期行为与异常边界”表按操作逐类写出正常、失败、超时、并发或重复、边界值的预期，测试依据这张表写，不从实现倒推。
- 契约里的预期和场景表交用户集中确认一次；之后同一功能的小修复沿用这份契约，需求变了才重新确认。
- 实现中自行确定的口径要单列，待用户确认，不写成已决定。
- 方案对比至少写三栏：复杂度、风险、能否回退。推荐只是建议；用户选定或“按授权采用推荐”之后才成为决定，并写进决定记录。

## 3. 开发

- 测试先行：改源文件前，先写或补引用它的测试。测试随改动一起改。识别方法、支持范围与局限（含间接引用须在豁免表里写理由）见 `../SKILL.md` 第 6 节。
- 注释：每个源文件有业务职责说明；导出的函数、类、常量前有说明（输入输出、异常、为什么这样做）。
- 目录：代码按语言惯例放 `src/`、`tests/`。新顶层目录须在白名单内：`layout.topLevelAllowed`，加上 `sourceGlobs`、`testGlobs` 里写明的顶层目录。

## 4. 测试、审查与合并（目标流程）

目标顺序：PR 前受影响测试 → CI 与独立代码复审、一致性审 → 合并；复审可以与 CI 并行开始；CI 全部通过后才登记、合并。套件闸门的 `pr` 流程实现了“CI 与双审 → 合并入口”这一段（见本节末“套件闸门的两种流程”）；受影响测试由 `gate.mjs --affected` 按项目配置的测试分组选择，判断不了影响范围时自动改跑全量（见本节末“测试模式与结果复用”）。默认的 `pre-push` 流程次序不同：复审在推送之前，见本节末“套件闸门的两种流程”。适配状态见 `../SKILL.md` 第 5 节；项目已有更完善流程时，以项目规则和实际闸门为准（R1）。

1. PR 前执行静态检查及受影响的单元、集成、端到端、视觉和安全检查；不能可靠判断影响范围时扩大范围或跑全量，说明选择及结果。测试用隔离环境和合成数据。
2. CI 对最终提交执行全量单元测试和项目适用的全量集成测试；端到端、兼容性、安全等检查按风险安排，明确跳过的理由。复审可以与 CI 并行开始；CI 全部通过后才登记、合并；必需检查须为成功（`pr` 流程的判定见本节“套件闸门的两种流程”一段）。
3. 按下方分档进行独立代码复审和增量一致性审（矛盾、重复、过时）；一致性审可以集中审多个 PR，但每个 PR 的最终提交、所做审查的结论及证据各自记录。合并前核对 PR、最终提交、CI 和该档要求的审查；提交或基线变化后重新核查受影响部分。
4. 审查发现的高、中级问题，以及影响体验或使用的问题在合并前修复；低级和提示级问题默认记入 PR 的后续清单；已登记、不扩大风险的可以同批改并写明，修后复核一并核对；不为它们单独再修一轮。本次引入的矛盾、重复和过时问题同样按级别处理：高、中级的在本 PR 修复，低级的同样默认记入后续清单。同一 PR 三轮审查后仍需下一轮时，向用户说明问题、原因、已做处置和建议，等待用户决定。套件闸门按被审内容机械计数：一轮是登记过代码复审或一致性审 fail 的一份被审内容，`pr` 流程是同一 PR 的一个最终提交，`pre-push` 流程是同一分支上登记时的一份工作区内容（按树哈希加文档内容哈希区分，不按 HEAD 提交号）；同一份内容上两种审查都不通过只算一轮，修复后在新内容上再不通过才算下一轮；已有 `modules.review.maxReviewRounds`（默认 3）份不同内容登记过 fail 后，再登记 pass 或 fail 都被拒，用户同意继续的带 `--user-decision "<用户的决定及出处>"` 重新登记；唯一例外是在已计入的内容上首次登记另一种审查。用户知情后决定接受报告里的问题、不再修改的，登记 `accept`（报告结论须为不通过），它不计轮次，合并入口和推送核对按用户决定放行。
5. 合并遵循项目规定与实际授权；不绕过失败的必需检查。`pr` 流程下合并只经 `merge.mjs`，它核对 CI 与两项审查都针对 PR 的最终提交；`pre-push` 流程的记录只证明推送前复审，不能证明对 PR 最终提交的双审查或最终 PR 绑定。

审查频率按风险分档（风险分级见第 2 节）：

| 改动 | 代码复审 | 一致性审 |
|---|---|---|
| 只改文档（`reviewIgnore` 之内） | 不做 | 并入每周巡检（第 8 节） |
| 低风险小新增、小改动 | 每个 PR 合并前 | 可延期：并入每周巡检，或与其他 PR 集中审；延期要写明理由 |
| 中高风险 | 每个 PR 合并前 | 每个 PR 合并前 |

代码复审不攒到合并后：结论绑定 PR 的最终提交，合并后才发现的问题已在主干上，后续 PR 又叠在其上。一致性审可以集中审多个 PR，结论仍按 PR 各自记录。拿不准风险档位时按高一档处理。

套件闸门的两种流程（`engineering.config.json` 的 `modules.gate.reviewFlow`，命令在项目的 `scripts/engineering/gate/` 下）。两种流程共同的规则：闸门的判定依据不由被审分支决定。基准分支设置 `modules.gate.base` 以默认主干上的配置为准；判定策略字段 `reviewIgnore`、`reviewFlow`、`requiredChecks`、`reviewers`、`reviewMinChars`、`reviewSections`、`reviewKeyword`、`maxReviewRounds`、`externalExecutors`、`externalExclude`（外部复审的两项；`externalExclude` 另与工作区的值取并集，当轮生效，不给提示行）取基准提交上的配置（基准上还没有配置时用工作区的值）；分支里改其余字段要合入主干后才生效，工作区的值与生效值不同时闸门和推送核对会给提示行。测试命令、测试分组、glob 等其余字段仍用工作区的值。git 的 pre-push 钩子核对实际推送的提交：分支推送的提交必须是当前 HEAD 或已在基准分支里，`git push origin 别的分支` 会被拒绝；标签推送不查引用，只删除远端引用（分支或标签）的推送直接放行。

- `pre-push`（默认）：`gate.mjs` 通过后由独立复审者（宿主子代理或外部执行器，不共享作者上下文）复审，`review.mjs pass|fail --reviewer <名> --report <报告> --summary "<一句话>"` 登记；推送时核对静态检查、测试记录和复审记录，两份记录都绑定当前代码树和基线（`changedFiles` 做 diff 的基准提交）：合入新主干、变基后基线变了，旧记录作废，要重跑闸门并重新复审（没有基线字段的旧记录同样不认）。登记时除树哈希和基线外，还写明分支、HEAD 提交号、文档内容哈希和未提交的文件数：树哈希不含文档，只改规则文本这类改动每一轮都相同，靠提交号和文档内容哈希才能把登记对应到具体提交；推送核对认的是树哈希与基线。每次登记另追加到 git 目录下的 `engineering-gate/reviews/log.jsonl`（闸门记录所在的目录，不是 docs 下的记录目录），报告副本放在同目录的 `branches/<分支>/` 下。一致性审也可以登记：`review.mjs pass|fail --kind consistency …`，按分档延期用 `review.mjs defer --kind consistency --reason "<理由>"`；它只写进 log.jsonl 和 `review-consistency.json`，推送核对不要求它（不带 `--kind` 等同代码复审）。用户接受风险用 `review.mjs accept --kind code --reviewer <名> --report <报告> --user-decision "<用户的决定及出处>"`，推送核对认它并写明按用户决定放行。推送核对要求全量测试记录：复审过程中用 `gate.mjs --affected` 的，最终推送前跑一次 `gate.mjs`。套件不提供合并入口，Claude Code 的钩子拒绝直接 `gh pr merge`（别的宿主里没有这层钩子，只有 git 的 pre-push 钩子生效，同样不得直接合并）；合并按项目约定的入口，并等 CI 全部通过。项目没有约定入口时由用户合并或由用户指定入口。
- `pr`：`gate.mjs` 通过后即可推送，推送核对只要求静态检查和与当前代码、当前基线一致的测试记录（按影响范围的也认，CI 会在最终提交上跑全量）。按上表分档审查，复审可以与 CI 并行开始；CI 全部通过后才登记、合并。“CI 全部通过”指 PR 最终提交上：必需检查都是成功；非必需检查是成功、跳过或中性；失败、取消、运行中等其余结论不论必需与否一律不通过；一项检查都没有也视为未通过。同一工作流里同名的检查合在一起判定（同一个 job 可能因 push 与 pull_request 各跑一份）：有一份成功、其余只有跳过或中性的算成功；不同工作流里的同名检查各算一组、不互相抵（必需检查名出现在几个工作流里，每一组都要成功），报告里这几组带上工作流名分开显示（同名的检查运行与提交状态也各算一组；没有工作流名的那几组，显示名带“（CheckRun）”“（StatusContext）”）。必需检查名写在 `modules.gate.requiredChecks`，为空时每一项检查都算必需：写检查运行的 job 名（含矩阵后缀，不含工作流名和事件，例如 `test (ubuntu-latest)`）或提交状态的 context，与 GitHub 分支保护里必需检查的写法相同；PR 页面上显示的“工作流名 / job 名 (事件)”不是这个名字，用 `gh pr view <PR> --json statusCheckRollup --jq '.statusCheckRollup[] | .name // .context'` 查。列出的必需检查在 PR 上找不到（没有运行或改了名）按未通过处理，提示里列出本次看到的检查名。它是判定策略字段，取主干上的值，配置和 job 不放在同一个 PR 里一起删：给必需检查改名，先用一个 PR 新增新名的 job（旧 job 保留）并把配置改成新名，这个 PR 仍按主干上的旧名判定，能通过；合入后再用另一个 PR 删掉旧 job。删掉一个必需检查，先用一个 PR 删配置里的名字，合入后再删 job；别把配置里的名字删空，空数组表示每一项检查都必需，会让按条件跳过的检查都拦下合并。不要先在主干配置里加还没跑起来的新名，否则其余 PR 都报“没有出现在 PR 上”。配错卡住时连修正它的 PR 也过不了合并入口，由用户合并这个修正 PR。PR 未打开或 CI 未全过时拒绝登记：
  - 代码复审：`review.mjs pass|fail --pr <编号> --kind code --reviewer <名> --report <报告> --summary "<一句话>"`。
  - 一致性审：同上，`--kind consistency`；按分档可延期时用 `review.mjs defer --pr <编号> --kind consistency --reason "<理由>"`。
  - 合并：`merge.mjs <编号> [--method squash|merge|rebase]`。PR 打开、CI 全过、代码复审为 pass、一致性审为 pass 或延期、两份记录的提交都等于当前最终提交，才执行 `gh pr merge --match-head-commit`（默认 squash 并删除远端分支）；否则逐条列出原因，不合并。输出把成功的检查（标明必需与否）和被放行的跳过、中性检查分开列出，跳过的不算通过。PR 又有新提交时记录过期，重新审查后再登记；只有一个例外：代码复审之后的新提交只改了文档（`git diff --no-renames` 的文件全在 `reviewIgnore` 之内；项目配置、豁免表、`scripts/engineering/**` 不算文档，改名按旧路径删除加新路径新增算，代码改名进 docs/ 不算只改文档）时，代码复审记录仍认，输出写明沿用及两个提交号，本地算不出差异时按过期处理，一致性审记录仍须针对最终提交。
  - 用户接受风险：`review.mjs accept --pr <编号> --kind code|consistency --reviewer <名> --report <报告> --user-decision "<用户的决定及出处>"`，报告结论须为不通过；合并入口把它当作可放行，输出写明按用户决定接受风险放行。
  - 只改文档的 PR（本地算出的基准提交到 PR 最终提交之间全部文件在 `reviewIgnore` 之内；本地没有最终提交、基准分支解析不了或算不出共同提交时按含代码处理，输出写明原因并提示先 `git fetch`；口径同闸门：`reviewIgnore` 取基准提交上的配置，含项目配置、豁免表或 `scripts/engineering/**` 的不算）按上表不做审查，合并入口只核对 PR 打开与 CI 全过；差异为空时也按含代码处理。其余 PR 合并入口不判断风险档位：代码复审必需，能否延期一致性审由登记者按上表判断。
  - 需要 GitHub 远程和已登录的 `gh`；没有 CI 的项目留在 `pre-push`。

测试模式与结果复用（两种流程相同）：`gate.mjs` 跑配置的 `testCommand` 全量，通过的全量记录另存一份，记下当时范围内每个文件的内容哈希。`gate.mjs --affected` 以这份全量记录为起点算出此后改动的文件，每个改动文件都要命中 `modules.gate.testGroups` 里至少一个分组的 `paths`，命中的分组各跑一次 `command`；没有配置分组、没有可用的全量记录、基线或测试配置与全量记录不同、有改动不属于任何分组、改动涉及项目配置、豁免表、套件脚本或依赖清单与锁文件、这份代码（同一代码树、同一基线）上次的全量测试未通过、带 `--force` 而全量记录之后没有改动时，自动改跑全量并在输出里写明原因；不带 `--force` 而全量记录之后范围内没有改动时，直接沿用全量记录。已有通过的记录、且代码树、基线和测试配置（`testCommand`、`testEnv`、`testGroups`）都一致、模式满足要求时，闸门不重跑，输出“沿用已有通过记录”，要重跑加 `--force`；最近一次运行说了算：同一代码树、同一基线、同一测试配置上最近一次运行（全量或分组）未通过时不沿用任何记录，全量未通过时同一棵树的全量通过记录作废，失败之后的下一次运行一定真的跑。静态检查每次都做，其中断言检查要求本次改动的测试文件里有断言的痕迹，测试用例数比基准提交少时只提示、不拦截。

怎样读闸门的输出：闸门通过时先打印测试先行检查、注释检查、断言检查三行，再是测试结果一行；改跑全量或按影响范围测试时，测试结果前多一行说明原因或分组，沿用已有记录时测试结果一行换成“沿用已有通过记录”。前两行各写明本次改动的源文件里检查了几个、豁免了几个（测试先行另列“无需测试”的：已删除、没有可测的导出、只有再导出的文件；语言不支持而没能检查的另起一行写“未检查”并列出文件，不算无需测试）；都是 0 表示这次没有改到源文件。两行的范围不同：注释检查不看 `reviewIgnore` 之内的和已删除的源文件，所以两行的数字可以不一样；断言检查一行写明本次改动的测试文件查了几个，测试文件里找不到断言痕迹的判不通过（确实不需要断言的在豁免表 `assertions` 段写理由）；测试用例数比基准少时多一行提示（改名的测试文件按改名前的文件比较，规则见 `../SKILL.md` 第 6 节），不拦截，复审时核对是不是有意删的。最后一行括号里写明全量还是哪几个分组，以及 `reviewIgnore` 之外改动的源文件数。静态检查不过时，闸门只报出问题（有未检查的文件时，问题清单之后同样列出它们），不打印这些通过行，也不跑测试。同样的计数写在测试记录 `tests.json` 的 `staticChecks` 里。

## 5. 预发、生产与事故回归

生产发布、回滚、数据恢复、破坏性迁移的授权按 R2。

- 预发使用与生产一致的发布产物，按风险执行核心流程、冒烟、验收、回归、视觉、兼容、安全、性能与负载检查；压力测试在专项环境按需进行。修改或修复后做针对性 sanity 检查。记录不适用项及原因。
- 发布前准备并验证回滚方案、上一版本与数据迁移的兼容性、备份和恢复路径；镜像回滚不等于数据恢复。按项目授权部署，小范围灰度和健康检查通过后扩大，生产持续监控，异常按授权和预案处置。
- 用户验收的证据写进验收证据包（模板 `docs/_templates/acceptance-pack.md`，放 `docs/acceptance/`），发布记录放 `docs/release/`。
- 事故或测试漏检须调查为何测试和 AI 审查未发现、是否缺少测试或安全检查、CI 是否需要调整。将问题转成稳定、可重复的回归用例，放入适当阶段；无法自动化时记录原因、责任人和可执行的专项检查并跟踪补齐。可将事故、相关 PR、修复和回滚整理成脱敏样例，持续评估审查能力。

## 6. 文档与目录规则

| 类别 | 位置 | 规则 |
|---|---|---|
| 活文档（需求、架构、计划） | 阶段目录 | 原地覆盖，历史靠 git |
| 记录类（ADR、验收证据包、发布记录） | `docs/adr/`、`docs/acceptance/`、`docs/release/` | 只追加，不改、不删、不改名旧文件（巡检会报错） |
| 模板 | `docs/_templates/` | 只读，复制后使用 |
| 阶段索引 | `docs/README.md` | 每个阶段目录都要登记 |

新建文件须满足以下之一：独立生命周期、独立被引用、独立时间点。并登记到所在阶段的 README：在表格第一列写文件名（整格），或用反引号、链接写出；子目录里的文件怎样登记（只写文件名不算）见 [SKILL.md](../SKILL.md) 第 6 节。没登记的巡检会报错。推送核对会拦截不在允许位置、又没有理由的新文件；理由写在豁免表 `newFiles` 中。

新建目录或文件的位置：

- 项目根目录之外：须先经用户批准，不得自行创建。说明要建在哪里、建什么、为什么，得到同意后再建。会话的临时目录（scratchpad）不在此限。
- 项目根目录之内：可以按上面的规则创建；任务完成后逐个检查本次新建的目录和文件，不必留下的全部清理（见第 7 节）。

大版本（例如 v2）才用新目录（如 `v2/`）；同一版本内不新建平行目录。

阶段目录：`00-总览`（项目状态、决定与交接记录、实施交接与追踪矩阵）、`01-需求`、`02-原型`、`03-架构`、`04-开发`、`05-测试`、`06-发布`（可在 `layout.stages` 中修改；已安装项目写在配置里的阶段不随同步改变，同步会给出升级提示）。代码仍按语言惯例放在 `src/`、`tests/`。

## 7. 收工

1. 合并后删除远端与本地分支，清理工作树（`git worktree remove`）。合并入口报错时，先用 `gh pr view <编号> --json state,mergedAt` 确认 PR 是不是其实已经合并，再决定是否重试：已经合并的不再重试，直接收工。清理自己所在的工作树要回到主检出里做（`git -C <主检出> worktree remove <工作树>`），不在要删的工作树里删它自己。
2. 列出本次新建的目录和文件（`git status`、`git diff --no-renames --name-only --diff-filter=A <基准>`），逐个检查是否满足第 6 节；不必留下的清理掉。
3. 更新阶段索引（`docs/README.md` 和所在阶段的 README）。
4. 删除临时文件（scratchpad、导出物），不留在项目目录里。
5. 经验提炼（对应全局 CLAUDE.md 的“经验提炼”）：
   - 用户本人提出的决定或做法：直接记录到项目的 `practices/`（不跟踪）。
   - agent 总结的：只作为候选，列出标题、依据和建议归属，向用户确认后才记录或升格为能力。升格为能力时，写成变更集（见第 9 节），走同一条原子路径。
6. 汇报分四段，各有小标题，没有内容的写“无”：任务完成情况（做了什么、是否通过、实际做了哪些检查、证据在哪里）、后续待办（谁做、依赖什么、何时做）、用户需知（已做的默认选择、已知限制、风险，以及跳过了什么、没检查什么）、经验提炼。

### 经验记录

- 记录用户本人提出或采纳、跨项目可复用的决定、规则和解决问题的方法；项目特有结论仅提炼可迁移的做法。没有可记录的经验时不强行总结。已有条目更新而不重复；未采纳的 agent 建议不作为用户经验。
- 记录放在项目根目录的 `practices/`，不存在时直接新建；Git 仓库把该目录加入 `git rev-parse --git-common-dir` 下的 `info/exclude`，不跟踪、不提交。非 Git 项目直接创建。
- 按主题维护 `product-development.md`、`workflow.md`、`agentic-engineering.md`，以 `README.md` 索引；按实际需要创建。
- 每条记一条可迁移的原则、适用背景、要解决的问题、具体做法、可核实的实际效果和首次出处（项目、日期、例子）。效果未确认就写明，之后在原条目更新；再次验证可补充出处。
- 本轮有新增或更新时，汇报文件和条目；没有则如实说明。

## 8. 巡检（熵管理）

- 机械检查：`node <项目>/scripts/engineering/gate/hygiene.mjs`。检查顶层目录白名单、禁用文件名片段（copy、final、bak 等）、死链、阶段索引、阶段内登记、状态合法性、记录类只追加、重复内容、空目录、超期草稿、已合并分支与残留工作树。“已合并分支”按补丁等价判断，squash 合并后的分支需人工复核。
- “阶段索引”查各阶段目录有没有登记到 docs 根目录的 README；“阶段内登记”查阶段目录里的文件有没有登记到该阶段的 README（R6），没登记的报错，记录目录不查；登记的写法见第 6 节。以点开头的文件和 README 自己不查。
- 巡检只报告，不删除；删除按 R8。
- 套件有没有漂移不归巡检查，用 `../SKILL.md` 第 2 节的漂移检查。
- 语义一致性审：由子代理只审增量（本次或本周期新增、修改的文档），找出规则与文档之间的矛盾、重复、过时。
- 周期：建议每周一次，或在大批合并之后。巡检由用户或已授权的定时任务（R2）触发；语义一致性审的增量从上次巡检所在的提交算起，汇报里写明这次的起止提交。

## 9. 整包（一键复用、更新、回滚）

安装、升级、漂移检查、回滚、变更集与发布的命令只写在本技能的 `../SKILL.md` 第 1–4 节。

## 10. 授权边界

授权按 R2 和项目 AGENTS.md 的授权表：授权表里写了的按表执行，没写的先问用户。任务获得批准之后，推送功能分支、合并（经合并入口）、构建、预发部署属于常规动作，不必逐次再问；R2 列为始终单独授权的事项不在其内。整包发布（套件自身的发布）只提交套件目录，不推送，不开 PR，除非用户明确要求。
