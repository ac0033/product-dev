# 工程流程（完整版）

本文是工程能力包的完整流程，按需读取。项目的 AGENTS.md 里是流程地图和规则 R1–R10（engineering-kit 标记块）。
命令中的 `<kit>` 指本技能的 `kit/` 目录，`<项目>` 指项目根目录。

## 0. 原则

贯穿全程的规则（优先级、授权、提问、标准、状态与证据、文档、分支与合并、删除、子代理、排程与收工）只写在项目 AGENTS.md 的工程流程块里，编号 R1–R10；本文只写各步怎么做，引用编号，不复述。能用脚本或钩子强制的，就不靠自觉。

## 1. 开工

1. 从最新主干新建分支。主干没有远程时，以本地主干为准。
2. 列出分支与工作树（`git branch`、`git worktree list`），确认没有遗留的未提交改动（WIP）。遗留的先提交、归档或清理，再开新任务；不属于本任务的遗留工作按 R8 先问用户。
3. 读项目 AGENTS.md 的流程地图与目录地图；项目另有专用流程文档的一并读，按 R1 它优先于本文。
4. 按下面的“执行位置与排程”定好本任务的执行位置和顺序（含全量测试在本机还是 CI 跑）。

### 执行位置与排程

目的：用户在场的时间和本机的资源，留给需要用户参与、需要判断的工作；不需要人参与的重复性工作不占用这段时间，也尽量不占用本机。

前提：排程只决定同一流程里各项工作在哪里做、先做哪项，不改变流程本身。第 2–5 节规定的步骤、先后顺序、检查范围和通过标准一项不省、一项不降；排程与流程冲突时，按流程办。不为了方便调度而跳过、缩小、推迟到合并之后，或用较弱的检查代替。

工作分两类：

| 类别 | 包括 | 排在什么时候 |
|---|---|---|
| 创造性工作 | 需求澄清、方案、编码、处理复审意见、修复失败、需要用户决定的事 | 优先完成，排在用户在场的时段 |
| 重复性工作 | 全量测试、回归、端到端、构建、巡检、批量机械改动、跑闸门 | 攒成整块，在用户这一阶段要做的事做完、可以去忙别的之后一次跑完 |

“整块时段”是相对的，不指固定的钟点：凡是需要用户参与的事已经做完、用户可以离开的那一段，就是跑重复性工作的整块时段，白天、夜间都可以。一个任务可以分成几轮：创造 → 重复 → 再创造 → 再重复。每一轮先把需要用户的部分集中做完，再把这一轮的重复性工作集中跑完，下一轮的创造性工作以上一轮的结果为依据。

- 执行位置：按下面“每个环节的工作在哪做”的三步定：用户的选择（项目选项 `modules.environment.session`，用户当下的指示更优先）> 两条原则自动判断 > 多种可行且原则指向不同时问用户。云端会话不占本机资源、本机休眠时照常运行，但启动有费用（按 R2 先问）。全量测试和 CI 放在哪，由下面的项目选项和“按环境组合怎么办”决定。
- 能放云端的条件：代码已推送到远程；不依赖只在本机才有的东西（未推送的文件、本机的数据库或服务、本机凭据、图形界面、硬件）。不满足条件的才留在本机，并在汇报里说明原因。
- 开工时定顺序：列出本任务的创造性部分和重复性部分。先做完创造性部分并提交快照；重复性部分排队，不穿插在中间打断。互不依赖的重复性任务合成一批。
- 用户在场时，本机只跑小范围的快速检查（与改动直接相关的单元测试、静态检查），供写代码时即时反馈。全量和耗时的检查放云端，或留到整块时段。
- 与闸门的关系：推送仍须有与当前代码一致的通过测试记录（`fullTests` 为 `ci` 时除外：本机不要求测试记录，全量由 CI 在最终提交上跑、合并入口核对），复审、CI 与合并的先后照第 4 节，都不因排程而改变。在云端会话里开发的，闸门在云端跑、从云端推送；留在本机的，把“跑闸门、推送”放进本轮的整块时段。
- 每一轮整块跑完后集中汇报一次：通过与失败、失败的具体项、需要用户决定的事。失败不自行降低标准，修复属于创造性工作，放进下一轮用户在场的时段。
- 启动云端会话和定时任务属于有费用的外部动作，按 R2 执行。

#### 项目选项：全量测试在哪跑、CI 放哪

两项写在 `engineering.config.json` 的 `modules.gate`，都是判定策略字段（取主干上的值，分支自己改不生效，合入主干后才生效）：

| 选项 | 取值 | 含义 |
|---|---|---|
| `fullTests` | `local`（默认） | 闸门 `gate.mjs` 在当前会话所在环境跑全量测试并写记录（本地会话在本机，云端会话在云端沙箱）。推送核对按所选复审流程要求测试记录 |
| | `ci` | 全量交给 CI：`gate.mjs` 只做静态检查（`--affected` 跑受影响分组、`--full` 或 `--force` 在本机跑全量，都要显式加；`--full` 遇到与当前代码一致的通过记录会沿用，要重跑加 `--force`），不写测试记录；推送核对不要求本机测试记录，静态检查、未提交改动、推送引用照常核对；`merge.mjs` 合并前核对 CI 在最终提交上全部通过。须搭配 `reviewFlow: "pr"`（只有它核对 CI）和 `ciRunner`，不满足时配置报错 |
| `ciRunner` | `github-hosted` / `self-hosted` / `none`（不写 = 未声明） | CI 放哪：GitHub 托管 runner / 用户服务器上的自托管 runner（同样是 GitHub Actions，只是 `runs-on` 不同）/ 没有 CI。`fullTests` 为 `ci` 时只能是前两者；为 `local` 时只是声明 |

默认 `fullTests: local`，保持原行为，没有 CI 的项目照常可用。另有不影响闸门判定、供 agent 和工作流生成使用的环境选项（`modules.environment`，`ciFallback` 在 `modules.gate`）：

| 选项 | 取值 | 含义 |
|---|---|---|
| `ciFallback` | `github-hosted` / `self-hosted` / 不写 | 主 CI 额度用完或不可用时改用的另一处（须与 `ciRunner` 不同）。生成的工作流用仓库变量 `CI_RUNNER` 切换，不用改工作流、不用提交 |
| `ciOs` | `linux` / `windows` / `macos` 的列表，默认只 `linux` | CI 跑在哪些系统上：Linux 最快最便宜（Windows 按 2 倍、macOS 按 10 倍计费），产品要在别的系统运行时再加（更准确）。自托管 runner 只用于 Linux |
| `session` | `local` / `cloud` / 不写 | 开发和重复性工作更适合本地会话还是云端会话；不写时 agent 按下面的推荐原则选 |
| `parallel` | `parallel` / `serial` / 不写 | 能并行的并行还是串行；不写时同上 |

`session`、`parallel` 只影响 agent 怎么做，不换流程文件：值存在配置里，同步时由清单里 `rules-agents` 组件的 `render: environment` 渲染成项目 `AGENTS.md` 规则块末尾的“本项目的执行偏好”一节（没写的写“未声明”，按推荐原则由 agent 判断），agent 每次开工都读到；它们是默认偏好，具体任务仍按条件和环节表的三步判断，用户当次的选择优先。改了配置要重新同步才更新块；`check` 里块的状态为 `outdated`（详情提示重新同步）表示配置改了块还没跟上，`modified` 才是块被手改。

#### 装套件时怎么选（先问清楚，用户没选再推荐）

套件是公开分发的，每个用户的环境不同，所以首次安装前先问清楚、再装对应的版本：

1. 运行 `node <kit>/tools/environment.mjs detect --target <项目> [--choice 键=值]…`，得到本机事实（系统、CPU、内存、有没有 GitHub 远程与 `gh`）和推荐（每项带理由、冲突）。
2. 把要问的事一次问完，推荐项放第一：全量测试在 CI 还是本机跑；CI 放哪（GitHub 托管 / 自托管服务器，有没有自己的服务器、要不要后备）；CI 跑哪些系统（产品要在哪些系统上运行）；开发更适合本地会话还是云端会话；能并行的是否并行。用户已经说了想法的按用户的，不再问。
3. 用户没选或不知道怎么选：agent 直接用推荐，并告诉用户每项选了什么、为什么，用户可随时改。推荐按两条原则：一是本机的实际情况（系统决定命令写法，CPU 和内存决定本机扛不扛得住全量测试与并行任务，有没有 GitHub 和服务器决定 CI 放哪）；二是更快、更便宜、更高效、更准确——能并行就并行，并行受资源限制时先想能不能放到云端会话或 CI，不行才串行；CI 只用 Linux，除非产品要在别的系统上运行；有 GitHub 就把全量交给 CI。
4. 装：`node <kit>/sync.mjs --target <项目> --init --profile ts|python --env recommended [--choice 键=值]…`（`--env recommended` 把没选的项按推荐补全；只给 `--choice` 时只写给出的项）。首次创建配置时写入选择、按选择生成 `.github/workflows/ci.yml`（草稿 PR 不跑、只改免审文档跳过测试、汇总检查 `ci-gate` 仍成功；选了 pr 流程时它就是必需检查），并输出“本项目的执行方式”几行说明。已有配置的项目环境选择不生效，只提示，要改手动改配置。已有 `ci.yml` 不覆盖：套件看不出它跑不跑全量测试，所以 `fullTests=ci` 时必须加 `--choice requiredChecks=<跑全量测试的检查名，逗号分隔>` 写明，否则拒绝安装（不然一个只跑 lint 的 CI 也能让合并入口放行）。推荐用 `gh api user --hostname github.com` 判断 GitHub 是否可用（按 github.com 核对，不用 `gh auth status`：它会被另一个过期账号拖成失败，不带主机则可能核对到企业主机）：只装了 `gh` 没登录不算。
   - 自托管 runner 的安全：生成的工作流让来自 fork 的 PR 一律走 GitHub 托管 runner，自托管 runner 带 `self-hosted`、`linux` 两个标签，只用于 Linux；不要把自托管 runner 用在接受外部 PR 的公开仓库，并在仓库设置里要求外部贡献者的工作流经人批准后再运行；套件在装时只在“确认是私有仓库”（自动读到，或 `--choice publicRepo=false` 声明）时才接受自托管，读不出可见性按公开处理；探测到公开的仓库，声明私有也不采信。
5. 之后换环境（换机器、有了服务器、额度用完）时，按下面的表重新核对，改配置（判定策略字段须合入主干后才生效）。

#### 每类工作在哪做

环境有两维：资源（只有本机 / 本机加用户服务器）和会话（本地会话 / 云端会话）。

| 工作 | 在哪做 | 谁定 |
|---|---|---|
| 创造性工作、静态检查、受影响测试 | 当前会话所在环境（本地、云端都能做） | 不用选 |
| 全量测试 | `fullTests=local`：当前会话所在环境，本地、云端都能做；`ci`：CI（见下表） | 项目选项 |
| CI | `github-hosted`：任何环境都行；`self-hosted`：需要用户服务器；`none`：没有 | 项目选项 |
| 复审登记、合并入口 | **只能在同一个仓库副本里做完**：本机和云端沙箱是不同的副本，记录不跨副本共享，在云端登记的记录本机看不到（同一副本的各工作树之间：`pr` 流程的 PR 审查记录放在 git 公共目录、共享，`pre-push` 流程的复审记录各工作树自己一份） | 不用选 |
| 外部复审（Codex 等） | **只能在配了执行器的那台机器**：执行器的命令、模型写在仓库之外的本机配置，云端沙箱里没有 | 不用选 |
| 自托管 runner 的安装、维护 | **只能由用户（或经用户授权）在服务器上做** | 用户 |
| 依赖未推送文件、本机数据库或服务、本机凭据、图形界面、硬件的测试 | **只能在本机**；汇报里写明原因 | 不用选 |
| 启动云端会话、定时任务 | 有费用，按 R2 先问 | 用户 |

#### 每个环节的工作在哪做（环节表）

同一个任务依次经过四个通用环节：A 推送前、B PR 阶段、C 合并与收尾、W 每周巡检。每个环节里的每项工作，去处按下面的顺序定，由 `tools/stages.mjs` 的 `decideStage()` 实现。命令：`node <kit>/tools/stages.mjs --stage A|B|C|W [--target <项目>] [--choice hasServer=true] [--choice externalExecutor=true] [--choice tight=true] [--choice 工作编号=local-session|cloud-session|server]`，输出每项的去处、来源和理由；参数严格校验（未知参数、缺值、重复、`true`/`false` 以外的写法、不存在或固定去处的工作编号都报错，不静默丢弃）。项目配置优先取基准提交上生效的策略字段（与闸门一致），输出里的 `configSource` 标明来源；`hasServer` 指“有自己的服务器且 runner 在线”：对可以放服务器的工作（每周巡检）不确认就按没有，B 的 CI 全量则按项目选项展示、只在明确 `hasServer=false` 且配了自托管时转问用户；`tight` 不写则按本机 CPU 和内存探测。

1. 用户的选择：对具体工作的指定，或项目选项 `modules.environment.session`（`local` 或 `cloud`；装套件时用户选的，或按推荐写入并告知过用户，用户随时可改）。输出里前者标 `user`，后者标 `config`（项目选项），不把项目选项冒充成用户对这项工作的指定。指定了做不到的（例如没有服务器却指定服务器）当作没答，转到第 3 步问用户。
2. 用户没选时按两条原则自动判断：本机的实际情况（CPU 不超过 4 核或内存不超过 8 GB 算资源紧张，有没有自己的服务器），以及更快、更便宜、更高效。三个去处的特点：本机不花钱、步骤最少，但资源紧张时慢；云端会话不占本机、快，但启动有费用；自己的服务器不花钱也快，但要服务器和 runner 在线。一个去处在“便宜、快”上不输给其他且至少一项更好就选它；并列时选步骤最少的。
3. 多种做法都可行、两条原则指向不同（典型：资源紧张又没有服务器，本机省但慢、云端快但要花钱）时，问用户，列出可选项和各自代价，不自行决定。

只有“可选”的工作（表里标“按上面三步”的）走这三步；其余工作的去处是固定的，不给选择。两种复审流程的环节不同：

| 环节 | 工作 | 去处 | 谁定 |
|---|---|---|---|
| A 推送前 | 静态检查、受影响测试 | 当前会话所在环境 | 不用选 |
| A 推送前 | 全量测试（`fullTests=local`） | 本机或云端会话 | 按上面三步 |
| A 推送前 | 独立复审（仅 `pre-push` 流程，推送前做） | 宿主子代理或全新会话；配了外部执行器（如 Codex）的只能在那台机器上 | 不用选 |
| A 推送前 | 复审登记（仅 `pre-push` 流程） | 做推送的同一个工作树（记录在各工作树自己的 git 目录里，工作树之间、副本之间都不共享） | 不用选 |
| B PR 阶段 | 全量测试（`fullTests=ci`） | CI：`github-hosted` 或服务器（`self-hosted`；配了自托管却确认没有服务器时转问用户）；后备用仓库变量 `CI_RUNNER` 切换 | 项目选项 |
| B PR 阶段 | 独立复审（仅 `pr` 流程，可与 CI 并行开始） | 宿主子代理或全新会话；配了外部执行器（如 Codex）的只能在那台机器上（本仓库自己的规则更严：Linux、Windows CI 成功后才做） | 不用选 |
| B PR 阶段 | 登记审查记录（仅 `pr` 流程，CI 全部通过后） | 合并入口所在的仓库副本（记录在 git 公共目录，同一副本的各工作树共享，不跨副本） | 不用选 |
| B PR 阶段 | 处理复审意见、修复失败 | 当前会话（创造性工作，排在用户在场时段） | 不用选 |
| C 合并与收尾 | 合并入口（`pr` 流程） | 登记审查记录的同一个仓库副本；合并要用户授权 | 不用选 |
| C 合并与收尾 | 合并（`pre-push` 流程没有合并入口脚本） | 当前会话，按项目约定合并，要用户授权；等 PR 的 CI 全部通过（不只是必需检查；`ciRunner` 为 `none` 的项目没有 CI，无此条），不绕过失败的检查；复审与测试记录只证明推送前的状态 | 不用选 |
| C 合并与收尾 | 删除分支、清理工作树、汇报 | 当前会话 | 不用选 |
| W 每周巡检 | 巡检（重复性工作） | 本机、云端会话或服务器（确认有服务器时） | 按上面三步 |

- 命令的输出只是“按项目配置的计划”：读不到仓库变量 `CI_RUNNER`（已用它切换了 Linux 的 runner 时以实际为准），Windows、macOS 矩阵项始终在 GitHub 托管 runner 上跑；runner 是否在线、本机依赖未推送文件等具体约束，要由人或 agent 另外核实（`hasServer` 只代表你的确认）。
- 发布和发布后验收（D、E）是各项目自己的流程，不在套件的通用环节里；本仓库的见 `docs/release/README.md` 的“执行位置”。
- 外部复审（Codex 等）理论上可以迁到自己的服务器：命令和模型配置在仓库之外，迁移要在服务器上重做配置，且 Linux 上只读沙箱、无工具等行为未验证。结论是“可迁移，须先测试再迁”，套件目前不实现，也不替用户迁移。

#### 按环境组合怎么办（`fullTests=ci` 时；`local` 时全量由当前会话所在环境的闸门跑，不适用）

| 组合 | 做法 |
|---|---|
| 只有本机（本地或云端会话），`github-hosted` | 推送后 CI 在 GitHub 托管 runner 上跑。作业因额度用完启动不了时，agent 不自行改配置，列出可行做法让用户选：等额度或充值；在本机或云端会话用 `gate.mjs --force` 把全量重新跑通（`--full` 会沿用旧的通过记录，不算新证据），结果写进 PR，由用户合并（`pr` 流程的合并入口要求 CI 全过，CI 起不来时它会拦下，不要为此改配置绕过） |
| 只有本机，选了 `self-hosted` | 没有服务器，行不通：说明原因，改选 `github-hosted`，或把 `fullTests` 改成 `local`（同时 `reviewFlow` 可留 `pr`，全量由闸门在会话所在环境跑） |
| 本机加服务器（本地或云端会话），`self-hosted` | CI 在服务器上跑。runner 离线时如实报告，让用户选：启动 runner；切到后备 `github-hosted`（把仓库变量 `CI_RUNNER` 设成 `github-hosted`）；或在会话所在环境用 `gate.mjs --force` 重新跑通全量、写进 PR 由用户合并 |
| 本机加服务器，`github-hosted` 额度用完 | 配了 `ciFallback: self-hosted` 的，把仓库变量 `CI_RUNNER` 设成 `self-hosted` 即可，不用改工作流（设仓库变量是对外部服务的改动，按 R2 先问用户）；没配的让用户选：装好 runner 后改 `self-hosted`、等额度、在会话所在环境用 `gate.mjs --force` 重新跑通全量并写进 PR 由用户合并 |

- 已知限制：（1）已有 CI 的项目，`requiredChecks` 里写的检查名由用户负责，套件只查名字出现在 `ci.yml` 里，查不了该检查是否真的跑全量测试（只跑 lint 的检查名也会被接受）；（2）生成的 `ci.yml` 把安装时的 `reviewIgnore` 固化在文件里，之后改了配置里的免审范围要同步改 `ci.yml`，否则 CI 与闸门对“只改文档”的判断会不一致；（3）`testEnv`、`testCommand` 安装后改了同样要同步；（4）`pr` 流程还要求 `gh` 已登录，未登录时 `detect` 会列为冲突。（5）origin 地址只认 github.com（含 ssh.github.com）上的“属主/仓库”，企业版主机、路径里碰巧含 github.com 的地址不当作 GitHub 远程，探测和 `gh` 调用都显式指定 github.com 与该仓库。
- 改 `fullTests` / `ciRunner` 是判定策略改动，先合入主干才生效；CI 不可用而卡住这个 PR 本身时，由用户合并。
- 不降低标准：CI 起不来时，全量测试仍要在某个环境跑通并有证据（`gate.mjs --force` 的输出和测试记录；要重跑用 `--force`，`--full` 会沿用一致的旧记录），再由用户决定合并；不因为 CI 不可用就跳过全量。
- `CI_RUNNER` 变量只切换 Linux 作业；Windows、macOS 的矩阵项始终用 GitHub 托管 runner，托管额度用完时它们也跑不起来——额度紧张的项目 `ciOs` 只留 `linux`。
- 生成的 `ci.yml` 是项目自己的文件：安装时写入的 `testCommand`、`testEnv` 之后改了，要同步改 `ci.yml`，套件不会自动同步。
- 本机和云端会话都能做的，按“每个环节的工作在哪做”的三步决定（用户的选择 > 两条原则 > 原则指向不同时问用户）；只能本机做的，在汇报里写明为什么。
- 操作系统决定命令写法：Windows 用 PowerShell 写法（路径含空格加引号），macOS、Linux 用 shell 写法；云端会话按沙箱的系统（通常是 Linux）。工作流里的 CI 系统由 `ciOs` 决定，与本机系统无关。

## 2. 需求与方案

- 低风险改动直接做。中高风险（跨模块、新接口、数据库结构、权限、费用、服务器配置）先澄清需求，写功能契约，取得用户确认。
- 澄清按 R3：先查已有资料和确认记录，查得到的不问；剩下的归成一张清单一次问完，每个问题给出选项，推荐项放第一并写一句理由。
- 契约放在 `docs/04-开发/`，模板见 `docs/_templates/feature-contract.md`。契约定义“怎样证明正确”，验收标准不得擅自弱化。涉及日期、时间字段的，在契约里写明时区口径（存储、展示和输入、按日切分的边界各按哪个时区）。契约的“预期行为与异常边界”表按操作逐类写出正常、失败、超时、并发或重复、边界值的预期，测试依据这张表写，不从实现倒推。
- 契约里的预期和场景表交用户集中确认一次；之后同一功能的小修复沿用这份契约，需求变了才重新确认。
- 实现中自行确定的口径要单列，待用户确认，不写成已决定。
- 方案对比至少写三栏：复杂度、风险、能否回退。推荐只是建议；用户选定或“按授权采用推荐”之后才成为决定，并写进决定记录。

## 3. 开发

- 测试先行：改源文件前，先写或补引用它的测试。测试随改动一起改。识别方法、支持范围与局限（含间接引用须在豁免表里写理由）见 `../SKILL.md` 第 6 节。
- 注释：每个源文件有业务职责说明；导出的函数、类、常量前有说明（输入输出、异常、为什么这样做）。
- 目录：代码按语言惯例放 `src/`、`tests/`。新顶层目录须在白名单内：`layout.topLevelAllowed`，加上 `sourceGlobs`、`testGlobs` 里写明的顶层目录。

## 4. 测试、审查与合并（目标流程）

目标顺序：PR 前受影响测试 → CI 与独立代码复审、一致性审 → 合并；复审可以与 CI 并行开始；CI 全部通过后才登记、合并。套件闸门的 `pr` 流程实现了“CI 与双审 → 合并入口”这一段（见本节末“套件闸门的两种流程”）；受影响测试由 `gate.mjs --affected` 按项目配置的测试分组选择，判断不了影响范围时自动改跑全量（见本节末“测试模式与结果复用”）。默认的 `pre-push` 流程次序不同：复审在推送之前，见本节末“套件闸门的两种流程”。全量测试是在本机还是 CI 跑，由 `modules.gate.fullTests` 决定（第 1 节“执行位置与排程”）；`ci` 只能搭配 `pr` 流程。适配状态见 `../SKILL.md` 第 5 节；项目已有更完善流程时，以项目规则和实际闸门为准（R1）。

1. PR 前执行静态检查及受影响的单元、集成、端到端、视觉和安全检查；不能可靠判断影响范围时扩大范围或跑全量，说明选择及结果。测试用隔离环境和合成数据。
2. CI 对最终提交执行全量单元测试和项目适用的全量集成测试；端到端、兼容性、安全等检查按风险安排，明确跳过的理由。复审可以与 CI 并行开始；CI 全部通过后才登记、合并；必需检查须为成功（`pr` 流程的判定见本节“套件闸门的两种流程”一段）。
3. 按下方分档进行独立代码复审和增量一致性审（矛盾、重复、过时）；一致性审可以集中审多个 PR，但每个 PR 的最终提交、所做审查的结论及证据各自记录。合并前核对 PR、最终提交、CI 和该档要求的审查；提交或基线变化后重新核查受影响部分。
4. 审查发现的高、中级问题，以及影响体验或使用的问题在合并前修复；低级和提示级问题默认记入 PR 的后续清单；已登记、不扩大风险的可以同批改并写明，修后复核一并核对；不为它们单独再修一轮。每轮复核后先做收敛检查：问题再次出现、严重程度升高或数量比上一轮多，都先核实并查原因、系统地修，拿不准的问用户，见入口技能的 review.md 第 8 节“收敛检查”。本次引入的矛盾、重复和过时问题同样按级别处理：高、中级的在本 PR 修复，低级的同样默认记入后续清单。同一 PR 三轮审查后仍需下一轮时，向用户说明问题、原因、已做处置和建议，等待用户决定。套件闸门按被审内容机械计数：一轮是登记过代码复审或一致性审 fail 的一份被审内容，`pr` 流程是同一 PR 的一个最终提交，`pre-push` 流程是同一分支上登记时的一份工作区内容（按树哈希加文档内容哈希区分，不按 HEAD 提交号）；同一份内容上两种审查都不通过只算一轮，修复后在新内容上再不通过才算下一轮；已有 `modules.review.maxReviewRounds`（默认 3）份不同内容登记过 fail 后，再登记 pass 或 fail 都被拒，用户同意继续的带 `--user-decision "<用户的决定及出处>"` 重新登记；唯一例外是在已计入的内容上首次登记另一种审查。用户知情后决定接受报告里的问题、不再修改的，登记 `accept`（报告结论须为不通过），它不计轮次，合并入口和推送核对按用户决定放行。
5. 合并遵循项目规定与实际授权；不绕过失败的必需检查。`pr` 流程下合并只经 `merge.mjs`，它核对 CI 与两项审查都针对 PR 的最终提交；`pre-push` 流程的记录只证明推送前复审，不能证明对 PR 最终提交的双审查或最终 PR 绑定。

审查频率按风险分档（风险分级见第 2 节）：

| 改动 | 代码复审 | 一致性审 |
|---|---|---|
| 只改文档（`reviewIgnore` 之内） | 不做 | 并入每周巡检（第 8 节） |
| 低风险小新增、小改动 | 每个 PR 合并前 | 可延期：并入每周巡检，或与其他 PR 集中审；延期要写明理由 |
| 中高风险 | 每个 PR 合并前 | 每个 PR 合并前 |

代码复审不攒到合并后：结论绑定 PR 的最终提交，合并后才发现的问题已在主干上，后续 PR 又叠在其上。一致性审可以集中审多个 PR，结论仍按 PR 各自记录。拿不准风险档位时按高一档处理。

套件闸门的两种流程（`engineering.config.json` 的 `modules.gate.reviewFlow`，命令在项目的 `scripts/engineering/gate/` 下）。两种流程共同的规则：闸门的判定依据不由被审分支决定。基准分支设置 `modules.gate.base` 以默认主干上的配置为准；判定策略字段 `reviewIgnore`、`reviewFlow`、`requiredChecks`、`reviewers`、`reviewMinChars`、`reviewSections`、`reviewKeyword`、`maxReviewRounds`、`fullTests`、`ciRunner`、`externalExecutors`、`externalExclude`（外部复审的两项；`externalExclude` 另与工作区的值取并集，当轮生效，不给提示行）取基准提交上的配置（基准上还没有配置时用工作区的值）；分支里改其余字段要合入主干后才生效，工作区的值与生效值不同时闸门和推送核对会给提示行。测试命令、测试分组、glob 等其余字段仍用工作区的值。git 的 pre-push 钩子核对实际推送的提交：分支推送的提交必须是当前 HEAD 或已在基准分支里，`git push origin 别的分支` 会被拒绝；标签推送不查引用，只删除远端引用（分支或标签）的推送直接放行。

- `pre-push`（默认）：`gate.mjs` 通过后由独立复审者（宿主子代理、外部执行器，或宿主没有子代理时用户另开的全新会话，都不共享作者上下文）复审，`review.mjs pass|fail --reviewer <名> --report <复审数据> --summary "<一句话>"` 登记（复审数据是 `ek-review/1` JSON，写法见插件入口 `review.md` 第 7 节；中高风险另带 `--evidence-checked "<主对话核对了什么>"`）；推送时核对静态检查、测试记录和复审记录，两份记录都绑定当前代码树和基线（`changedFiles` 做 diff 的基准提交）：合入新主干、变基后基线变了，旧记录作废，要重跑闸门并重新复审（没有基线字段的旧记录同样不认）。登记时除树哈希和基线外，还写明分支、HEAD 提交号、文档内容哈希和未提交的文件数：树哈希不含文档，只改规则文本这类改动每一轮都相同，靠提交号和文档内容哈希才能把登记对应到具体提交；推送核对认的是树哈希与基线。每次登记另追加到 git 目录下的 `engineering-gate/reviews/log.jsonl`（闸门记录所在的目录，不是 docs 下的记录目录），数据副本和由它生成的报告放在同目录的 `branches/<分支>/` 下。一致性审也可以登记：`review.mjs pass|fail --kind consistency …`，按分档延期用 `review.mjs defer --kind consistency --reason "<理由>"`；它只写进 log.jsonl 和 `review-consistency.json`，推送核对不要求它（不带 `--kind` 等同代码复审）。用户接受风险用 `review.mjs accept --kind code --reviewer <名> --report <复审数据> --user-decision "<用户的决定及出处>"`（`external:` 名字不接受，外部复审的接受风险见第 4 节 `pr` 流程一条：`external-review.mjs register --accept`），推送核对认它并写明按用户决定放行。推送核对要求全量测试记录：复审过程中用 `gate.mjs --affected` 的，最终推送前跑一次 `gate.mjs`。套件不提供合并入口，Claude Code 的钩子拒绝直接 `gh pr merge`（别的宿主里没有这层钩子，只有 git 的 pre-push 钩子生效，同样不得直接合并）；合并按项目约定的入口，并等 CI 全部通过（`ciRunner` 为 `none` 的项目没有 CI，无此条）。项目没有约定入口时由用户合并或由用户指定入口。
- `pr`：`gate.mjs` 通过后即可推送，推送核对只要求静态检查和与当前代码、当前基线一致的测试记录（按影响范围的也认，CI 会在最终提交上跑全量）；`fullTests` 为 `ci` 时不要求本机测试记录（见“执行位置与排程”的项目选项）。按上表分档审查，复审可以与 CI 并行开始；CI 全部通过后才登记、合并。“CI 全部通过”指 PR 最终提交上：必需检查都是成功；非必需检查是成功、跳过或中性；失败、取消、运行中等其余结论不论必需与否一律不通过；一项检查都没有也视为未通过。同一工作流里同名的检查合在一起判定（同一个 job 可能因 push 与 pull_request 各跑一份）：有一份成功、其余只有跳过或中性的算成功；不同工作流里的同名检查各算一组、不互相抵（必需检查名出现在几个工作流里，每一组都要成功），报告里这几组带上工作流名分开显示（同名的检查运行与提交状态也各算一组；没有工作流名的那几组，显示名带“（CheckRun）”“（StatusContext）”）。必需检查名写在 `modules.gate.requiredChecks`，为空时每一项检查都算必需：写检查运行的 job 名（含矩阵后缀，不含工作流名和事件，例如 `test (ubuntu-latest)`）或提交状态的 context，与 GitHub 分支保护里必需检查的写法相同；PR 页面上显示的“工作流名 / job 名 (事件)”不是这个名字，用 `gh pr view <PR> --json statusCheckRollup --jq '.statusCheckRollup[] | .name // .context'` 查。列出的必需检查在 PR 上找不到（没有运行或改了名）按未通过处理，提示里列出本次看到的检查名。它是判定策略字段，取主干上的值，配置和 job 不放在同一个 PR 里一起删：给必需检查改名，先用一个 PR 新增新名的 job（旧 job 保留）并把配置改成新名，这个 PR 仍按主干上的旧名判定，能通过；合入后再用另一个 PR 删掉旧 job。删掉一个必需检查，先用一个 PR 删配置里的名字，合入后再删 job；别把配置里的名字删空，空数组表示每一项检查都必需，会让按条件跳过的检查都拦下合并。不要先在主干配置里加还没跑起来的新名，否则其余 PR 都报“没有出现在 PR 上”。配错卡住时连修正它的 PR 也过不了合并入口，由用户合并这个修正 PR。PR 未打开或 CI 未全过时拒绝登记：
  - 代码复审：`review.mjs pass|fail --pr <编号> --kind code --reviewer <名> --report <复审数据> --summary "<一句话>"`（中高风险另带 `--evidence-checked`）。数据的 `reviewedCommit` 必须是登记时 PR 的最终提交，被审范围要完整覆盖（从与主干的分叉点开始，或接上同一种审查此前一次完整覆盖的登记），只覆盖部分差异的只能登记 fail；登记在 PR 登记锁内进行，同一 PR 同时只有一个登记（锁是 git 引用 `refs/engineering-gate/locks/pr-<编号>` 的比较交换，持有者进程已不在时自动回收；持有者信息读不出时报占用，确认没有进程在用后按提示用 `git update-ref -d` 删除）。`--reviewer` 不接受 `external:` 开头的名字：外部复审者只能由 `external-review.mjs` 登记（两种流程都一样），手动登记会被拒绝。
  - 一致性审：同上，`--kind consistency`；按分档可延期时用 `review.mjs defer --pr <编号> --kind consistency --reason "<理由>"`。
  - 合并：`merge.mjs <编号> [--method squash|merge|rebase]`。PR 打开、CI 全过、代码复审为 pass、一致性审为 pass 或延期、两份记录的提交都等于当前最终提交，才执行 `gh pr merge --match-head-commit`（默认 squash 并删除远端分支）；否则逐条列出原因，不合并。输出把成功的检查（标明必需与否）和被放行的跳过、中性检查分开列出，跳过的不算通过。PR 又有新提交时记录过期，重新审查后再登记；只有一个例外：代码复审之后的新提交只改了文档（`git diff --no-renames` 的文件全在 `reviewIgnore` 之内；项目配置、豁免表、`scripts/engineering/**`、风险登记文件（`modules.review.riskRegister`）不算文档，改名按旧路径删除加新路径新增算，代码改名进 docs/ 不算只改文档）时，代码复审记录仍认，输出写明沿用及两个提交号，本地算不出差异时按过期处理，一致性审记录仍须针对最终提交。
  - 轮次收口（可选，`modules.review.roundClosure: fix-and-record`，只限 `pr` 流程）：满轮次后只剩中、低级时修完中级，`review.mjs risks --pr <编号> --shared-summary <kind>:<编号>="<可共享摘要>"` 生成风险登记（`modules.review.riskRegister`，JSON Lines，只存编号、指纹和摘要，不写复审原文）并提交，修复差异只能含白名单内的文件（定位文件、申报的修复路径、测试、文档、风险登记），`review.mjs close --pr <编号> --summary "<一句话>"` 登记，合并入口按收口放行；有高级时开放一轮最后的复核，系统性问题或无法彻底解决时停下交用户。阶段口径见插件入口 `review.md` 第 8 节“轮次收口”。
  - 用户接受风险：`review.mjs accept --pr <编号> --kind code|consistency --reviewer <名> --report <复审数据> --user-decision "<用户的决定及出处>"`，数据的结论须为不通过；合并入口把它当作可放行，输出写明按用户决定接受风险放行。外部复审者（`external:` 名字）的不通过不能这样手动登记：用 `external-review.mjs register --run-dir <运行目录> --accept --user-decision "<用户的决定及出处>"`；满轮次上限后用户同意继续的，同一命令不带 `--accept`、带 `--user-decision` 重登。
  - 只改文档的 PR（本地算出的基准提交到 PR 最终提交之间全部文件在 `reviewIgnore` 之内；本地没有最终提交、基准分支解析不了或算不出共同提交时按含代码处理，输出写明原因并提示先 `git fetch`；口径同闸门：`reviewIgnore` 取基准提交上的配置，含项目配置、豁免表、`scripts/engineering/**` 或风险登记文件的不算）按上表不做审查，合并入口只核对 PR 打开与 CI 全过；差异为空时也按含代码处理。其余 PR 合并入口不判断风险档位：代码复审必需，能否延期一致性审由登记者按上表判断。
  - 需要 GitHub 远程和已登录的 `gh`；没有 CI 的项目留在 `pre-push`。

测试模式与结果复用（两种流程相同）：`gate.mjs` 跑配置的 `testCommand` 全量，通过的全量记录另存一份，记下当时范围内每个文件的内容哈希。`gate.mjs --affected` 以这份全量记录为起点算出此后改动的文件，每个改动文件都要命中 `modules.gate.testGroups` 里至少一个分组的 `paths`，命中的分组各跑一次 `command`；没有配置分组、没有可用的全量记录、基线或测试配置与全量记录不同、有改动不属于任何分组、改动涉及项目配置、豁免表、套件脚本或依赖清单与锁文件、这份代码（同一代码树、同一基线）上次的全量测试未通过、带 `--force` 而全量记录之后没有改动时，自动改跑全量并在输出里写明原因；不带 `--force` 而全量记录之后范围内没有改动时，直接沿用全量记录。已有通过的记录、且代码树、基线和测试配置（`testCommand`、`testEnv`、`testGroups`）都一致、模式满足要求时，闸门不重跑，输出“沿用已有通过记录”，要重跑加 `--force`；最近一次运行说了算：同一代码树、同一基线、同一测试配置上最近一次运行（全量或分组）未通过时不沿用任何记录，全量未通过时同一棵树的全量通过记录作废，失败之后的下一次运行一定真的跑。静态检查每次都做，其中断言检查要求本次改动的测试文件里有断言的痕迹，测试用例数比基准提交少时只提示、不拦截。

怎样读闸门的输出：闸门通过时先打印测试先行检查、注释检查、断言检查三行，再是测试结果一行；改跑全量或按影响范围测试时，测试结果前多一行说明原因或分组，沿用已有记录时测试结果一行换成“沿用已有通过记录”。前两行各写明本次改动的源文件里检查了几个、豁免了几个（测试先行另列“无需测试”的：已删除、没有可测的导出、只有再导出的文件；语言不支持而没能检查的另起一行写“未检查”并列出文件，不算无需测试）；都是 0 表示这次没有改到源文件。两行的范围不同：注释检查不看 `reviewIgnore` 之内的和已删除的源文件，所以两行的数字可以不一样；断言检查一行写明本次改动的测试文件查了几个，测试文件里找不到断言痕迹的判不通过（确实不需要断言的在豁免表 `assertions` 段写理由）；测试用例数比基准少时多一行提示（改名的测试文件按改名前的文件比较，规则见 `../SKILL.md` 第 6 节），不拦截，复审时核对是不是有意删的。最后一行括号里写明全量还是哪几个分组，以及 `reviewIgnore` 之外改动的源文件数。静态检查不过时，闸门只报出问题（有未检查的文件时，问题清单之后同样列出它们），不打印这些通过行，也不跑测试。同样的计数写在测试记录 `tests.json` 的 `staticChecks` 里。

## 5. 预发、生产与事故回归

生产发布、回滚、数据恢复、破坏性迁移的授权按 R2。

- 预发使用与生产一致的发布产物，按风险执行核心流程、冒烟、验收、回归、视觉、兼容、安全、性能与负载检查；压力测试在专项环境按需进行。修改或修复后做针对性 sanity 检查。记录不适用项及原因。
- 发布前准备并验证回滚方案、上一版本与数据迁移的兼容性、备份和恢复路径；镜像回滚不等于数据恢复。按项目授权部署，小范围灰度和健康检查通过后扩大，生产持续监控，异常按授权和预案处置。
- 用户验收的证据写进验收证据包（模板 `docs/_templates/acceptance-pack.md`，放 `docs/acceptance/`），发布记录放 `docs/release/`。
- 事故或测试漏检须调查为何测试和 AI 审查未发现、是否缺少测试或安全检查、CI 是否需要调整。将问题转成稳定、可重复的回归用例，放入适当阶段；无法自动化时记录原因、责任人和可执行的专项检查并跟踪补齐。可将事故、相关 PR、修复和回滚整理成脱敏样例，持续评估审查能力。

## 6. 文档与目录规则

| 类别 | 位置 | 规则 |
|---|---|---|
| 活文档（需求、架构、计划） | 阶段目录 | 原地覆盖，历史靠 git |
| 记录类（ADR、验收证据包、发布记录） | `docs/adr/`、`docs/acceptance/`、`docs/release/` | 只追加，不改、不删、不改名旧文件（巡检会报错） |
| 模板 | `docs/_templates/` | 只读，复制后使用 |
| 阶段索引 | `docs/README.md` | 每个阶段目录都要登记 |

新建文件须满足以下之一：独立生命周期、独立被引用、独立时间点。并登记到所在阶段的 README：在表格第一列写文件名（整格），或用反引号、链接写出；子目录里的文件怎样登记（只写文件名不算）见 [SKILL.md](../SKILL.md) 第 6 节。没登记的巡检会报错。推送核对会拦截不在允许位置、又没有理由的新文件；理由写在豁免表 `newFiles` 中。

新建目录或文件的位置：

- 项目根目录之外：须先经用户批准，不得自行创建。说明要建在哪里、建什么、为什么，得到同意后再建。会话的临时目录（scratchpad）不在此限。
- 项目根目录之内：可以按上面的规则创建；任务完成后逐个检查本次新建的目录和文件，不必留下的全部清理（见第 7 节）。

大版本（例如 v2）才用新目录（如 `v2/`）；同一版本内不新建平行目录。

阶段目录：`00-总览`（项目状态、决定与交接记录、实施交接与追踪矩阵）、`01-需求`、`02-原型`、`03-架构`、`04-开发`、`05-测试`、`06-发布`（可在 `layout.stages` 中修改；已安装项目写在配置里的阶段不随同步改变，同步会给出升级提示）。代码仍按语言惯例放在 `src/`、`tests/`。

## 7. 收工

1. 合并后删除远端与本地分支，清理工作树（`git worktree remove`）。合并入口报错时，先用 `gh pr view <编号> --json state,mergedAt` 确认 PR 是不是其实已经合并，再决定是否重试：已经合并的不再重试，直接收工。清理自己所在的工作树要回到主检出里做（`git -C <主检出> worktree remove <工作树>`），不在要删的工作树里删它自己。
2. 列出本次新建的目录和文件（`git status`、`git diff --no-renames --name-only --diff-filter=A <基准>`），逐个检查是否满足第 6 节；不必留下的清理掉。
3. 更新阶段索引（`docs/README.md` 和所在阶段的 README）。
4. 删除临时文件（scratchpad、导出物），不留在项目目录里。
5. 经验提炼（对应全局 CLAUDE.md 的“经验提炼”）：
   - 用户本人提出的决定或做法：直接记录到项目的 `practices/`（不跟踪）。
   - agent 总结的：只作为候选，列出标题、依据和建议归属，向用户确认后才记录或升格为能力。升格为能力时，写成变更集（见第 9 节），走同一条原子路径。
6. 汇报分四段，各有小标题，没有内容的写“无”：任务完成情况（做了什么、是否通过、实际做了哪些检查、证据在哪里）、后续待办（谁做、依赖什么、何时做）、用户需知（已做的默认选择、已知限制、风险，以及跳过了什么、没检查什么）、经验提炼。

### 经验记录

- 记录用户本人提出或采纳、跨项目可复用的决定、规则和解决问题的方法；项目特有结论仅提炼可迁移的做法。没有可记录的经验时不强行总结。已有条目更新而不重复；未采纳的 agent 建议不作为用户经验。
- 记录放在项目根目录的 `practices/`，不存在时直接新建；Git 仓库把该目录加入 `git rev-parse --git-common-dir` 下的 `info/exclude`，不跟踪、不提交。非 Git 项目直接创建。
- 按主题维护 `product-development.md`、`workflow.md`、`agentic-engineering.md`，以 `README.md` 索引；按实际需要创建。
- 每条记一条可迁移的原则、适用背景、要解决的问题、具体做法、可核实的实际效果和首次出处（项目、日期、例子）。效果未确认就写明，之后在原条目更新；再次验证可补充出处。
- 本轮有新增或更新时，汇报文件和条目；没有则如实说明。

## 8. 巡检（熵管理）

- 机械检查：`node <项目>/scripts/engineering/gate/hygiene.mjs`。检查顶层目录白名单、禁用文件名片段（copy、final、bak 等）、死链、阶段索引、阶段内登记、状态合法性、记录类只追加、重复内容、空目录、超期草稿、已合并分支与残留工作树。“已合并分支”按补丁等价判断，squash 合并后的分支需人工复核。
- “阶段索引”查各阶段目录有没有登记到 docs 根目录的 README；“阶段内登记”查阶段目录里的文件有没有登记到该阶段的 README（R6），没登记的报错，记录目录不查；登记的写法见第 6 节。以点开头的文件和 README 自己不查。
- 巡检只报告，不删除；删除按 R8。
- 套件有没有漂移不归巡检查，用 `../SKILL.md` 第 2 节的漂移检查。
- 语义一致性审：由子代理只审增量（本次或本周期新增、修改的文档），找出规则与文档之间的矛盾、重复、过时。
- 周期：建议每周一次，或在大批合并之后。巡检由用户或已授权的定时任务（R2）触发；语义一致性审的增量从上次巡检所在的提交算起，汇报里写明这次的起止提交。

## 9. 整包（一键复用、更新、回滚）

安装、升级、漂移检查、回滚、变更集与发布的命令只写在本技能的 `../SKILL.md` 第 1–4 节。

## 10. 授权边界

授权按 R2 和项目 AGENTS.md 的授权表：授权表里写了的按表执行，没写的先问用户。任务获得批准之后，推送功能分支、合并（经合并入口）、构建、预发部署属于常规动作，不必逐次再问；R2 列为始终单独授权的事项不在其内。整包发布（套件自身的发布）只提交套件目录，不推送，不开 PR，除非用户明确要求。
