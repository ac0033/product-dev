# 独立复审

交付段“独立复审”一步的方法：怎样派发首轮复审和修后复核、审什么、怎样分级、复审数据怎样写才能登记、不通过之后怎样收敛。作者自查不在这里，见 [self-review.md](self-review.md)。

## 1. 派发

复审者必须独立：宿主子代理、外部执行器（其他厂商的模型），或宿主没有子代理时用户另开的全新会话（见“宿主没有子代理时”），都不共享作者上下文，不能是写代码的主对话自己。登记时 `--reviewer` 填实际派发的复审者名（外部执行器是 `external:<执行器名>`，见本节末“外部复审者”），它要在项目配置 `modules.review.reviewers` 的名单内（按基准提交上的配置判定，功能分支里改名单要合入主干后才生效；套件 0.5.0 起的默认名单是 `product-dev:code-reviewer`、`feature-dev:code-reviewer`、`/code-review`、`general-purpose`；项目配置里写了名单的以项目的为准）。

| 复审者（登记名） | 用在哪里 | 注意 |
|---|---|---|
| `product-dev:code-reviewer` | 首选的代码复审，定义在插件的 [agents/code-reviewer.md](../../../agents/code-reviewer.md) | 套件 0.5.0 起新装的项目默认名单里已有它；用更早版本安装的项目没有，见下一段。它只有只读工具，不能写文件、不能运行命令 |
| `general-purpose` | 宿主的通用子代理：一致性审用它；首选不可用时代码复审也用它 | 必须带第 2 节的任务书；代码复审时把上面那份定义文件的正文一并交给它 |

`product-dev:code-reviewer` 不在名单里时（用 0.5.0 之前的套件安装的项目会这样：升级套件不改项目配置）：把它加进项目配置是改闸门的行为，先得到用户同意（R2），且名单要合入主干后才生效；没有同意就改派 `general-purpose` 并按实际登记，不借用名单里别的名字。

首轮怎样派：代码复审和一致性审针对同一个最终提交并行派发，各带一份第 2 节的首轮任务书。任务书只给核心上下文（依据、提交、差异文件、文件清单、验证证据），复审者需要时自己去读调用方和相关测试，主对话不把代码或本文的原文贴进任务书。复审可以与 CI 并行开始；CI 全部通过后才登记、合并（`pr` 流程的登记脚本和合并入口在 CI 未全过时拒绝）。

安全专项（中高风险必做）：默认由同一位代码复审者带上第 4 节的安全清单一并做，任务书里写明，发现写进它的代码复审数据。只有改动很大（例如超过约三百行，或同时涉及认证、权限、外部集成中的两项以上）时，才另派一个只审安全的子代理：它交一份独立的复审数据（第 7 节）；它的结论不通过时，用这份数据登记代码复审的 fail，两份都通过才用代码复审的数据登记 pass。

模型：按 R9 的分档，写在派发的调用参数里，以任务书和调用参数指定的模型为准；三个 `code-*` 子代理定义里写死的 `model: sonnet` 是 feature-dev 第三方原文，构建时原样复制，不作数；宿主不能指定模型时，在数据和汇报里写明实际用的模型。用中档模型的复审者，在数据里另写一节“局限”，单列它拿不准或超出任务书范围的地方，主对话就这些地方改派更强一档重审，不把中档的结论当作这些地方已经审过。

宿主没有子代理时（指派发不了任何子代理：例如只能对话的工具，或派不了子代理的云端会话；只是不能指定模型的单模型宿主、能派子代理的云端会话不算，照常派宿主子代理，模型按 R9 写明实际用的）：复审不跳过，也不由写代码的主对话自审（R7）。按下面的次序选，用实际的复审者登记，汇报里写明用了替代办法：

1. 外部复审者：项目已配外部执行器时优先（见下面“外部复审者”三步），登记名是 `external:<执行器名>`；它由套件启动，在宿主之外的进程和仓库之外的只读副本里运行，不要求宿主有子代理（执行器和它的登录要在当前环境里可用）。
2. 新开会话做独立复审：请用户另开一个全新会话（宿主能换模型的，按 R9 分档选），只交给它第 2 节的任务书、差异文件和依据，不带写代码会话的上下文；它按第 7 节把复审数据放在回复里，主对话（或用户）原样存成文件、核对（R9）后登记。它是宿主子代理的等价物：没有作者上下文的通用复审者，登记名用名单里已有的 `general-purpose`，不为它另起新名（不用 `external:` 开头的名字，也不借用 `product-dev:code-reviewer` 这类专用名）。项目自定义的名单里没有 `general-purpose` 时，把它加进主干配置是改闸门的行为，先得到用户同意（R2），合入后再登记；不同意时按下面第 3 条处理。用第 2 条登记的复审，PR 里的复审摘要都要写明复审者是用户另开的新会话、实际模型和局限。
3. 两条都做不到：不降低标准，不把自审记成独立复审；`pr` 流程的合并入口因缺复审记录拒绝合并。如实告诉用户“独立复审未完成”和原因，由用户决定怎么办（R4）。

子代理定义与任务书不一致时，以任务书为准，不改插件里的定义文件：`product-dev:code-reviewer` 的定义按置信度过滤、默认审未暂存的改动、用自己的报告格式，这几处由第 2 节两份任务书的开头一段改掉。

外部复审者（其他厂商的模型，不消耗宿主的模型额度）：由套件的 `external-review.mjs` 调用。它与厂商无关，内置执行器是 Codex CLI（按 Codex 当前的登录计费，ChatGPT 登录即用订阅额度），别的厂商写一个遵守其协议的命令接入。接入和使用分三步：

1. 配置。项目在主干的配置里把执行器名加进 `modules.review.externalExecutors`（如 `["codex"]`），把 `external:codex` 这样的真实名字加进 `modules.review.reviewers`；两处都是判定策略，合入主干后才生效。套件默认名单不加，改它要用户同意（R2）。本机在仓库之外写 `~/.engineering-kit/external-review.json`，记执行器的命令、默认模型和推理强度，例如 `{"executors":{"codex":{"type":"codex","command":["codex"],"defaultModel":"gpt-6.1-sol","defaultEffort":"medium"}}}`。命令不经 shell 启动：Windows 上要写可执行文件（如 `codex.exe` 的完整路径），不能写 `.cmd`。密钥和登录留在执行器自己那里，不写进任何配置；执行器只拿到系统运行所需的环境变量（含代理变量，代理地址里带的账号口令也会传过去）和本机配置里显式写的 `env`。用 API 密钥环境变量登录的执行器（如 `OPENAI_API_KEY`），在本机配置的执行器里加 `"passEnv": ["OPENAI_API_KEY"]`，只写变量名、不写值，否则拿不到。
2. 调用。在被审分支上运行 `node scripts/engineering/gate/external-review.mjs run --executor codex --kind code --round first --pr <编号> --model <模型> --model-chosen-by user|agent --model-reason "<依据>"`。一致性审用 `--kind consistency`；修后复核用 `--round followup`（`pr` 流程自动从 PR 的登记历史取上一次同种审查不通过的高、中级发现，要求复审者逐条处置；这份待处置清单只外发编号和级别，有这类发现时必须同时用 `--prior-report <文件>` 附上一份不通过登记的报告（登记记录里 `report` 指向的文件），发送前按当前外发策略核对（例如去掉此后新列入 `externalExclude` 的文件内容），保留“指纹”一行，每条编号留下可核对的问题摘要；没附、缺指纹或缺编号都拒绝运行；某条发现连摘要都不能外发的，这一种审查本轮改由能看到原材料的复审者（宿主子代理）做；`pre-push` 流程可用 `--prior-report <文件>` 附上一轮材料作参考）；中高风险加 `--risk high`（要求输出测试缺口检查）；`--context <文件>` 附依据与验证证据的摘录，它和 `--prior-report` 各不超过 64 KiB，只放摘要，不放整份日志；`pre-push` 流程不带 `--pr`，审的是本地 HEAD；不写 `--model` 时用本机配置的默认模型，选择者记为 `config`。它只外发去掉密钥类文件的被审提交，在仓库之外的副本里运行（执行器只读、不给工具；副本文件在 Windows 上不设只读属性，复审前后核对副本哈希，复审者写过文件就不出可登记的结果），跑完核对副本、仓库工作区和最终提交都没变；结论由代码按发现判定，转成第 7 节的复审数据并生成报告；执行失败、超时、拿不到实际模型、数据不合格（例如高、中级缺理由或建议改法，只有低级却判不通过）时不出可登记的结果，原因逐条写在输出和运行目录的 `assessment.json` 里。运行目录每次新建、只归这一次运行：`--out-dir` 指向已存在的目录会被拒绝。没外发的改动文件（密钥类文件、项目配置的 `externalExclude`）记进数据的 `unreviewedFiles`，这次外部复审因此只算部分覆盖、不能登记通过：这类改动要由能看到它们的复审者（宿主子代理）完整复审。模型同样按 R9 选；跨厂商比不出强弱时，把依据和不确定性写进 `--model-reason`，它会进报告。
3. 登记。`pr` 流程等 CI 全部通过后再登记：运行 `node scripts/engineering/gate/external-review.mjs register --run-dir <运行目录> --pr <编号> --summary "<一句话>"`（运行目录和这条命令都在上一步的输出里），不必重跑模型；CI 已经全过时，上一步也可以直接加 `--register --summary "<一句话>"`；中高风险（`--risk high`）不能这样直接登记：先出结果，主对话对照功能、层级、边界核对证据后，用 `register --run-dir <运行目录> --evidence-checked "<核对了什么>"` 登记。两种写法登记前都再核对一次最终提交仍是被审的那个；`pre-push` 流程另外要求本地 HEAD 是被审提交、工作区没有未提交的改动。生成的报告同样由主对话打开核对（R9），PR 里的复审摘要写明是外部复审、实际模型和局限。`external:` 开头的名字只能这样由 `external-review.mjs` 登记：手动运行 `review.mjs pass --reviewer external:<执行器>` 配手写报告会被拒绝；用户另开的新会话不用这类名字，登记名用 `general-purpose`。局限：这道限制只防走捷径，不防有意伪造（`register --run-dir` 只核对运行目录里几份文件互相对得上），外部复审是否真跑过，仍靠 PR 里公开的复审摘要和运行记录让人核对。外部复审者的放行也只经这条命令：已审满轮次上限、用户同意继续的，在 `register`（或 `run --register`）后加 `--user-decision "<用户的决定及出处>"` 重登 pass 或 fail；报告判不通过、用户已知情并决定接受其中问题的，用 `register --run-dir <运行目录> --accept --user-decision "<…>"` 登记 accept（`--accept` 只用于 `register`，`run` 不接受；只对判定为不通过的运行有效）；`review.mjs` 对 `external:` 名字仍一律拒绝。用户的决定只在这里登记，不写进给复审者的输入。

外部执行器不得带联网工具（网页抓取、联网搜索）：被审代码会经它们发给第三方。内置的 Codex 执行器已关闭联网搜索、子代理、记忆、钩子和外部应用，不给执行工具，只依据提示里的 diff 审：它的只读沙箱只挡写入、能读全盘，给了工具，被审内容里的提示注入就能让它去读本机的密钥。自己写的协议执行器要做到同样的限制。

## 2. 任务书

两份模板：首轮用“首轮任务书”，复审要求修改、修完之后用“修后复核任务书”。填好后原样交给复审者；只有按第 7 节交回的复审数据才能登记。

填任务书时不写自己的结论和猜测，只给意图、依据、范围和证据，避免复审者顺着作者的思路走。派发前由主对话把差异存成文件，放在会话的临时目录：首轮是 `git diff <主干>...HEAD` 的输出，修后复核是 `git diff <上一轮提交>..HEAD` 的输出；把路径和文件清单填进任务书，复审者不一定能自己运行 git。`{review.md 的绝对路径}` 填本文件在插件里的绝对路径（`<插件根>/skills/product-dev/references/review.md`，按入口“约定”换成实际路径），让复审者自己读维度、清单和报告格式。

### 首轮任务书

> 以本任务书为准：你的子代理定义里与它不同的做法这次都不用。不按置信度过滤，低级和既有问题也要报，并标明级别；范围是下面给的差异文件，不是未暂存的改动；按第 7 节交回复审数据（JSON），不用你自己的报告格式。
>
> 你是独立复审者，没有参与这次改动的编写。只读不改，不修代码，不重跑全量测试。
>
> 复审对象：`{仓库路径}`，分支 `{分支}`，对比基准 `{主干}`，最终提交 `{提交哈希}`（PR `{编号}`）。被审范围 `{分叉点的完整哈希}..{提交的完整哈希}`，照填进数据的 `reviewedBase`、`reviewedCommit`。
> 改动意图：`{一段话：要解决什么问题}`。依据：`{功能契约、计划或 bug 描述的路径}`。
> 审查种类：`{代码复审 | 一致性审}`。风险档位：`{低 | 中高}`。`{中高风险的代码复审写：安全专项由你按第 4 节一并做}`
> 改动范围：改动的文件清单是 `{文件清单}`，完整差异在 `{差异文件的路径}`。
> 验证证据：闸门输出 `{路径或摘录}`；CI `{链接和结果，还在跑的写“进行中”}`；变异检查 `{反转了哪个条件、哪条测试失败的输出}`。这些是共用的测试证据，不必重跑。你能运行命令时，需要的话只做针对性的复现（单个测试、单个场景）；不能运行的只核对这些证据，并在数据的“作者的验证”一节写明没有复现。
>
> 模型：`{实际派发的模型}`。用的是中档模型的，在数据里另写一节“局限”，单列你拿不准或超出本任务书范围的地方，不对它们下结论。
>
> 做法：先读 `{review.md 的绝对路径}`，按其中第 3 节的维度逐项审（中高风险加第 4 节的安全清单；一致性审改用第 5 节），按第 6 节分级，按第 7 节交回复审数据。先读依据，再读测试，最后读实现；不只看差异，改动函数的调用方、相关的校验和测试按需去读。每条发现先对照调用方、已有的保护和测试核实，被它们排除的不报。改动之前就存在的问题标“既有”。核对变异检查：反转的是不是关键条件，失败的是不是该失败的测试。没有发现就写没有，不为了凑数而报。高、中级问题尽量在这一轮一次报全，每条写明理由（为什么是这一级、影响多大）和建议改法；确实无法彻底解决的，`unresolvable` 写 true 并在建议改法里说明原因。风险档位是中高的，逐项检查测试缺口：功能是否都有测试、测试层级是否齐全、边界是否覆盖，写进数据的 `testGaps`，缺关键测试按中级报；拿不到证据的写 `insufficient`，不猜。
>
> 交回：按第 7 节的 `ek-review/1` JSON 放在你的回复里，不写文件：`sections` 写范围、作者的验证（节名以项目配置 `modules.review.reviewSections` 为准，“发现”就是 `findings`），`findings` 写发现，`verdict` 写结论。

### 修后复核任务书

> （首轮任务书开头“以本任务书为准”那一段照样放在这里。）
>
> 你在上一轮复审过 `{分支}` @ `{上一轮提交}`，上一轮的复审数据是 `{上一轮数据的路径}`。作者已针对意见集中修改，新的最终提交是 `{提交哈希}`（PR `{编号}`）。
> 修复差异：`{上一轮提交}..{提交哈希}` 的差异在 `{修复差异文件的路径}`，文件清单是 `{文件清单}`；数据的 `reviewedBase` 填上一轮提交的完整哈希，`reviewedCommit` 填新的最终提交。（派发前先看上一轮的登记输出：上一轮的登记不能作为覆盖接续的依据时，即部分覆盖（`partial`，例如只审了部分差异、或外部复审有没外发的文件），或 0.9.0 之前的旧版登记（记录里没有 `dataSha`、`coverageRule`），它接不上覆盖：这一轮仍用本任务书、照常逐条写处置，只把被审范围换成从分叉点到新的最终提交的完整差异，`reviewedBase` 填分叉点。`pre-push` 流程的登记不接续覆盖：给被审范围的修后复核一律审分叉点到新 HEAD 的完整差异，`reviewedBase` 填分叉点，处置照常逐条写。）
> 各条处置：`{逐条：编号、处置（已修 / 记进后续清单 / 用户决定不改）、改在哪里、补了哪条测试}`。
> 重点核对：`{要你特别看的风险，例如修复是否覆盖了同类路径、新增的分支有没有测试}`。
> 验证证据：`gate.mjs --affected` 的输出 `{路径或摘录}`；CI `{pr 流程填链接和结果，还在跑的写“进行中”；pre-push 流程填“推送前，无”}`。
>
> 做法：评审口径仍按 `{review.md 的绝对路径}` 的第 3 到第 7 节。只审修复差异和它直接影响的代码，不从头重审。上一轮的每条高、中级发现逐条写进 `dispositions`（`fixed`、`partial`、`not-fixed`，附证据：位置、测试名）；部分修复、未修的，另在 `findings` 里报一条，`prior` 写上一轮的编号。挑一两处修复做反转验证：能运行命令的，在临时副本里实际撤掉这处修复、跑相关测试并贴出失败输出；不能运行的，读代码说明撤掉后哪条测试的哪条断言会失败、为什么，并注明是读代码作答；两种都答不出来的，记为一条“缺回归测试”的发现。修复引入的新问题照第 6 节分级，`tag` 写“修复新增”；本轮才查出、但不是修复引入的，写“原先漏检”；上一轮问题再次出现的，`prior` 写上一轮哪条。风险档位是中高的，测试缺口检查照首轮做。拿不准的、或发现问题超出修复范围的，在数据里另写一节“局限”单列，不自己扩大范围。
>
> 交回：按第 7 节的 `ek-review/1` JSON 放在你的回复里，不写文件；上一轮高、中级的处置写在 `dispositions`，`sections` 的节名以项目配置的 `reviewSections` 为准。

修后复核沿用首轮的复审者：宿主能继续同一个子代理的（保留它的上下文），把这份任务书发给它；不能继续的，新派一个同档的复审者，把上一轮的复审数据一并交给它，并在汇报里写明。

## 3. 代码复审的五个维度

| 维度 | 要回答的问题 | 重点看 |
|---|---|---|
| 正确性 | 代码做的是不是它声称要做的 | 与契约或任务是否一致；空值、空集合、边界值；错误路径；差一、竞态、状态不一致；测试测的是不是该测的 |
| 可读性与简洁 | 别人不问作者能不能看懂 | 命名；控制流是否直白；能否用更少的代码做到；抽象是否值得它的复杂度；残留的无用代码；硬塞进无关流程的新条件分支；同一种判断反复出现 |
| 架构 | 改动是否合乎系统已有的设计 | 是否沿用现有模式；模块边界；重复代码；依赖方向；功能专属的逻辑有没有漏进公共模块；重构是减少了复杂度还是只挪了位置；类型边界是否明确 |
| 安全 | 是否引入了漏洞 | 输入校验；密钥是否进了代码、日志或版本库；鉴权；查询是否参数化；输出编码；新依赖的来源与已知漏洞；外部数据是否当作不可信处理 |
| 性能 | 是否引入了性能问题 | 循环里逐条查询；没有上限的循环或取数；该异步的同步操作；界面不必要的重复渲染；列表接口缺分页；热路径上的大对象 |

“这些测试能不能拦住回归”用实验回答，不靠读：作者在首次候选时已经做过变异检查（见 [process.md](process.md) 的“测试的四个阶段”），复审者核对这份证据：反转的是不是本次新增的关键条件，失败的是不是该失败的测试。证据缺失、或反转的条件无关紧要时，记为一条发现，写明应当反转哪个条件、缺哪个用例。

指出结构问题时同时给出改法，例如：把一串条件分支换成显式的分派；合并重复分支；把编排和业务逻辑分开；把功能专属的逻辑移回它所属的模块；复用已有的公共函数；把类型边界写明；删掉只做转发的包装；把过大的文件按职责拆开。优先选能让整条分支或整层消失的改法。

改动规模：约一百行易于审清；约三百行在只做一件事时可以接受；上千行应要求拆分（整文件删除和机械重构除外）。还要看文件本身：小改动把一个已经很大的文件继续撑大时，先问要不要拆。重构和新功能混在一个 PR 里，要求分开。

新增或升级依赖的改动另查：现有的栈是否已能解决；体积；是否有人维护；已知漏洞；许可是否相容。升级要读变更日志，一次只升一个包，锁文件的差异也要看，锁文件不手改。

## 4. 安全清单（中高风险）

先花几分钟站在攻击者一边：不可信数据从哪些地方进来（请求、表单、上传、回调、第三方接口、模型输出、别的进程写下的值），哪些东西值得偷或破坏，每个入口能否被冒充、篡改、抵赖、泄露、压垮、越权。然后逐项查与本次改动有关的部分：

| 方面 | 查什么 |
|---|---|
| 密钥 | 代码、日志、提交历史里没有密钥；真实的环境文件已被忽略；示例文件只有占位值 |
| 认证 | 口令用 bcrypt、scrypt 或 argon2 哈希；会话 cookie 设了 httpOnly、secure、sameSite 并有期限；登录接口限流；重置令牌有时限且只能用一次 |
| 授权 | 每个受保护的接口都检查身份；每次访问资源都检查归属或角色；管理接口校验管理员角色；令牌校验签名、期限、签发者 |
| 输入 | 在系统边界用允许清单校验（长度、范围、格式）；查询参数化；输出编码；上传限制类型和大小并校验内容；跳转地址先校验 |
| 服务端取数 | 用户能影响的网址先过允许清单，拒绝内网和保留地址，不跟随跳转 |
| 破坏性操作 | 删除、移动、覆盖的目标路径：先解析符号链接，确认在允许的根目录之下且不是根本身，并有归属证据 |
| 数据保护 | 敏感字段不出现在响应和日志里；对外通信走 HTTPS；个人数据有明确用途、保留期限和删除途径 |
| 响应与跨域 | 安全响应头齐全；跨域只放行明确的来源，带凭据时不用通配；错误信息不暴露内部细节 |
| 依赖 | 包管理器自带的审计没有未处理的、可达的高危项；新依赖看过来源、维护情况和安装脚本；不自动执行强制修复 |
| 模型输出 | 当作不可信输入：不进 `eval`、查询、命令行、页面结构或文件路径；提示词不是安全边界，权限在代码里做；密钥和别的租户的数据不进上下文 |

涉及新的认证流程、新类别的敏感数据、新的外部集成、跨域配置、上传、限流、权限提升的改动，本身就要先经用户同意，复审时核对有没有这个记录。

## 5. 一致性审的三个维度

只审增量：本次 PR（或本周期）新增和修改的文档、规则、注释。

| 维度 | 找什么 |
|---|---|
| 矛盾 | 两处对同一件事说法不同；文档与代码、配置、闸门的实际行为不符 |
| 重复 | 同一内容写在两处；应当引用的地方复述了一遍 |
| 过时 | 指向已改名或已删除的文件、章节、命令；描述的是旧行为 |

链接能否到达、版本号是否一致、状态值是否合法这类能用脚本查的，先用项目已有的检查脚本查，一致性审把精力放在脚本查不出的语义问题上。

## 6. 严重级别

| 级别 | 含义 | 作者要做的 |
|---|---|---|
| 高 | 安全漏洞、数据丢失或损坏、功能不可用、与已确认的需求或契约不符 | 合并前修完 |
| 中 | 会在真实使用中出错的缺陷、缺少关键测试、明显让结构变差的改动、影响体验或使用的问题 | 合并前修完 |
| 低 | 不影响正确性的改进：命名、小的简化、风格 | 默认记入后续清单，可否同批改见第 8 节 |
| 提示 | 供参考的信息 | 默认记入后续清单，可否同批改见第 8 节 |

先报影响大的：正确性和安全在前，结构问题其次，其余在后。一个结构问题加十条小毛病，重点是那个结构问题。能量化的量化，不把会上线出错的问题说成“可能有点小问题”；也不因为写法和自己习惯的不同就拦下一个确实让代码变好的改动。

## 7. 复审数据与登记

复审者交回的是一份结构化的复审数据（`ek-review/1` JSON），闸门只校验这份数据，不读 Markdown；给人看的报告由登记脚本从数据生成（`report.md`，与数据副本一起存在登记记录旁边）。0.9.0 起不再接受 Markdown 报告，传 Markdown 文件会被拒绝。

数据由主对话原样落盘：复审者把完整的 JSON 放在回复里（可以放在一个 json 代码块里），主对话把 JSON 原样存成文件，一个字不改、不增不删；回复里没有合法 JSON 或缺字段的，让复审者补全，不由主对话代写。文件放在会话的临时目录，不放进被审的仓库。

```json
{
  "format": "ek-review/1",
  "kind": "code",
  "verdict": "fail",
  "risk": "low",
  "reviewedCommit": "<最终提交的完整 40 位哈希>",
  "reviewedBase": "<被审范围的起点：首轮是与主干的分叉点，修后复核是上一轮被审的提交>",
  "sections": {
    "范围": "读了哪些文件（含 diff 之外的调用方和测试），哪些没读、为什么。",
    "作者的验证": "作者声称跑过的测试、构建、手工验证和变异检查，核对到了哪些，哪些没有证据。"
  },
  "findings": [
    {
      "id": "M1", "severity": "medium", "location": "src/dedup.ts:12", "files": ["src/dedup.ts"],
      "problem": "空数组时返回 undefined。", "trigger": "传入 [] 时。",
      "reason": "调用方直接取长度会抛错，主路径上就会遇到，所以是中级。",
      "fix": "空数组时返回 []，并补一条空数组的测试。",
      "tag": null, "prior": null, "unresolvable": false, "systemic": false
    }
  ],
  "dispositions": []
}
```

| 字段 | 写法 |
|---|---|
| `kind`、`verdict` | `code` 或 `consistency`；`pass` 或 `fail` |
| `risk` | 任务书里的风险档位：`low`（低）或 `high`（中高） |
| `reviewedCommit`、`reviewedBase` | 被审范围 `reviewedBase..reviewedCommit` 的两端，完整哈希；`pr` 流程必填，`pre-push` 流程可写 `null` |
| `sections` | `modules.review.reviewSections` 里除“发现”以外的各节（默认范围、作者的验证），每节有内容；可以多写别的节（如“局限”），同样要有内容。“发现”就是 `findings`；`reviewKeyword`（默认是“结论”）只决定生成报告里结论一节的标题 |
| `findings` | 七栏：编号 `id`、级别 `severity`（`high`、`medium`、`low`、`info`，即高、中、低、提示）、位置 `location`、问题 `problem`、触发条件或例子 `trigger`、理由 `reason`（为什么是这一级、影响多大）、建议改法 `fix`。编号用级别首字母加数字（H1、M2、L1、I1），同一份内不重复。可选：`files`（定位到的仓库内文件）、`tag`（`既有`、`修复新增`、`原先漏检`）、`prior`（与上一轮哪条是同一问题，即“重复出现”）、`unresolvable`（认为无法彻底解决）、`systemic`（认为是系统性问题）。没有发现写空数组 |
| `testGaps` | 中高风险必有：`functions`（功能是否都有测试）、`layers`（测试层级是否齐全）、`boundaries`（边界是否覆盖）三项，每项 `{ "status": "verified" \| "gap" \| "insufficient" \| "n/a", "note": "说明", "findings": ["M1"] }`；`gap` 要列出对应的高、中级发现编号，缺关键测试按中级报 |
| `unreviewedFiles`、`priorFailSha` | 一般不写，外部复审自动填：前者是改动里没有交给复审者的文件（例如不外发的密钥类文件），有它就只算部分覆盖；后者是修后复核所依据的上一份不通过数据的指纹，登记时要与登记历史里的上一份一致 |
| `dispositions` | 修后复核时对上一轮每条高、中级的处置：`{ "id": "H1", "status": "fixed" \| "partial" \| "not-fixed", "evidence": "位置、测试名" }`；首轮写空数组 |

登记脚本 `review.mjs` 的要求，不满足的逐条列出、全部拒绝，且不写任何记录：

- 复审者的登记名在允许名单内；`--report` 指向上面的 JSON 文件。
- 结构：只认上表的字段，类型和取值合格；单行字段（编号、位置、文件、节名）不换行；文本里没有控制字符、零宽和方向控制字符；字段不超过 4000 字，节不超过 20000 字，发现不超过 200 条，文件不超过 512 KiB。
- 有内容：去掉空白、不可见字符和 HTML 字符实体（如 `&nbsp;`）后至少有一个文字或数字，且不是“无、暂无、待补、待定、-、—、/、n/a、tbd、todo、none”这类占位词。所有级别的问题要有内容；高、中级的位置、问题、触发条件、理由、建议改法五栏都要有内容，外部复审者也一样。
- 结论与发现一致：`pass` 不能有高、中级发现，不能有部分修复或未修的处置，测试缺口不能有 `insufficient`；`fail` 至少有一条高级或中级。登记的结论要与数据的 `verdict` 相同（`accept` 要求数据是 `fail`）。只有低级和提示级发现时写 `pass`，它们进后续清单。
- `files` 里的每个文件要在被审提交或基准里存在。
- 中高风险：数据要有 `testGaps`；登记必须带 `--evidence-checked "<主对话核对了什么>"`。证据齐不齐脚本判断不了，由主对话对照功能、层级、边界核对后写明；外部复审的中高风险结果也不能在运行时直接登记（见第 1 节末“外部复审者”）。
- `pr` 流程另有四条：`reviewedCommit` 必须是登记时 PR 的最终提交（复审者审的是旧提交、PR 又推送了的，拒绝，按新提交重审）；被审范围要完整覆盖，`reviewedBase` 是与主干的分叉点，或是同一 PR、同一种审查此前一次完整覆盖的登记的被审提交，只审了部分差异的可以登记 `fail`，不能登记 `pass`、`accept`，合并入口也只认完整覆盖的记录；同一 PR 登记过中高风险的，之后的 `pass`、`accept` 也须是中高风险；同一种审查此前登记过 `fail` 的，`dispositions` 要逐条覆盖上一次的高、中级编号，部分修复、未修的每条都要有一条本轮高、中级发现用 `prior` 指向它。
- 存在高、中级问题时登记为 fail；修完后按第 8 节做修后复核，交新数据再登记。轮次上限、`--user-decision` 和 `accept` 怎样用，见第 8 节。

主对话存好数据后先核对（R9）：范围是否覆盖了改动、发现是否属实、结论与发现是否一致，然后才登记。登记命令按项目的复审流程，见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”一段：`pr` 流程两种审查各按 PR 登记；`pre-push` 流程登记代码复审，一致性审按分档另行登记（同一命令加 `--kind consistency`）或写明理由延期（`review.mjs defer --kind consistency --reason "<理由>"`），这两种记录推送核对都不要求；它们都写进历史，其中只有 fail 计入轮次（pass、defer、accept 不计），轮次的口径见第 8 节。把生成的报告摘要和后续清单贴进 PR：复审记录是本机约定，公开的摘要才是别人能核对的证据。

## 8. 一轮与修复循环

目的：让复审在两轮以内收敛，最多不超过三轮（轮次口径见下文“一轮怎样计”）。每轮都从头读全量、每修一条就重审一次，审查记录会不断过期，轮次和费用都失控。

### 一轮怎样计

一轮是登记过不通过的一份被审内容：`pr` 流程是 PR 的一个最终提交，`pre-push` 流程是登记时的一份工作区内容（不管提交没有）。所以并行双审在同一份内容上都不通过，这一次修复循环只算一轮；修复后在新内容上再不通过，才算下一轮。上限、满上限后怎样带 `--user-decision` 登记、在同一份内容上首次补登另一种审查为什么不拦，见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节第 4 条；满上限后用户同意继续的，这一轮的每次登记都带同一份用户决定。每份结论为不通过的复审数据都照实登记，不为省轮次而不登记。

### 轮次收口（可选配置）

项目在主干配置里把 `modules.review.roundClosure` 设为 `fix-and-record`（默认 `off`；只限 `pr` 流程，判定策略字段，合入主干后才生效）后，满轮次不再一律等用户决定，而是按一处算出的轮次状态（套件 `review-rounds.mjs`）分流。N 是 `maxReviewRounds`；登记、`close`、合并入口和外部复审都读同一份状态。

| 阶段 | 什么时候 | 怎么办 |
|---|---|---|
| 收齐前 | 最新不通过的那一轮还缺某种必需审查（一致性审延期也算登记） | 只能在该提交上补登缺的那种（延期也一样，别的提交上要用户决定）；阶段判定（加轮、停下、收口）等收齐后才做 |
| 停下 | 收齐的一轮里（两种审查的报告都算，通过的那份也算）有无法彻底解决的发现（`unresolvable`），或系统性问题：有高、中级发现用 `prior` 指向上一轮（同一问题再现）、有发现标 `systemic`、上一轮没有高级而本轮有、高级或中级数量比上一轮多 | 停下向用户汇报，建议单开对话专项处理；用户同意继续的带 `--user-decision` 登记 |
| 最后一轮 | 第 N 轮收齐，仍有高级 | 收齐之后第一条落在别的提交上的 pass 或 fail 登记，它所在的提交就是最后一轮（以登记先后为准，不看提交出现的先后；同一提交上两种审查都按最后一轮），登记不要 `--user-decision`，只认这一个提交。最后一轮的收齐、风险信号和收口证据只算第 N 轮收齐之后、这个提交上的登记（pass、fail、accept、一致性审延期都算）；收齐之前（经用户决定）在这个提交上的任何登记都不算，要按最后一轮重新登记；收齐之前在别的提交上的不通过也不占轮次。外部复审在启动执行器之前按同样的准入核对，不能登记的提交不启动。修后复核任务书在开头加一句“这是最后一轮复审，务必全面、彻底；中高风险逐条列清理由和彻底解决办法；确实无法彻底解决的，unresolvable 写 true 并说明原因”，外部复审自动带上 |
| 收口 | 第 N 轮（或最后一轮）收齐，只剩中、低级，且该轮每种审查都是完整覆盖（只审了部分差异的不能借收口放行，可在失败提交上补登一份完整覆盖的同种复审；按规则延期的一致性审不要求覆盖） | 不再加轮：修完全部中级 → `review.mjs risks --pr <编号> --shared-summary <kind>:<编号>="<可共享摘要>" [--fixed-in <kind>:<编号>=<路径>]` 按登记的发现生成风险登记 → 提交、推送、CI 全过 → `review.mjs close --pr <编号> --summary "<一句话>"` → 合并入口按收口放行 |
| 最后一轮仍有高级，或最后一轮之后又在别的提交上按规则登记了不通过 | — | 同“停下”。在最后一轮之外的提交上登记本身会被拒；经用户决定登记的是越权登记，不改变阶段（见下） |

风险登记是项目里的一份 JSON Lines 文件（`modules.review.riskRegister`，默认 `docs/04-开发/review-risks.jsonl`），会随 PR 提交推送，所以不写复审原文（本地复审者看得到不外发的内容）：每行一条中级问题，只有 PR、提交、轮次、审查种类、编号、级别、状态（固定“已修、未再复审”）、实际改在、原复审数据的指纹（`dataSha`）、这条发现的指纹（`findingSha`）和可共享摘要（`summary`）。摘要由主对话核对发现里哪些内容可以共享后用 `--shared-summary` 逐条写（不超过 300 字、不换行，也不含行分隔符等不可见字符），本机申报记下它的指纹，提交里改过的摘要不认；重跑 `risks` 没给的只从本机申报沿用同一条发现的摘要；其余字段由 `risks` 从登记生成，不手写，`close` 和合并入口按指纹核对；“实际改在”只认 `risks --fixed-in` 的申报：`risks` 在本机 git 公共目录（PR 的提交改不到）另存一份申报，提交里的条目与它不一致、或本机没有这份申报，都不能收口。原文留在本机 git 公共目录的复审数据副本里。0.10.0 生成的旧格式条目（逐字写了原文）不能作收口证据，同一条发现还留着旧格式行时不能收口；重跑 `risks` 会把同一条改写成新格式，其他旧格式行只提示行号、不改动，已推送过的 git 历史里的原文要按项目规则另行处理。“已修”的证据：发现定位到文件的，至少一个定位文件在修复差异（最新不通过的提交到最终提交，不算风险登记文件本身）里，或“实际改在”写的文件都在修复差异里；没定位到文件的，“实际改在”必须写、且都在修复差异里。两者都没有，`close` 拒绝并逐条列出原因。修复差异只放行白名单：本轮中级发现的定位文件、`--fixed-in` 申报的路径、测试文件（按失败提交上的 `testGlobs`）、文档（`reviewIgnore`）和风险登记；出现别的文件 `close` 拒绝并列出，这些改动没有经过复审，要么撤到另一个 PR，要么向用户说明、由用户决定后对最终提交做普通双审（登记带 `--user-decision`）。同一文件里夹带的无关改动机制查不出：`close` 成功时按文件列出修复差异的增删行数，主对话逐个核对。

收口之后又改了非文档文件，或风险登记在最终提交上不成立，合并入口不认收口，退回普通双审核对，两边原因都列出；此时阶段仍是收口，新提交上的登记要用户决定。越权登记（按上表不带 `--user-decision` 就会被拒、经用户决定才登记的，例如收齐前在别的提交上、停下之后继续的）在登记时标记（0.10.1 之前的记录没有这个标记，带用户决定的按当时已有的记录重放一次准入来判定）：它照常作为最新记录供合并入口核对，但轮次计算（收齐、最后一轮、超额、收口证据）一律不计它，只留作追溯；所以停下之后经用户同意继续的，之后每次登记仍要用户决定。收口关闭时，轮次行为与上面“一轮怎样计”一样。

### 收齐再改

1. 两份意见都收齐再动手，不收到一份改一份。
2. 主对话逐条核实、去重，把每条归入一类：

   | 类别 | 含义 | 怎么处理 |
   |---|---|---|
   | 原先漏检 | 本 PR 原有改动里的问题，作者、自查或上一轮复审没有发现 | 高、中级在本 PR 修；后几轮才查出的，下一轮的“重点核对”里写上同类风险 |
   | 修复新增 | 上一轮的修复引入的问题 | 高、中级在本 PR 修 |
   | 既有问题 | 本 PR 改动之前就存在 | 记进后续清单；直接影响本次改动正确性的，告诉用户，由用户决定是否在本 PR 修 |
   | 新增范围 | 超出本 PR 依据的新要求或改进 | 不在本 PR 做，见下面的“中途追加与主干变化” |

3. 有疑问的先补证：觉得某条不成立或看不懂的，先让同一位复审者给出复现步骤或具体位置，不直接返工，也不直接驳回。
4. 集中修一次：修根因和同类路径，同一根因第二次出现时按类别修（把同类的调用点一起找出来改），不逐项补；每条修复补一个回归测试；同步受影响的文档、契约和注释。修完按两种流程各自的次序走（闸门命令见 [process.md](process.md) 的“测试的四个阶段”里“修复后”一行）：
   - `pre-push`：修复 → 提交 → `gate.mjs --affected` → 修后复核 → 登记 → 全量 `gate.mjs` → 推送。推送钩子要求代码复审记录和全量测试记录都与推送的代码一致，所以复核和登记都在推送之前。
   - `pr`：修复 → 提交 → `gate.mjs --affected` → 推送 → 修后复核 → 登记（复审可以与 CI 并行开始；CI 全部通过后才登记、合并）。
5. 修后复核：用第 2 节的修后复核任务书，交给首轮的复审者。修复提交让哪份审查记录过期，哪份就要复核：`pr` 流程里任何新提交都会让两份记录过期，只有一个例外——代码复审之后只改了文档的提交，代码复审记录仍认（见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”里 `pr` 流程的合并入口一条），一致性审记录仍须针对最终提交。`pre-push` 流程下推送核对不要求一致性审记录，代码改了以后要不要复核一致性，按 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节的审查分档表定。复核范围都只是修复差异。

### 收敛检查（每轮复核结果出来后先做，再决定怎么修）

正常情况下复审是收敛的：上一轮发现的问题不会再出现；各轮的高、中级问题在严重程度和数量上都不增加（上一轮没有高级，这一轮就不该出现；这一轮的数量不多于上一轮）。出现下面任一情形，先停下来查，不一发现就修、修完再冒出来再修（那是治标不治本）：

1. 同一个问题（或同一类问题）再次出现；
2. 严重程度升高，例如上一轮没有高级、这一轮出现了；
3. 同级问题的数量比上一轮多。

怎么查：

- 先核实是不是真问题：让复审者给出复现步骤或具体位置，主对话自己复现；不一律接受，也不一律驳回。
- 再判断原因，不同原因处理不同：
  - 修复不彻底或同类路径漏改（同一规则在几处各写一份、改一处漏一处）：按类别修，把同类调用点一起找出来；能合成一处实现的合成一处，并补一个把各处判定对齐的一致性测试。
  - 测试断言没防住回归（断言形同虚设）：按“删掉被测逻辑、断言要失败”的方式做变异验证，不只看通过。
  - 复审口径变了（任务书范围、重点核对不同）：任务书统一，每轮都附上一轮的问题清单，让复审者在数据里逐条写处置（`dispositions`），发现用 `tag`、`prior` 标出修复新增、原先漏检、重复出现（与修后复核任务书一致）。
  - 确实是新引入或新发现的：按类别记录，下一轮任务书的“重点核对”写上同类风险。
- 拿不准是不是真问题、或判断不了原因的，向用户确认，不自行决定；目标是尽量不增加轮次：修之前先按类别扫一遍同类路径，每条修复的断言做过变异验证，再交复审。

### 低级和提示级问题的去处

- 记进后续清单：PR 描述里的“后续清单”一节，或登记后贴进 PR 的复审摘要评论；每项写编号、级别、位置、一句话问题和建议。默认不在本 PR 修，同批改的条件见下一条。不为它们单独再跑一轮复审。
- 修复提交只处理已登记的问题：高、中级必修；已登记的低级和提示级问题不扩大风险的，可以在同一次提交里同批改，并在处置说明里写明，修后复核一并核对；不夹带未登记的新改进。
- 合并后，后续清单列进汇报的“后续待办”，由用户决定什么时候做。“以后再清理”要落到这张清单上才算处理了。

### 争议

- 对复审意见有异议时，按事实和数据、项目规范、工程原则、与现有代码一致的顺序判断；仍不能一致的交用户决定，不自行忽略高、中级问题。
- 用户知情后决定不改的：复审数据照实先登记 fail（结论不通过的都要登记），用户作出决定后再用 `accept` 登记：数据的结论仍是不通过，`--user-decision` 写明用户的决定及出处，命令和放行方式见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”一段；PR 摘要里写明哪一条、为什么不改。不为它反复重审，也不改写数据的结论。

### 中途追加与主干变化

- 复审期间用户追加需求，或复审提出属于“新增范围”的建议：不并入当前 PR 的复审循环。先改契约（需要时经用户确认），另开分支和 PR；当前 PR 按原依据审完。
- 主干变了：先合入主干或变基，重跑闸门（基线变了，旧的测试和复审记录都会失效）。合入带来的差异没有碰到本 PR 改动的文件时，复审只对合入带来的差异做复核（用修后复核任务书，修复差异换成合入差异）；碰到了的，按首轮重审受影响的文件。

### 减少轮次的做法

目标与本节开头一致：两轮以内收敛，最多三轮。以下做法都是提高第一轮的覆盖率，或减少每轮要审的内容，不降低标准（R4）。做不到两轮时，说明原因，不为凑轮次压低审查。

1. **派发前清掉明显问题。** 作者先做推送前自查（[self-review.md](self-review.md)）和变异检查，低级错误不留给复审者。
2. **控制改动规模。** 约一百行容易审清，约三百行以上覆盖率明显下降。大改动拆成多个 PR，比在一个 PR 里反复修更快收敛。
3. **第一轮同时派发该派的审查。** 代码复审、一致性审，中高风险加安全专项，在同一最终提交上并行做，不分批。
4. **任务书写清全部维度和证据。** 把第 3 节的五个维度、闸门输出和变异检查结果写进任务书，减少复审者重复跑测试和漏看维度的可能。
5. **修后复核保持小范围。** 只审修复差异和直接受影响的代码，沿用同一位复审者，不从头再读。

低级和提示级问题按上面“低级和提示级问题的去处”办，不为它们再跑一轮。
