# 独立复审

交付段“独立复审”一步的方法：怎样派发首轮复审和修后复核、审什么、怎样分级、报告怎样写才能登记、不通过之后怎样收敛。作者自查不在这里，见 [self-review.md](self-review.md)。

## 1. 派发

复审者必须是独立上下文的子代理，不是写代码的主对话自己。登记时 `--reviewer` 填实际派发的子代理名，它要在项目配置 `modules.review.reviewers` 的名单内（按基准提交上的配置判定，功能分支里改名单要合入主干后才生效；套件 0.5.0 起的默认名单是 `product-dev:code-reviewer`、`feature-dev:code-reviewer`、`/code-review`、`general-purpose`；项目配置里写了名单的以项目的为准）。

| 复审者（登记名） | 用在哪里 | 注意 |
|---|---|---|
| `product-dev:code-reviewer` | 首选的代码复审，定义在插件的 [agents/code-reviewer.md](../../../agents/code-reviewer.md) | 套件 0.5.0 起新装的项目默认名单里已有它；用更早版本安装的项目没有，见下一段。它只有只读工具，不能写文件、不能运行命令 |
| `general-purpose` | 宿主的通用子代理：一致性审用它；首选不可用时代码复审也用它 | 必须带第 2 节的任务书；代码复审时把上面那份定义文件的正文一并交给它 |

`product-dev:code-reviewer` 不在名单里时（用 0.5.0 之前的套件安装的项目会这样：升级套件不改项目配置）：把它加进项目配置是改闸门的行为，先得到用户同意（R2），且名单要合入主干后才生效；没有同意就改派 `general-purpose` 并按实际登记，不借用名单里别的名字。

首轮怎样派：代码复审和一致性审针对同一个最终提交并行派发，各带一份第 2 节的首轮任务书。任务书只给核心上下文（依据、提交、差异文件、文件清单、验证证据），复审者需要时自己去读调用方和相关测试，主对话不把代码或本文的原文贴进任务书。复审可以与 CI 同时进行，结论在 CI 通过之后才登记（`pr` 流程的登记脚本在 CI 未全过时拒绝登记）。

安全专项（中高风险必做）：默认由同一位代码复审者带上第 4 节的安全清单一并做，任务书里写明，发现写进它的代码复审报告。只有改动很大（例如超过约三百行，或同时涉及认证、权限、外部集成中的两项以上）时，才另派一个只审安全的子代理：它出一份独立的报告，格式同第 7 节；它的结论不通过时，用这份报告登记代码复审的 fail，两份报告都通过才用代码复审报告登记 pass。

模型：按 R9 的分档，写在派发的调用参数里，不依赖子代理定义文件里偏弱的默认值；宿主不能指定模型时，在报告和汇报里写明实际用的模型。用中档模型的复审者，在报告里单列它拿不准或超出任务书范围的地方，主对话就这些地方改派更强一档重审，不把中档的结论当作这些地方已经审过。

子代理定义与任务书不一致时，以任务书为准，不改插件里的定义文件：`product-dev:code-reviewer` 的定义按置信度过滤、默认审未暂存的改动、用自己的报告格式，这几处由第 2 节两份任务书的开头一段改掉。

## 2. 任务书

两份模板：首轮用“首轮任务书”，复审要求修改、修完之后用“修后复核任务书”。填好后原样交给复审者；只有按第 7 节格式出的报告才能通过登记。

填任务书时不写自己的结论和猜测，只给意图、依据、范围和证据，避免复审者顺着作者的思路走。派发前由主对话把差异存成文件，放在会话的临时目录：首轮是 `git diff <主干>...HEAD` 的输出，修后复核是 `git diff <上一轮提交>..HEAD` 的输出；把路径和文件清单填进任务书，复审者不一定能自己运行 git。`{review.md 的绝对路径}` 填本文件在插件里的绝对路径（`<插件根>/skills/product-dev/references/review.md`，按入口“约定”换成实际路径），让复审者自己读维度、清单和报告格式。

### 首轮任务书

> 以本任务书为准：你的子代理定义里与它不同的做法这次都不用。不按置信度过滤，低级和既有问题也要报，并标明级别；范围是下面给的差异文件，不是未暂存的改动；按本任务书要求的四节格式出报告。
>
> 你是独立复审者，没有参与这次改动的编写。只读不改，不修代码，不重跑全量测试。
>
> 复审对象：`{仓库路径}`，分支 `{分支}`，对比基准 `{主干}`，最终提交 `{提交哈希}`（PR `{编号}`）。
> 改动意图：`{一段话：要解决什么问题}`。依据：`{功能契约、计划或 bug 描述的路径}`。
> 审查种类：`{代码复审 | 一致性审}`。风险档位：`{低 | 中高}`。`{中高风险的代码复审写：安全专项由你按第 4 节一并做}`
> 改动范围：改动的文件清单是 `{文件清单}`，完整差异在 `{差异文件的路径}`。
> 验证证据：闸门输出 `{路径或摘录}`；CI `{链接和结果，还在跑的写“进行中”}`；变异检查 `{反转了哪个条件、哪条测试失败的输出}`。这些是共用的测试证据，不必重跑。你能运行命令时，需要的话只做针对性的复现（单个测试、单个场景）；不能运行的只核对这些证据，并在报告的“作者的验证”一节写明没有复现。
>
> 模型：`{实际派发的模型}`。用的是中档模型的，在报告里单列你拿不准或超出本任务书范围的地方，不对它们下结论。
>
> 做法：先读 `{review.md 的绝对路径}`，按其中第 3 节的维度逐项审（中高风险加第 4 节的安全清单；一致性审改用第 5 节），按第 6 节分级，按第 7 节的格式出报告。先读依据，再读测试，最后读实现；不只看差异，改动函数的调用方、相关的校验和测试按需去读。每条发现先对照调用方、已有的保护和测试核实，被它们排除的不报。改动之前就存在的问题标“既有”。核对变异检查：反转的是不是关键条件，失败的是不是该失败的测试。没有发现就写没有，不为了凑数而报。
>
> 交回：完整报告放在你的回复里，不写文件。报告必须有“结论”一节，全文不少于 200 字。

### 修后复核任务书

> （首轮任务书开头“以本任务书为准”那一段照样放在这里。）
>
> 你在上一轮复审过 `{分支}` @ `{上一轮提交}`，报告是 `{上一轮报告的路径}`。作者已针对意见集中修改，新的最终提交是 `{提交哈希}`（PR `{编号}`）。
> 修复差异：`{上一轮提交}..{提交哈希}` 的差异在 `{修复差异文件的路径}`，文件清单是 `{文件清单}`。
> 各条处置：`{逐条：编号、处置（已修 / 记进后续清单 / 用户决定不改）、改在哪里、补了哪条测试}`。
> 重点核对：`{要你特别看的风险，例如修复是否覆盖了同类路径、新增的分支有没有测试}`。
> 验证证据：`gate.mjs --affected` 的输出 `{路径或摘录}`；CI `{pr 流程填链接和结果，还在跑的写“进行中”；pre-push 流程填“推送前，无”}`。
>
> 做法：评审口径仍按 `{review.md 的绝对路径}` 的第 3 到第 7 节。只审修复差异和它直接影响的代码，不从头重审。上一轮的每条高、中级发现逐条写“已关闭”或“未关闭”，附证据（位置、测试名）。挑一两处修复做反转验证：能运行命令的，在临时副本里实际撤掉这处修复、跑相关测试并贴出失败输出；不能运行的，读代码说明撤掉后哪条测试的哪条断言会失败、为什么，并注明是读代码作答；两种都答不出来的，记为一条“缺回归测试”的发现。修复引入的新问题照第 6 节分级，编号后标“修复新增”。拿不准的、或发现问题超出修复范围的，在报告里单列，不自己扩大范围。
>
> 交回：完整报告放在你的回复里，不写文件；格式同第 7 节，在“发现”之前加一节“上一轮发现的处置”（编号、上一轮级别、已关闭或未关闭、证据）。报告必须有“结论”一节，全文不少于 200 字。

修后复核沿用首轮的复审者：宿主能继续同一个子代理的（保留它的上下文），把这份任务书发给它；不能继续的，新派一个同档的复审者，把上一轮报告一并交给它，并在汇报里写明。

## 3. 代码复审的五个维度

| 维度 | 要回答的问题 | 重点看 |
|---|---|---|
| 正确性 | 代码做的是不是它声称要做的 | 与契约或任务是否一致；空值、空集合、边界值；错误路径；差一、竞态、状态不一致；测试测的是不是该测的 |
| 可读性与简洁 | 别人不问作者能不能看懂 | 命名；控制流是否直白；能否用更少的代码做到；抽象是否值得它的复杂度；残留的无用代码；硬塞进无关流程的新条件分支；同一种判断反复出现 |
| 架构 | 改动是否合乎系统已有的设计 | 是否沿用现有模式；模块边界；重复代码；依赖方向；功能专属的逻辑有没有漏进公共模块；重构是减少了复杂度还是只挪了位置；类型边界是否明确 |
| 安全 | 是否引入了漏洞 | 输入校验；密钥是否进了代码、日志或版本库；鉴权；查询是否参数化；输出编码；新依赖的来源与已知漏洞；外部数据是否当作不可信处理 |
| 性能 | 是否引入了性能问题 | 循环里逐条查询；没有上限的循环或取数；该异步的同步操作；界面不必要的重复渲染；列表接口缺分页；热路径上的大对象 |

“这些测试能不能拦住回归”用实验回答，不靠读：作者在首次候选时已经做过变异检查（见 [process.md](process.md) 的“测试的四个阶段”），复审者核对这份证据：反转的是不是本次新增的关键条件，失败的是不是该失败的测试。证据缺失、或反转的条件无关紧要时，记为一条发现，写明应当反转哪个条件、缺哪个用例。

指出结构问题时同时给出改法，例如：把一串条件分支换成显式的分派；合并重复分支；把编排和业务逻辑分开；把功能专属的逻辑移回它所属的模块；复用已有的公共函数；把类型边界写明；删掉只做转发的包装；把过大的文件按职责拆开。优先选能让整条分支或整层消失的改法。

改动规模：约一百行易于审清；约三百行在只做一件事时可以接受；上千行应要求拆分（整文件删除和机械重构除外）。还要看文件本身：小改动把一个已经很大的文件继续撑大时，先问要不要拆。重构和新功能混在一个 PR 里，要求分开。

新增或升级依赖的改动另查：现有的栈是否已能解决；体积；是否有人维护；已知漏洞；许可是否相容。升级要读变更日志，一次只升一个包，锁文件的差异也要看，锁文件不手改。

## 4. 安全清单（中高风险）

先花几分钟站在攻击者一边：不可信数据从哪些地方进来（请求、表单、上传、回调、第三方接口、模型输出、别的进程写下的值），哪些东西值得偷或破坏，每个入口能否被冒充、篡改、抵赖、泄露、压垮、越权。然后逐项查与本次改动有关的部分：

| 方面 | 查什么 |
|---|---|
| 密钥 | 代码、日志、提交历史里没有密钥；真实的环境文件已被忽略；示例文件只有占位值 |
| 认证 | 口令用 bcrypt、scrypt 或 argon2 哈希；会话 cookie 设了 httpOnly、secure、sameSite 并有期限；登录接口限流；重置令牌有时限且只能用一次 |
| 授权 | 每个受保护的接口都检查身份；每次访问资源都检查归属或角色；管理接口校验管理员角色；令牌校验签名、期限、签发者 |
| 输入 | 在系统边界用允许清单校验（长度、范围、格式）；查询参数化；输出编码；上传限制类型和大小并校验内容；跳转地址先校验 |
| 服务端取数 | 用户能影响的网址先过允许清单，拒绝内网和保留地址，不跟随跳转 |
| 破坏性操作 | 删除、移动、覆盖的目标路径：先解析符号链接，确认在允许的根目录之下且不是根本身，并有归属证据 |
| 数据保护 | 敏感字段不出现在响应和日志里；对外通信走 HTTPS；个人数据有明确用途、保留期限和删除途径 |
| 响应与跨域 | 安全响应头齐全；跨域只放行明确的来源，带凭据时不用通配；错误信息不暴露内部细节 |
| 依赖 | 包管理器自带的审计没有未处理的、可达的高危项；新依赖看过来源、维护情况和安装脚本；不自动执行强制修复 |
| 模型输出 | 当作不可信输入：不进 `eval`、查询、命令行、页面结构或文件路径；提示词不是安全边界，权限在代码里做；密钥和别的租户的数据不进上下文 |

涉及新的认证流程、新类别的敏感数据、新的外部集成、跨域配置、上传、限流、权限提升的改动，本身就要先经用户同意，复审时核对有没有这个记录。

## 5. 一致性审的三个维度

只审增量：本次 PR（或本周期）新增和修改的文档、规则、注释。

| 维度 | 找什么 |
|---|---|
| 矛盾 | 两处对同一件事说法不同；文档与代码、配置、闸门的实际行为不符 |
| 重复 | 同一内容写在两处；应当引用的地方复述了一遍 |
| 过时 | 指向已改名或已删除的文件、章节、命令；描述的是旧行为 |

链接能否到达、版本号是否一致、状态值是否合法这类能用脚本查的，先用项目已有的检查脚本查，一致性审把精力放在脚本查不出的语义问题上。

## 6. 严重级别

| 级别 | 含义 | 作者要做的 |
|---|---|---|
| 高 | 安全漏洞、数据丢失或损坏、功能不可用、与已确认的需求或契约不符 | 合并前修完 |
| 中 | 会在真实使用中出错的缺陷、缺少关键测试、明显让结构变差的改动、影响体验或使用的问题 | 合并前修完 |
| 低 | 不影响正确性的改进：命名、小的简化、风格 | 记进后续清单（第 8 节），不在本 PR 修 |
| 提示 | 供参考的信息 | 不在本 PR 处理，记进后续清单（第 8 节） |

先报影响大的：正确性和安全在前，结构问题其次，其余在后。一个结构问题加十条小毛病，重点是那个结构问题。能量化的量化，不把会上线出错的问题说成“可能有点小问题”；也不因为写法和自己习惯的不同就拦下一个确实让代码变好的改动。

## 7. 报告格式与登记

报告一律由主对话落盘：复审者把完整报告放在回复里，主对话原样存成报告文件，一个字不改、不增不删。宿主有时会拒绝子代理写报告文件，所以不再区分复审者能不能写文件。回复里没有完整报告的，让它补全，不由主对话代写。报告文件放在会话的临时目录里，不放进被审的仓库（它不属于被审代码，放进去还会改变代码树）。必须有下面四节：

```markdown
# 复审报告：<PR 或改动的标题>

审查种类：代码复审（或 一致性审）　复审者：<登记名>　模型：<实际使用的模型>
对象：<分支> @ <最终提交哈希>，基准 <主干>

## 范围
读了哪些文件（含 diff 之外的调用方和测试），哪些没读、为什么。

## 发现
| 编号 | 级别 | 位置 | 问题 | 触发条件或例子 | 建议改法 |
|---|---|---|---|---|---|
（没有发现时写“无”。已存在的问题在编号后标“既有”，修复引入的标“修复新增”。）

## 作者的验证
作者声称跑过的测试、构建、手工验证和变异检查，复审者核对到了哪些，哪些没有证据。

## 结论
不通过。一句话理由；高、中级问题的编号清单：H1、M2。
```

结论一节在“通过。一句话理由”和“不通过。一句话理由；高、中级问题的编号清单”两种写法中二选一，上面示例的是不通过。只有低级和提示级发现时写通过，它们进后续清单。

登记脚本 `review.mjs` 的要求，报告要同时满足：

- 复审者的登记名在允许名单内。
- 报告不少于 `modules.review.reviewMinChars` 个字（默认 200）。
- 报告里有一处明确的结论，关键词是 `reviewKeyword`（默认是“结论”）。两种写法都认：同一行写“结论：通过。理由”或“结论：不通过。理由”（行首可以有井号、引用符，词两边可以加星号）；或者像上面的模板，单独一行“## 结论”，其后第一个非空行写“通过。理由”或“不通过。理由”。两种写法按同一条规则判定：按逗号、分号、句号、冒号拆成小句，整句恰好是结论词的小句才算（“不通过：H1 未修复”认得出）；结论词后不要加括号，“通过（待 M2 修复后）”“通过（或 不通过）”都认不出结论，登记会被拒；结论词只认中文的“通过”“不通过”“未通过”（“未通过”等同“不通过”），“通过前需修复 H1”“通过与否取决于……”都不算结论。
- 登记 pass 要求结论是通过，登记 fail 要求结论是不通过；找不到明确结论、有多处结论且不一致、或与登记不符时拒绝登记。所以结论只写一处；引用旧结论时换个说法，不要另起一行“结论：……”。
- 存在高、中级问题时结论写不通过，登记为 fail；修完后按第 8 节做修后复核，出新报告再登记。轮次上限、`--user-decision` 和 `accept` 怎样用，见第 8 节。

主对话存好报告后先打开核对（R9）：范围是否覆盖了改动、发现是否属实、结论与发现是否一致，然后才登记。登记命令按项目的复审流程，见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”一段：`pr` 流程两种审查各按 PR 登记；`pre-push` 流程登记代码复审，一致性审按分档另行登记（同一命令加 `--kind consistency`）或写明理由延期（`review.mjs defer --kind consistency --reason "<理由>"`），这两种记录推送核对都不要求；它们都写进历史，其中只有 fail 计入轮次（pass、defer、accept 不计），轮次的口径见第 8 节。把报告摘要和后续清单贴进 PR：复审记录是本机约定，公开的摘要才是别人能核对的证据。

## 8. 一轮与修复循环

目的：让复审在两三轮内收敛。每轮都从头读全量、每修一条就重审一次，审查记录会不断过期，轮次和费用都失控。

### 一轮怎样计

一轮是登记过不通过的一份被审内容：`pr` 流程是 PR 的一个最终提交，`pre-push` 流程是登记时的一份工作区内容（不管提交没有）。所以并行双审在同一份内容上都不通过，这一次修复循环只算一轮；修复后在新内容上再不通过，才算下一轮。上限、满上限后怎样带 `--user-decision` 登记、在同一份内容上首次补登另一种审查为什么不拦，见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节第 4 条；满上限后用户同意继续的，这一轮的每次登记都带同一份用户决定。每份结论为不通过的报告都照实登记，不为省轮次而不登记。

### 收齐再改

1. 两份意见都收齐再动手，不收到一份改一份。
2. 主对话逐条核实、去重，把每条归入一类：

   | 类别 | 含义 | 怎么处理 |
   |---|---|---|
   | 原先漏检 | 本 PR 原有改动里的问题，作者、自查或上一轮复审没有发现 | 高、中级在本 PR 修；后几轮才查出的，下一轮的“重点核对”里写上同类风险 |
   | 修复新增 | 上一轮的修复引入的问题 | 高、中级在本 PR 修 |
   | 既有问题 | 本 PR 改动之前就存在 | 记进后续清单；直接影响本次改动正确性的，告诉用户，由用户决定是否在本 PR 修 |
   | 新增范围 | 超出本 PR 依据的新要求或改进 | 不在本 PR 做，见下面的“中途追加与主干变化” |

3. 有疑问的先补证：觉得某条不成立或看不懂的，先让同一位复审者给出复现步骤或具体位置，不直接返工，也不直接驳回。
4. 集中修一次：修根因和同类路径，同一根因第二次出现时按类别修（把同类的调用点一起找出来改），不逐项补；每条修复补一个回归测试；同步受影响的文档、契约和注释。修完按两种流程各自的次序走（闸门命令见 [process.md](process.md) 的“测试的四个阶段”里“修复后”一行）：
   - `pre-push`：修复 → 提交 → `gate.mjs --affected` → 修后复核 → 登记 → 全量 `gate.mjs` → 推送。推送钩子要求代码复审记录和全量测试记录都与推送的代码一致，所以复核和登记都在推送之前。
   - `pr`：修复 → 提交 → `gate.mjs --affected` → 推送 → 修后复核（可以与 CI 同时进行）→ CI 通过后登记。
5. 修后复核：用第 2 节的修后复核任务书，交给首轮的复审者。修复提交让哪份审查记录过期，哪份就要复核：`pr` 流程里任何新提交都会让两份记录过期，只有一个例外——代码复审之后只改了文档的提交，代码复审记录仍认（见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”里 `pr` 流程的合并入口一条），一致性审记录仍须针对最终提交。`pre-push` 流程下推送核对不要求一致性审记录，代码改了以后要不要复核一致性，按 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节的审查分档表定。复核范围都只是修复差异。

### 低级和提示级问题的去处

- 记进后续清单：PR 描述里的“后续清单”一节，或登记后贴进 PR 的复审摘要评论；每项写编号、级别、位置、一句话问题和建议。不在本 PR 修，不为它们再跑一轮复审。
- 修复提交只处理已登记的高、中级问题；已登记的低级问题可以在同一次提交里顺手改，并在处置说明里写明，修后复核一并核对；不夹带未登记的新改进。
- 合并后，后续清单列进汇报的“后续待办”，由用户决定什么时候做。“以后再清理”要落到这张清单上才算处理了。

### 争议

- 对复审意见有异议时，按事实和数据、项目规范、工程原则、与现有代码一致的顺序判断；仍不能一致的交用户决定，不自行忽略高、中级问题。
- 用户知情后决定不改的：报告照实先登记 fail（结论不通过的报告都要登记），用户作出决定后再用 `accept` 登记：报告结论仍是不通过，`--user-decision` 写明用户的决定及出处，命令和放行方式见 [套件流程文档](../../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”一段；PR 摘要里写明哪一条、为什么不改。不为它反复重审，也不改写报告的结论。

### 中途追加与主干变化

- 复审期间用户追加需求，或复审提出属于“新增范围”的建议：不并入当前 PR 的复审循环。先改契约（需要时经用户确认），另开分支和 PR；当前 PR 按原依据审完。
- 主干变了：先合入主干或变基，重跑闸门（基线变了，旧的测试和复审记录都会失效）。合入带来的差异没有碰到本 PR 改动的文件时，复审只对合入带来的差异做复核（用修后复核任务书，修复差异换成合入差异）；碰到了的，按首轮重审受影响的文件。
