# product-dev：产品开发入口

用户只说想法，你判断情况、选路线、逐步推进。贯穿全程的规则只有一个出处：[工程流程规则块](../engineering-kit/kit/rules/AGENTS.block.md)的 R1–R10（装了工程套件的项目里，它在项目的 AGENTS.md 中）。本文只引用编号；本文与规则块、项目自己的规则或闸门不一致时按 R1。

## 约定

- **插件根**：`${CLAUDE_PLUGIN_ROOT}`。Claude Code 加载本技能时把它替换成绝对路径（它不是 Bash 里的环境变量，命令里要写替换后的路径）；看到的仍是这串字面量时，插件根就是本文件所在目录的上两级。Codex 是否做同样的替换未核实，按后一种办法处理。下文命令里的 `<插件根>` 都指它，`<项目>` 指目标项目的根目录。
- **内部技能**在 `<插件根>/skills/` 下。Claude Code 用技能工具按 `product-dev:<技能名>` 加载。Codex 只注册入口技能，内部技能按下文链接读取。宿主没有技能工具或找不到技能时，直接读它的 `SKILL.md` 并照做。
- **子代理**在 `<插件根>/agents/` 下，派发名是 `product-dev:<子代理名>`。派发时显式指定模型，不用子代理文件里的默认值：探索类用中档模型，方案设计用不弱于主对话的模型，测试设计和各种复审按 R9 的分档。宿主不支持插件子代理时（Codex 一侧未核实），把对应 `.md` 文件的正文作为任务书交给宿主的通用子代理，并在汇报里写明。设计角色（需求、原型、架构）不是这里的子代理：它们用什么模型、主对话什么时候可以兼任，只写在[设计总控](../product-design-orchestrator/SKILL.md)第 1 节，以那里为准。
- **工程套件的脚本**装进项目后在 `<项目>/scripts/engineering/gate/` 下，模板在 `<项目>/docs/_templates/` 下；它们的来源是 [engineering-kit](../engineering-kit/SKILL.md) 的 `kit/`。项目没装套件时见第 0 步。
- **方法文档**按需读取，不要一次全读：

| 文件 | 什么时候读 |
|---|---|
| [process.md](references/process.md) | 入口步骤到套件流程文档各节的对照、配置闸门的字段、测试的四个阶段 |
| [planning.md](references/planning.md) | 任务拆解 |
| [build.md](references/build.md) | 测试设计、逐片开发、最小修复 |
| [self-review.md](references/self-review.md) | 推送前自查 |
| [review.md](references/review.md) | 派发首轮复审与修后复核、安全清单、修复循环、登记复审结论 |
| [debugging.md](references/debugging.md) | 修 bug，或开发中遇到意外的失败 |

每一步固定四栏：目标、原则、工具（写明怎样调用）、过关证据。过关证据没拿到就不进下一步；某个工具用不了时见“工具缺失与宿主差异”。

## 0. 恢复现场

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 恢复现场 | 确认目标项目和已有成果，从实际缺口续做 | 核对实际文件、版本和确认记录，不沿用上一次的结论（R5）；启动技能时所在的仓库不一定是目标项目 | 只读命令 `git status`、`git log`、`git worktree list`、`gh pr list`；读项目的 AGENTS.md、`engineering.config.json`、`docs/00-总览/PROJECT_STATE.md`；已装套件的再跑 `node "<插件根>/skills/engineering-kit/kit/sync.mjs" --target "<项目>" --check`（只读的漂移检查） | 能说出：目标目录、当前分支、未合并的工作、设计与开发做到哪一步、套件是否已装及版本 |

这一步全部是只读操作，不需要批准。目标目录还不是 git 仓库或没有远程仓库时，`git log`、`gh pr list`、`git fetch` 这些跑不出结果的命令如实记成“不是仓库”或“没有远程”，不算这一步没过（第 3 节的“开工检查”里，没有远程的同样处理，以本地主干为准）；`PROJECT_STATE.md` 不存在时按还没有设计成果处理。套件是否已装，看项目里有没有 `scripts/engineering/kit.lock.json`：

- 新项目没装：安装是新项目路线的第一步（见第 2 节“装工程底座”的授权说明）。
- 已有项目没装：不自动装。按项目自己的规则和闸门走下面的路线，文中套件的闸门命令换成项目对应的检查；可以建议安装，由用户决定（R2）。已使用自有闸门的项目不覆盖。
- 已装但版本落后或漂移检查不一致：告诉用户，建议走“装或升级工程套件”，不擅自升级。

## 1. 分流

| 情况 | 判断条件 | 路线 |
|---|---|---|
| 新项目 | 还没有代码：目录是空的，或只有说明和设计文档 | 第 2 节（装工程底座 → 设计段 → 配置闸门）→ 第 4 节 |
| 加功能 | 已有项目里新增或改变一项能力，且不满足下一行“小新增”的条件；跨模块、新接口、数据库结构、权限、费用、服务器配置一律算这一档 | 第 3 节 → 第 4 节 |
| 小新增 | 已有项目里新增一项低风险的小能力：单模块、不改接口和数据结构、需求明确。在已有模块里新增内部或导出的函数、而现有调用方式和行为不变，不算新接口；给已有函数加向后兼容的可选参数、新增带默认值且不改变默认行为的配置项，也不算新接口，改变默认行为的算；新增对外的 HTTP 或 RPC 接口、命令行命令、跨模块的新依赖方向、数据库结构，算新接口，按加功能。PRD（或已确认的需求）里没有对应需求的不算“需求明确”：先经设计总控修订需求，修订后再按小新增或加功能分流 | 第 6 节 |
| 修 bug | 行为与已确认的需求、契约或文档不符 | 第 5 节 |
| 小改动 | 低风险、单模块、需求明确，不改接口和数据结构 | 第 6 节 |
| 只改文档 | 全部文件都在项目配置 `rules.reviewIgnore` 之内，且不改变 agent 或产品的行为 | 第 6 节 |
| 装或升级工程套件 | 用户要求安装、检查、升级或回滚，或第 0 步的漂移检查发现不一致 | 第 7 节 |

- 拿不准属于哪一档，按高一档处理（上表前六行越靠上档位越高；拿不准是小新增还是加功能的，按加功能）。修 bug 与小新增之间不比高低：拿不准是 bug 还是新能力时，先按修 bug 的前两步复现和定位，再用“是需求缺口?”一步判断。已有代码但产品方向要重新定的，按“加功能”走并先回设计段，不按新项目重装套件。
- **先说判断，再按 R2 动手。** 用一句话告诉用户判断结果和依据。判断本身不必等确认；能不能马上动手看用户的话：
  - 可以直接做：只读的事（读代码、查记录、不改文件也不切换检出的复现、漂移检查、`--dry-run`）任何时候都可以；用户的话是明确的要求（“把它修掉”“加上这个功能”“做一个……”）时，说完判断就按路线开始，用户纠正就换路线。
  - 先得到批准：用户的话只是描述或问句（“这里好像报错了”“能不能支持……”）时，只做只读的事，说明判断和打算怎么做，得到批准后才改文件、提交或安装。已授权按推荐执行也一样：那份授权只管已获批准的任务之内的待决事项，新提出的描述或问句不因它变成要求。
  - 始终单独授权的事项和有费用的外部动作，按 R2 的清单办，不因路线已开始而省略。
- 需求探索的问题不在分流时列成一张清单，用户的话是不是明确要求都一样：说完判断后最多带上第一个主题的问题（通常是要解决谁的什么问题），其余由需求角色按 R3 一轮问一个主题；加功能路线上关于边界、错误处理和兼容性的问题不在此列，仍按第 3 节“澄清问题”集中一次问完。等批准的那一轮，另外只问能不能开始和眼下必须由用户定的事。
- 对设计产物（PRD、原型、架构）的反馈和修订先交设计总控，不直接套上表的开发路线：加载 `product-dev:product-design-orchestrator`，按它的第 3 节把一句话里的几件事分开，补全某个角色自己的细节（例如一句提示的文案、列表默认的排序）由负责角色直接改并留记录，新增或改变产品能力（例如多一种导出格式）经总控送需求角色提出修订建议，改 PRD 之前取得用户同意（已授权按推荐执行的按 R2 记录后继续）。前一类不因为和后一类出现在同一句话里就一起升档；用户只要求动其中一份产物时只动那一份，对其他产物的影响列出来交用户决定；项目已有代码、后一类要落到实现时，设计修订完再接第 3 节。
- 动手改文件之前都先做第 3 节的“开工检查”（新项目在装好工程底座并做完首次提交之后做），修 bug、小改动、只改文档也一样。修 bug 时加临时日志、人为加延迟、`git bisect`、写失败测试都算动手。
- 一句话里有几件事时分别判断，各走各的路线，各开各的分支。只要求其中一段（只做设计、只复审、只发布）时，从对应步骤进入，做完该段即止。用户指定了做到哪一步为止的，做到那一步就停，后面的步骤在汇报里逐项写未执行。
- 只读的问题（解释代码、调研、评估方案）直接回答，不走路线、不开分支。线上应急（回滚、数据恢复）按 R2 单独授权，处置后转修 bug 路线。

## 2. 新项目：设计段

设计段的第一步就是第 0 步的恢复现场。从“需求 PRD”到“综合评审”由设计总控编排：加载内部技能 `product-dev:product-design-orchestrator`（[SKILL.md](../product-design-orchestrator/SKILL.md)），由它按阶段启动三个设计角色；不绕过总控直接加载角色技能（主对话兼任某个角色的条件见总控第 1 节）。

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 装工程底座 | 装好规则、钩子、阶段目录和文档模板，设计文档从第一天就落在规定位置 | 能用脚本强制的不靠自觉 | 先看计划 `node "<插件根>/skills/engineering-kit/kit/sync.mjs" --target "<项目>" --init --dry-run`，再去掉 `--dry-run` 执行（技术栈未定时不加 `--profile`）；装好后用 `git add -A`、`git commit` 把生成的文件做成首次提交；说明见 [engineering-kit](../engineering-kit/SKILL.md) 第 1 节 | 同步成功的输出；`scripts/engineering/kit.lock.json` 存在；首次提交已做 |
| 需求 PRD | 得到用户确认的 PRD 版本，每项需求有 ID 和验收标准 | 从问题出发；分清事实、分析和假设；把“方便、及时”改写成可检验的条件 | 经设计总控启动需求角色 [product-discovery-prd](../product-discovery-prd/SKILL.md) | `docs/01-需求/` 下的 PRD，用户确认了具体版本（或 R2 的授权记录） |
| 原型与 UI | 产出信息架构、核心路径和可操作原型 | 按用户任务组织页面；模拟数据和占位功能逐处标明 | 经设计总控启动原型角色 [prototype-design](../prototype-design/SKILL.md)；界面的视觉与实现加载内部技能 `product-dev:impeccable`（[SKILL.md](../impeccable/SKILL.md)） | `docs/02-原型/` 下的原型说明和能打开操作的原型 |
| 实际走查 | 留下走查证据，取得用户认可的体验基线 | 实际运行过才算验证；发现缺需求就退回需求角色，不自行改体验 | 用宿主的浏览器工具把原型实际操作一遍；再用 [impeccable](../impeccable/SKILL.md) 的 `critique` 和 `audit` 两个命令评审 | 走查记录（走了哪些路径、结果、截图或输出）；用户确认体验基线 |
| 架构设计 | 给出两张核心图、关键机制和 ADR | 先提最简单的可行方案；把精力放在错了难改的决定上 | 经设计总控启动架构角色 [system-architecture-design](../system-architecture-design/SKILL.md)；画图加载内部技能 `product-dev:archify`（[SKILL.md](../archify/SKILL.md)） | `docs/03-架构/` 下的架构文档与两张图；`docs/adr/` 下的 ADR |
| 综合评审 | 判定实施准备度，交出实施计划和追踪矩阵 | 文档齐全不等于可以实施；每项需求都能追到原型、组件、任务和测试 | 设计总控第 4 节，加[共享协议](../product-design-orchestrator/references/shared-protocol.md)和[产物模板的实施准备度](../product-design-orchestrator/references/artifacts.md#implementation) | 准备度结论 `READY`、`READY_WITH_LIMITATIONS` 或 `BLOCKED`；`docs/00-总览/` 下的实施交接与追踪矩阵 |
| 配置闸门 | 按选定的技术栈填好测试命令和源码、测试文件的匹配规则 | 配置不准，闸门就不准；配完先跑一次，确认它拦得住问题；以规则、技能正文、提示词为主的项目，默认的 `reviewIgnore` 会让它们免审，要收窄 | 改项目的 `engineering.config.json`（要填的字段见 [process.md](references/process.md) 的“配置闸门”）；试跑 `node scripts/engineering/gate/gate.mjs` | 两次闸门输出：故意放一个会失败的检查时被拦下，恢复后通过 |

- **装工程底座的授权（R2）**：安装会初始化 git 仓库、写入 AGENTS.md、钩子和 `.claude/settings.json`。用户已明确要求做这个项目时，在判断结果里说明“第一步在哪个目录安装工程套件并做首次提交”后直接装；用户只是在描述想法或提问时，先得到批准再装，已授权按推荐执行也不例外。目标目录不在当前项目根之内、需要新建时，按 R6 先经用户批准。`--dry-run` 不改任何文件，可以直接跑。
- `docs/00-总览/` 下的 `PROJECT_STATE.md` 和 `RECORDS.md` 不由套件生成：第一份设计产物落盘时，由主对话按[产物模板](../product-design-orchestrator/references/artifacts.md)第 1 节建立，并登记到该目录的 README。
- 准备度为 `READY` 才进第 4 节；`READY_WITH_LIMITATIONS` 只做已放行的范围；`BLOCKED` 停下，把阻塞项交给用户。
- 用户没有授权工程实现时，综合评审交接后就停。授权了的，第 4 节的任务拆解以实施交接里的实施顺序为输入。

## 3. 加功能：开发之前

低风险的小新增不走本节，见第 6 节；本节是中高风险加功能的完整路线。

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 开工检查 | 从最新主干开分支，确认没有遗留的未提交改动 | 续做前核对提交记录和开着的 PR（R7） | `git fetch`、`git status`、`git worktree list`、`gh pr list`；`node scripts/engineering/gate/hygiene.mjs` 报告残留的分支和工作树；步骤见 [套件流程文档](../engineering-kit/references/process.md) 第 1 节 | 新分支从最新主干开出，工作区干净；遗留工作已说明去向 |
| 探索代码库 | 找出相似功能、相关模块和必读文件清单 | 先读懂再动手；子代理只给线索，主对话亲自读关键文件（R9） | 并行派发 2 到 3 个子代理 `product-dev:code-explorer`（[定义](../../agents/code-explorer.md)），各查一个方面，任务书要求交回文件清单和调用链 | 必读文件清单，且主对话都已读过 |
| 澄清问题 | 边界情况、错误处理、兼容性都有明确答案 | 问题集中一次问完，推荐项放第一（R3）；不带着猜测往下走 | 宿主的提问工具，问法见 [套件流程文档](../engineering-kit/references/process.md) 第 2 节 | 问题清单逐项有答案，或有“按授权采用推荐”的记录 |
| 改产品行为? | 判断这次改动要不要先改 PRD 和原型 | 产品行为由需求角色决定，开发不因实现方便改体验 | 对照 `docs/01-需求/` 与 `docs/02-原型/`；要改时加载 `product-dev:product-design-orchestrator`（[SKILL.md](../product-design-orchestrator/SKILL.md)），只修订受影响的部分再回来 | 结论及依据；需要时有修订后的设计版本 |
| 功能契约 | 写清“怎样证明做对了”，取得用户确认 | 验收标准不得擅自弱化；自行确定的口径单列待确认；契约里的预期和“预期行为与异常边界”场景表交用户集中确认一次，之后的小修复沿用这份契约，需求变了才重新确认 | 复制 `docs/_templates/feature-contract.md` 到 `docs/04-开发/` 填写（[模板原件](../engineering-kit/kit/templates/docs/templates/feature-contract.md)），场景表的写法见 [套件流程文档](../engineering-kit/references/process.md) 第 2 节 | 用户确认的契约，含场景表（或 R2 的授权记录） |
| 方案对比 | 比较最小改动、结构清晰、折中三种做法并给出推荐 | 建议不写成决定；说明复杂度、风险和能否回退 | 按三种做法各派一次子代理 `product-dev:code-architect`（[定义](../../agents/code-architect.md)；它的定义要求只给一个方案），每份任务书写明这次取哪种取向；主对话把三份蓝图汇成对比表。改动很小（只动一两个函数、三种取向的差别一眼可见）时可以不派，由主对话自己按三种取向比较，并在汇报里写明没有派发及理由 | 对比表和推荐理由 |
| 用户选定方案 | 得到明确批准再进入交付段 | 问句不算授权（R2） | 决定写进 `docs/00-总览/RECORDS.md`（格式见[共享协议](../product-design-orchestrator/references/shared-protocol.md)）；错了难改的决定另写 ADR（`docs/_templates/adr.md`，[模板原件](../engineering-kit/kit/templates/docs/templates/adr.md)） | 用户的选择，或“按授权采用推荐”的记录 |

“改产品行为?”为“是”时先回设计段修订，再写契约。子代理的报告只当线索，主对话打开产物核对（R9）。项目的源文件和测试文件加起来不超过十个、主对话已经逐个读完时，“探索代码库”可以不派发子代理，过关证据不变，并在汇报里列出读过的文件。

## 4. 交付段

新项目和加功能共用；修 bug 和缩短路线用它的后半。下表按 `pr` 复审流程的次序写；项目配置为 `pre-push`（默认）时，独立复审排在机械闸门之后、推送之前，两种流程的命令见 [套件流程文档](../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”一段。

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 任务拆解 | 拆成纵向切片，每片有验收条件和验证方法 | 每片能独立验证、独立回退；高风险实验排在最前 | 按 [planning.md](references/planning.md) 拆；计划用 `docs/_templates/plan.md` 写在 `docs/04-开发/`（[模板原件](../engineering-kit/kit/templates/docs/templates/plan.md)）；新项目（没有功能契约）的场景表在这一步补出，来源见 [build.md](references/build.md) 第 4 节 | 计划文件；中高风险的经用户看过；新项目的场景表经用户确认 |
| 测试设计 | 依据场景表先写出测试，预期不从实现倒推 | 由不写实现的独立子代理按场景表写测试，做法见 [build.md](references/build.md) 第 4 节 | 按 [build.md](references/build.md) 的“测试设计”派发宿主的通用子代理，依据和任务书内容照那里写，不给实现代码 | 每条测试对应到场景表的哪一行；每片开工时那一片的测试在实现之前运行的输出：新增或改变行为的测试失败，已满足的行测试通过，逐条标明 |
| 逐片开发 | 每片先写测试、再实现、通过后提交 | 测试先行；用最少的新代码解决整个问题；只动任务范围内的文件 | 按 [build.md](references/build.md) 逐片做；测试先行由闸门里的 `scripts/engineering/gate/check-test-first.mjs` 检查 | 每片一个提交，相关测试通过 |
| 推送前自查 | 作者一侧的问题清零 | 自查不算独立复审（R7）；不靠屏蔽检查或跳过测试变绿（R4） | 按 [self-review.md](references/self-review.md) 的清单逐项过 | 自查发现的问题已修，或写明不修的理由 |
| 机械闸门 | 静态检查、测试记录都与当前代码一致 | 标准只有达标与未达标；闸门失败就修代码，不改阈值（R4） | 首次候选 `node scripts/engineering/gate/gate.mjs`，修复后 `node scripts/engineering/gate/gate.mjs --affected`；各阶段跑什么见 [process.md](references/process.md) 的“测试的四个阶段” | 闸门输出通过；首次候选另有变异检查的输出（反转了哪个条件、哪条测试失败） |
| PR 与 CI | PR 最终提交上的必需检查全部通过 | 命令返回 0 不等于业务成功（R5）；不绕过失败的检查 | `git push`（推送钩子运行 `scripts/engineering/gate/verify.mjs`）、`gh pr create`、`gh pr checks`；细则见 [套件流程文档](../engineering-kit/references/process.md) 第 4 节 | PR 链接和检查结果 |
| 独立复审 | 代码复审和一致性审的结论绑定 PR 最终提交 | 复审者独立于作者，模型按 R9 分档；首轮查全、收齐再改、修后只复核修复；高、中级问题合并前修完，低级和提示级的记进后续清单 | 必做：任务书用 [review.md](references/review.md) 第 2 节的模板（首轮用首轮任务书，修后用修后复核任务书）原样填写，不自拟；差异先存成文件，路径写进任务书；报告由主对话原样落盘，不改写，核对后再登记。首轮按同一文件第 1、2 节对同一提交并行派发代码复审 `product-dev:code-reviewer`（[定义](../../agents/code-reviewer.md)，中高风险带上同一文件的安全清单）和一致性审；不通过时按同一文件的“一轮与修复循环”处理；报告由主对话原样落盘，核对后用 `node scripts/engineering/gate/review.mjs` 登记，两种流程的登记与延期命令见 [套件流程文档](../engineering-kit/references/process.md) 第 4 节“套件闸门的两种流程”一段 | 登记成功的输出；PR 里的复审摘要和后续清单 |
| 合并与收工 | 经合并入口合并，删除分支和工作树，清理临时文件 | 汇报“完成”前确认已清理（R8、R10）；经验提炼分清用户提出和 agent 总结 | `pr` 流程用 `node scripts/engineering/gate/merge.mjs <PR>`，`pre-push` 流程走项目约定的入口；收工步骤见 [套件流程文档](../engineering-kit/references/process.md) 第 7 节；之后跑 `node scripts/engineering/gate/hygiene.mjs` | 合并提交；分支与工作树已删；巡检无新增问题 |
| 验收与发布 | 预发验证、用户验收、灰度上线各留证据 | 实现、CI、验收、上线四种状态不能互相替代（R5）；生产发布和回滚单独授权（R2） | 按 [套件流程文档](../engineering-kit/references/process.md) 第 5 节；验收证据用 `docs/_templates/acceptance-pack.md`（[模板原件](../engineering-kit/kit/templates/docs/templates/acceptance-pack.md)） | `docs/acceptance/`、`docs/release/` 下的记录 |

- 复审不通过时不逐条来回改：两份意见收齐、核实后集中修一次，提交后闸门用 `--affected`，再交原复审者只复核修复；`pre-push` 流程在推送前复核和登记，`pr` 流程推送后复核、CI 通过后登记，两种次序见 [review.md](references/review.md) 第 8 节的“收齐再改”。一轮怎样计、满上限后怎样办、争议和中途追加的需求怎样处理，都在 [review.md](references/review.md) 第 8 节。
- 开发中出现意外的失败（测试、构建、运行时），先停下新功能，按 [debugging.md](references/debugging.md) 处理。
- 远程仓库与合并入口：项目没有远程仓库时，“PR 与 CI”做不了。建远程仓库是外部动作，先得到用户批准；没有批准时，“PR 与 CI”和要靠它才能做的步骤都不做，在汇报里逐项写明未执行，不把本地检查当成 CI。`pre-push` 流程下套件不提供合并入口：项目 AGENTS.md 写了合并入口的按它办，没写的由用户合并或由用户指定入口，不自行合并。
- 用户没要求发布时，做到合并与收工为止，并写明验收和上线尚未进行。

## 5. 修 bug

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 稳定复现 | 拿到能重复触发的步骤和实际输出 | 复现不了就先补日志和证据，不凭猜测改代码 | [debugging.md](references/debugging.md) 第 1 步 | 复现步骤及输出 |
| 定位根因 | 说清哪一行、哪个条件导致了错误 | 修根因，不修症状；缩小到最小可复现的输入 | [debugging.md](references/debugging.md) 第 2、3 步；回归问题用 `git bisect` | 一句话根因，附代码位置 |
| 是需求缺口? | 分清“实现错了”还是“需求没写” | 需求没写的属于新功能，转加功能路线，由用户决定 | 对照 `docs/01-需求/` 的 PRD 和 `docs/04-开发/` 的功能契约；判断方法见 [debugging.md](references/debugging.md) 的“是不是需求缺口” | 判断及依据 |
| 写失败测试 | 有一个现在失败、修好后通过的测试 | 先证明 bug 存在，再证明它消失；预期依据需求、契约和复现结果写，不从现有实现倒推（同“测试设计”） | 项目的测试框架；闸门里的 `scripts/engineering/gate/check-test-first.mjs` 核对测试随改动一起变；写法见 [debugging.md](references/debugging.md) 第 5 步 | 测试失败的输出 |
| 最小修复 | 在共用代码里修一次，测试转绿 | 改动越小越好；不顺手重构无关代码；改之前先搜这个函数的全部调用方 | 按 [build.md](references/build.md) 的“修 bug 时” | 该测试通过，其余测试不变红 |
| 查同类与调用方 | 确认同一个函数的其他调用方没有被改坏 | 同类问题一并列出，范围外的不顺手改 | 宿主的代码搜索；范围大时派发 `product-dev:code-explorer`（[定义](../../agents/code-explorer.md)） | 调用方清单和处理结论；同类问题清单 |
| 自查到合并 | 走完交付段的自查、闸门、CI、独立复审和合并 | bug 修复不免审；涉及数据库、权限的按中高风险审 | 第 4 节从“推送前自查”到“合并与收工”：[self-review.md](references/self-review.md)、`node scripts/engineering/gate/gate.mjs`、`product-dev:code-reviewer`（[定义](../../agents/code-reviewer.md)） | 同第 4 节对应各步 |
| 回归入库 | 失败测试留在测试集里；线上事故另查为何漏检 | 每个漏掉的问题都变成可重复的回归用例 | 测试随修复一起合并，闸门的测试记录为证；事故按 [套件流程文档](../engineering-kit/references/process.md) 第 5 节 | 测试已在主干；事故有漏检分析 |

“是需求缺口?”为“是”时告诉用户并转第 3 节。前两步里不改文件、不切换检出的部分可以直接做；第一个会改文件或切换检出的动作（加临时日志、人为加延迟、`git bisect`、写失败测试）之前，先按第 1 节得到批准，并做第 3 节的“开工检查”。失败测试不必单独提交：留下它失败时的输出作证据，测试和修复可以放在同一个提交里。

## 6. 缩短路线

| 路线 | 步骤（都在第 3、4 节） | 与完整路线的差别 |
|---|---|---|
| 小新增 | 开工检查 → 读相关代码 → 逐片开发（测试先行）→ 推送前自查 → 机械闸门 → PR 与 CI → 独立复审 → 合并与收工 | 不派探索子代理，不写功能契约，不做方案对比的三份蓝图、任务拆解和测试设计；“读相关代码”没有单独的表格行：目标是找出要改的模块、它的调用方和测试，原则是主对话亲自读，工具是宿主的读文件和代码搜索，过关证据是汇报里列出读过的文件；预期写进测试和 PR 描述；只做代码复审（派发和登记照第 4 节“独立复审”一行的必做项：review.md 第 2 节的任务书、差异存成文件、报告原样落盘后登记）；一致性审可延期，延期也要登记：`node scripts/engineering/gate/review.mjs defer --kind consistency --reason "<理由>"`（`pr` 流程加 `--pr <编号>`） |
| 小改动 | 开工检查 → 逐片开发（测试先行）→ 推送前自查 → 机械闸门 → PR 与 CI → 独立复审 → 合并与收工 | 不做探索、契约、方案对比、任务拆解和测试设计；只做代码复审（派发和登记照第 4 节“独立复审”一行的必做项：review.md 第 2 节的任务书、差异存成文件、报告原样落盘后登记）；一致性审可延期，延期也要登记：`node scripts/engineering/gate/review.mjs defer --kind consistency --reason "<理由>"`（`pr` 流程加 `--pr <编号>`） |
| 只改文档 | 开工检查 → 直接改 → 机械闸门 → PR 与 CI → 合并与收工 | 不做独立复审（R7）；一致性审并入巡检，由用户或已授权的定时任务触发，见 [套件流程文档](../engineering-kit/references/process.md) 第 8 节 |

- 次序同第 4 节：`pre-push` 流程下，小新增和小改动的独立复审排在闸门之后、推送之前。
- 做的过程中发现超出了判断条件（要改接口、动第二个模块、动了 `reviewIgnore` 之外的文件），立刻升档，告诉用户并补上缺的步骤。
- 规则、技能正文、提示词这类会改变 agent 行为的 Markdown 不算“只改文档”，按它改变的范围定档。项目的 `reviewIgnore` 没有收窄时，闸门和合并入口在机制上不会要求审查它们，复审要按本条主动做（收窄的办法见 [process.md](references/process.md) 的“配置闸门”）。

## 7. 装或升级工程套件

加载内部技能 `product-dev:engineering-kit`（[SKILL.md](../engineering-kit/SKILL.md)）。安装、漂移检查、升级按它的第 1、2 节执行，其中 `<kit>` 是 `<插件根>/skills/engineering-kit/kit`。它的第 3 节（回滚到某个版本）和第 4 节（变更集与发布）要读源仓库的 git 标签和历史，装好的插件目录不是 git 仓库，在那里跑会报错：这两件事要在套件源仓库的检出里做，`<kit>` 换成该检出的 `components/engineering-kit/kit`；本机没有检出时告诉用户，由用户决定是否获取。不改插件里的套件副本。漂移检查和 `--dry-run` 是只读的，可以直接跑；实际安装、升级、回滚先得到用户批准（R2），已有自有闸门的项目不覆盖。同步产生的改动按第 6 节“小改动”提交，闸门脚本或钩子有变化时按中高风险审。

## 用户授权“按推荐执行”后怎么推进

依据是 R2，这里只写操作：

1. 取推荐项：遇到待决事项，采用推荐项继续推进，不停下等确认。阶段关口照常逐项检查。
2. 写决定记录：写进 `docs/00-总览/RECORDS.md`，字段和状态用词按 R2。
3. 收尾集中汇报：把这一轮代为决定的事项列成一张表（事项、备选、所选、理由、能否回退），用户可逐项推翻。

仍然要停下的两类情况：R2 列出的始终须单独授权的事项和未列入项目授权表的有费用动作；推荐项会推翻用户已确认的目标或范围。停下时说明卡在哪里、需要用户决定什么，其余不受影响的工作继续做。用户本人新提出的要求与已确认的范围或需求冲突时，不属于第二类，但也不直接照改：先说明它与哪一条已确认的内容冲突、会带来什么影响；用户在知情之后仍明确要求的（原话明确提到要改的那条已确认内容的才算知情，例如“不再只做单设备”，说明影响后不必再问一遍要不要改；只提出新做法、没有提到旧约定的不算），按 R1 执行，受影响的需求文档经设计总控修订，修订版照常取得用户确认（已授权按推荐执行的按 R2 记录），变更连同来源写进决定记录。

## 工具缺失与宿主差异

- 调用前先确认部件在不在：内部技能和子代理看宿主的清单，脚本和文档看文件是否存在。不在时用同一栏里写的替代办法；没有替代办法的如实告诉用户，不跳过这一步，也不降低它的过关证据（R4）。用了替代办法的在汇报里写明。
- 设计段要求另开角色上下文、而宿主派发不了子代理时，不停在原地：把那个角色的任务书（目标、依据、要交回的产物）写好交给用户，由用户另开会话执行；能否改由主对话兼任，只按[设计总控](../product-design-orchestrator/SKILL.md)第 1 节判断，并在汇报里写明。
- 没有浏览器工具时，“实际走查”不能算完成：启动原型后请用户走查，或标明未走查。没有图表渲染环境时，架构图标明未渲染。
- 浏览器工具打不开或操作不了本机文件（`file://` 地址）时，以原型目录为根起一个只监听 127.0.0.1 的临时静态服务（脚本放在项目之外），用它的地址走查；走查完关掉服务并在汇报里写明，关不掉的把端口和进程号告诉用户。用脚本模拟页面逻辑得到的结果只算线索，不算实际走查。
- 宿主的权限机制拒绝了某个动作（删除文件、结束进程）时，不换一种办法绕过去：说明哪一步没做成、现场留下了什么，交用户处理。
- 可选加强（只有 Claude Code 有，不能代替上面任何一步的工具）：`/simplify` 会直接改代码，只在逐片开发里测试转绿之后用，用完重跑测试，不算自查也不算复审；`/code-review` 和 `/security-review` 可以在独立复审之外多跑一遍，它们的输出要登记时须按 [review.md](references/review.md) 的报告格式整理，并由独立上下文产生。
- 不调用 feature-dev 自带的流程命令，只用它的三个子代理；agent-skills 和 ponytail 只取方法，不采用它们的文件路径、git 流程和回复格式。
