# project-flow：从想法到上线的唯一入口

用户只说想法，你判断情况、选路线、一步步推进。贯穿全程的纪律写在项目 AGENTS.md 的工程流程块（R1–R10，源文件是 [AGENTS.block.md](../engineering-kit/kit/rules/AGENTS.block.md)），本文只引用编号；项目还没有这个块时，读源文件并按它执行。规则冲突按 R1：项目自己的规则和闸门压过本文。

各步的细则按需读取，不要一次全读：

| 文件 | 什么时候读 |
|---|---|
| [process.md](references/process.md) | 排程、开发细则、自查清单、两种复审流程的命令、预发与发布、文档位置、收工、巡检 |
| [planning.md](references/planning.md) | 任务拆解和逐片开发 |
| [debugging.md](references/debugging.md) | 修 bug，或开发中遇到意外的失败 |
| [review.md](references/review.md) | 派发独立复审、登记复审结论 |

下文的工具栏写“首选（没装或宿主不支持时的替代）”。用了替代做法的，在汇报里写明用的是哪一种。

## 0. 恢复现场

| 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|
| 确认目标项目，弄清做到哪一步，从实际缺口续做 | 核对实际文件、提交记录和开着的 PR，不沿用上一次的结论（R5）；启动技能时所在的仓库不一定是目标项目 | `git status`、`git log`、`git worktree list`、`gh pr list`；读项目 AGENTS.md、`engineering.config.json`、`docs/00-总览/PROJECT_STATE.md` | 能说出当前分支、未合并的工作、套件是否已装及版本 |

套件是否已装看项目里有没有 `scripts/engineering/kit.lock.json`：

- 新项目没装：先装，这是新项目路线的第一步，命令见 [engineering-kit](../engineering-kit/SKILL.md) 第 1 节。
- 已有项目没装：不自动装。按项目自己的规则和闸门走下面的路线，文中套件的闸门命令换成项目对应的检查；可以建议安装，由用户决定（R2）。
- 已装但版本落后或有漂移：告诉用户，建议走“装或升级套件”路线，不擅自升级。

## 1. 分流

| 情况 | 判断条件 | 路线 |
|---|---|---|
| 新项目 | 还没有代码，或产品方向、核心需求未定 | 装套件 → 设计段 → 配置闸门 → 第 3 节 |
| 加功能 | 已有项目里新增或改变能力；跨模块、新接口、数据库结构、权限、费用、服务器配置一律算这一档 | 第 2 节 → 第 3 节 |
| 修 bug | 行为与已确认的需求、契约或文档不符 | 第 4 节 |
| 小改动 | 低风险、单模块、需求明确，不改接口和数据结构 | 第 5 节 |
| 只改文档 | 全部文件都在 `rules.reviewIgnore` 之内 | 第 5 节 |
| 装或升级套件 | 用户要求，或巡检发现漂移 | 按 [engineering-kit](../engineering-kit/SKILL.md) 第 1–3 节执行 |

- 拿不准属于哪一档，按高一档处理（上表越靠上档位越高；修 bug 涉及数据库、权限、费用时按加功能的审查强度）。
- 用一句话告诉用户判断结果和依据，然后直接开始，不等确认；用户纠正就换路线。
- 一句话里有几件事时分别判断，各走各的路线，各开各的分支。
- 用户只要求其中一段（只做设计、只做复审、只发布）时，从对应步骤进入，做完该段即止。

### 新项目：设计段

1. 装套件（空目录加 `--init`，栈未定时先不加 `--profile`）。设计文档从第一天就落在阶段目录里。
2. 加载设计总控 [product-design-orchestrator](../product-design-orchestrator/SKILL.md)，按它走完需求、原型、架构、综合评审。单阶段的设计任务也经总控，只启动对应角色。
3. 总控给出实施准备度后回到这里。`READY` 继续；`READY_WITH_LIMITATIONS` 只做已放行的范围；`BLOCKED` 停下，把阻塞项交给用户。
4. 配置闸门：按选定的技术栈填 `engineering.config.json` 的测试命令、源码与测试文件的匹配规则、`reviewIgnore`。配完故意放一个会失败的检查跑一次闸门，确认它拦得住，再恢复。
5. 用户授权了工程实现，就进第 3 节，任务拆解以 `docs/00-总览/IMPLEMENTATION.md` 的实施顺序为输入；只要设计的，到此结束。

## 2. 加功能：开发之前

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 开工检查 | 干净的新分支 | R7；遗留的未提交改动先提交、归档或清理 | `git fetch`、`git worktree list` | 分支从最新主干开出，工作区干净 |
| 探索代码库 | 找出相似功能、相关模块和必读文件 | 先读懂再动手；子代理只给线索，关键文件主对话亲自读（R9） | 并行 2–3 个 `feature-dev:code-explorer`（通用子代理，任务书写明要交回文件清单和调用链） | 一份必读文件清单，且都已读过 |
| 澄清问题 | 边界情况、错误处理、兼容性都有明确答案 | R3；不带着猜测往下走 | 宿主的提问工具 | 问题清单逐项有答案或有“按授权采用推荐”的记录 |
| 是否改产品行为 | 判断要不要先改 PRD 和原型 | 产品行为由需求角色决定，开发不因实现方便改体验 | 改了就加载设计总控，只修订受影响的部分，再回来 | 结论及依据；需要时有修订后的设计版本 |
| 功能契约 | 写清怎样证明做对了 | 验收标准不擅自弱化；自定的口径单列待确认 | `docs/_templates/feature-contract.md`，放 `docs/04-开发/` | 用户确认的契约（或 R2 的授权记录） |
| 方案对比 | 比较最小改动、结构清晰、折中三种做法并推荐一种 | 建议不写成决定；写明复杂度、风险、能否回退 | `feature-dev:code-architect`（主对话自己写对比，或派通用子代理） | 对比表和推荐理由 |
| 用户选定 | 得到明确批准 | R2；高风险决定写 ADR | `docs/_templates/adr.md` | 用户的选择或授权记录 |

不调用 `/feature-dev` 命令：它自带一套逐阶段等批准的流程，与本文冲突；只用它的三个子代理。

## 3. 交付段

所有路线共用。下表按 `pr` 复审流程的顺序写；项目配置为 `pre-push` 时，独立复审排在闸门之后、推送之前，命令见 process.md 的“测试、审查与合并”节。

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 任务拆解 | 拆成纵向切片，每片有验收条件和验证方法 | 每片能独立验证和回退；高风险的排最前（planning.md） | `docs/_templates/plan.md`，放 `docs/04-开发/` | 计划文件；中高风险的经用户看过 |
| 逐片开发 | 一片一片做：先写测试，再实现，通过后提交 | 测试先行；用最少的新代码解决整个问题；只动任务范围内的文件 | ponytail 常驻模式约束改动量（按 planning.md 的“每片做完自问”）；测试转绿后可用 `/simplify` 清理（手工清理） | 每片一个提交，相关测试通过 |
| 推送前自查 | 作者一侧的问题清零 | 自查不算独立复审（R7）；R4 | ponytail-review（按 process.md 的“推送前自查清单”逐项过） | 自查发现的问题已修，或写明不修的理由 |
| 机械闸门 | 静态检查和测试记录都与当前代码一致 | 失败就修代码，不改阈值、不加豁免了事（R4） | `node scripts/engineering/gate/gate.mjs` | 闸门输出通过 |
| PR 与 CI | PR 最终提交上的必需检查全部通过 | 命令返回 0 不等于业务成功（R5）；不绕过失败的检查 | `git push`、`gh pr create`、`gh pr checks` | PR 链接和检查结果 |
| 独立复审 | 复审结论绑定最终提交，高、中级问题修完 | 复审者独立于作者，模型不弱于作者（R9）；报告打开核对后才登记 | `feature-dev:code-reviewer` 或 `/code-review`，中高风险加 `/security-review`（通用子代理，登记名 `general-purpose`）；任务书和报告格式见 review.md | `review.mjs` 登记成功 |
| 合并与收工 | 经合并入口合并，现场清理干净 | R7、R8、R10；汇报“完成”前确认已清理 | `pr` 流程用 `merge.mjs <PR>`；`pre-push` 流程走项目约定的入口；收工步骤见 process.md | 合并提交；分支与工作树已删 |
| 验收与发布 | 预发验证、用户验收、上线各留证据 | 四种完成状态不互相替代（R5）；生产发布、回滚单独授权（R2） | `docs/_templates/acceptance-pack.md`；process.md 的“预发、生产与事故回归”节 | `docs/acceptance/`、`docs/release/` 下的记录 |

- `/simplify` 会直接改代码，只在逐片开发里、测试转绿之后用，用完重跑测试；它不算自查，也不算复审。
- 复审要求修改时回到逐片开发，改完重新过自查、闸门、CI，再复审。同一 PR 审了三轮还要下一轮，停下向用户说明。
- 开发中出现意外的失败（测试、构建、运行时），先停下新功能，按 debugging.md 处理。
- 用户没要求发布时，做到合并与收工为止，并写明验收和上线尚未进行。

## 4. 修 bug

| 步骤 | 目标 | 原则 | 工具 | 过关证据 |
|---|---|---|---|---|
| 稳定复现 | 能重复触发的步骤和实际输出 | 复现不了先补日志和证据，不凭猜测改代码 | debugging.md 第 1 步 | 复现步骤及输出 |
| 定位根因 | 说清哪一处、什么条件导致错误 | 修根因不修症状；缩到最小可复现输入 | debugging.md 第 2–3 步；回归问题用 `git bisect` | 一句话根因，附代码位置 |
| 是否需求缺口 | 分清实现错了还是需求没写 | 需求没写的是新功能，告诉用户并转第 2 节 | 对照 PRD、功能契约 | 判断及依据 |
| 写失败测试 | 一个现在失败、修好后通过的测试 | 先证明 bug 存在，再证明它消失 | 项目的测试框架 | 测试失败的输出 |
| 最小修复 | 在共用代码里修一次，测试转绿 | 不顺手重构无关代码 | — | 该测试通过，其余测试不变红 |
| 查同类与调用方 | 其他调用方没被改坏，同类问题已列出 | 改之前搜全部调用方 | 全仓搜索；范围大时用 `feature-dev:code-explorer`（通用子代理） | 调用方清单和处理结论 |
| 自查到合并 | 走完第 3 节从推送前自查到合并与收工 | 修 bug 不免审；涉及数据库、权限的按中高风险审 | 同第 3 节 | 同第 3 节 |
| 回归入库 | 失败测试留在测试集；线上事故另查为何漏检 | 每个漏掉的问题都变成可重复的回归用例 | process.md 的“预发、生产与事故回归”节 | 测试已合并；事故有漏检分析 |

## 5. 缩短路线

| 路线 | 步骤 | 与完整路线的差别 |
|---|---|---|
| 小改动 | 开工检查 → 直接做（测试先行）→ 推送前自查 → 机械闸门 → PR 与 CI → 独立代码复审 → 合并与收工 | 不做探索、契约、方案对比和任务拆解；一致性审可延期并写明理由 |
| 只改文档 | 开工检查 → 直接改 → 机械闸门 → PR 与 CI → 合并与收工 | 不做独立复审（R7）；一致性并入每周巡检 |

做的过程中发现超出了判断条件（要改接口、动第二个模块、动了 `reviewIgnore` 之外的文件），立刻升档，告诉用户并补上缺的步骤。套件自身的文档改动同样走这里。

## 6. 汇报与外部工具

- 每个阶段完成时按 process.md“收工”节的四段格式汇报。ponytail 要求在回复结尾写的“跳过了什么、没检查什么”，并入“用户需知”一段，不另起格式。
- 按授权代用户决定的事项（R2），收尾时列成一张表：事项、备选、所选、理由、能否回退。
- 外部工具都是可选的。调用前先看它在不在当前宿主的技能或子代理清单里；不在就用括号里的替代做法，不因此降低该步的过关证据。界面设计与复查用 impeccable（没装时沿用项目已有的设计资产），架构图用 archify（没装时用 Mermaid），这两项由设计技能在各自阶段调用。
- 工具清单、来源和许可见仓库根的 [README](../README.md)。
