# 流程细则

`project-flow` 各步骤的操作细则，按需读取对应的节。贯穿全程的规则（R1–R10）在项目 AGENTS.md 的工程流程块里，本文只写怎么做。
命令中的 `<项目>` 指项目根目录；套件的闸门脚本装在 `<项目>/scripts/engineering/gate/` 下。套件的安装、升级和回滚见 [engineering-kit](../../engineering-kit/SKILL.md)。

## 排程与执行位置

R10 的展开。目的：用户在场的时间和本机的资源，留给需要用户参与、需要判断的工作。

排程只决定同一流程里各项工作在哪里做、先做哪项。步骤、先后顺序、检查范围和通过标准都不因排程改变；两者冲突时按流程办，不为了方便调度而跳过、缩小、推迟到合并之后，或用较弱的检查代替。

| 类别 | 包括 | 排在什么时候 |
|---|---|---|
| 创造性工作 | 需求澄清、方案、编码、处理复审意见、修复失败、需要用户决定的事 | 优先完成，排在用户在场的时段 |
| 重复性工作 | 全量测试、回归、端到端、构建、巡检、批量机械改动、跑闸门 | 攒成整块，在用户这一阶段要做的事做完之后一次跑完 |

“整块时段”不指固定的钟点：需要用户参与的事已经做完、用户可以离开的那一段就是。一个任务可以分成几轮，每一轮先把需要用户的部分集中做完，再把这一轮的重复性工作集中跑完，下一轮以上一轮的结果为依据。

- 能放云端的条件：代码已推送到远程；不依赖只在本机才有的东西（未推送的文件、本机的数据库或服务、本机凭据、图形界面、硬件）。不满足的留在本机，并在汇报里说明原因。
- 开工时定顺序：列出本任务的创造性部分和重复性部分。先做完创造性部分并提交快照；重复性部分排队，不穿插在中间；互不依赖的合成一批。
- 用户在场时，本机只跑与改动直接相关的单元测试和静态检查，供写代码时即时反馈。
- 与闸门的关系：推送仍须有与当前代码一致的通过测试记录。在云端会话里开发的，闸门在云端跑、从云端推送；留在本机的，把“跑闸门、推送”放进本轮的整块时段。
- 每一轮整块跑完后集中汇报一次：通过与失败、失败的具体项、需要用户决定的事。修复属于创造性工作，放进下一轮。

## 开发细则

- 测试先行：改源文件前，先写或补引用它的测试，测试随改动一起改。闸门靠“测试文件是否引用了源文件的模块名”判断，经 index 再导出的间接引用识别不出来，这种情况在豁免表里写理由。
- 注释：每个源文件开头有业务职责说明；导出的函数、类、常量前有说明（输入输出、异常、为什么这样做）。外部工具主张少写注释时，按 R1 以闸门为准。
- 目录：代码按语言惯例放 `src/`、`tests/`。新的顶层目录要在 `layout.topLevelAllowed` 里，或是 `sourceGlobs`、`testGlobs` 写明的顶层目录。
- 实现中自行确定的口径单列出来，待用户确认，不写成已决定。

## 测试、审查与合并

顺序：推送前受影响的测试 → CI → 独立代码复审和一致性审 → 合并。项目已有更完善的流程时，以项目规则和实际闸门为准（R1）。

1. 推送前执行静态检查及受影响的单元、集成、端到端、视觉和安全检查；不能可靠判断影响范围时扩大范围或跑全量，说明选择及结果。测试用隔离环境和合成数据。套件闸门目前不做受影响测试选择，一律跑配置的 `testCommand`。
2. CI 对最终提交执行全量单元测试和项目适用的全量集成测试；端到端、兼容性、安全等检查按风险安排，明确跳过的理由。
3. 按下方分档做独立代码复审和增量一致性审（矛盾、重复、过时）。合并前核对 PR、最终提交、CI 和该档要求的审查；提交或基线变化后重新核查受影响部分。
4. 高、中级问题，以及影响体验或使用的问题，合并前修复；低级问题按项目规则记录并安排修复。本次引入的矛盾、重复和过时在本 PR 修复。同一 PR 三轮审查后仍需下一轮时，向用户说明问题、原因、已做处置和建议，等用户决定。
5. `pr` 流程下合并只经 `merge.mjs`，它核对 CI 与两项审查都针对 PR 的最终提交；`pre-push` 流程的记录只证明推送前复审过，不能证明 CI 之后的双审或与最终 PR 的绑定。

### 推送前自查清单

作者自查，不算独立复审。装了 ponytail 时用 ponytail-review；没装时逐项过：

- 改动只做了任务要求的事，没有顺手改无关代码。
- 每条验收条件都有测试或可重复的验证方法，并且实际跑过。
- 边界值、空值、错误路径有处理；改动函数的全部调用方都看过。
- 没有为了变绿而屏蔽检查、跳过测试、放宽配置（R4）。
- 没有写入密钥、凭据、个人信息；外部输入在边界上做了校验。
- 没有留下调试输出、注释掉的代码、未使用的文件。
- 文档、索引、契约与代码一致；新文件的位置符合“文档与目录”节。

### 审查分档

风险分级：跨模块、新接口、数据库结构、权限、费用、服务器配置为中高风险，其余为低风险。拿不准时按高一档。

| 改动 | 代码复审 | 一致性审 |
|---|---|---|
| 只改文档（`reviewIgnore` 之内） | 不做 | 并入每周巡检 |
| 低风险小改动 | 每个 PR 合并前 | 可延期：并入每周巡检，或与其他 PR 集中审；延期要写明理由 |
| 中高风险 | 每个 PR 合并前 | 每个 PR 合并前 |

代码复审不攒到合并后：合并后才发现的问题已在主干上，后续 PR 又叠在其上。一致性审可以集中审多个 PR，但每个 PR 的最终提交、结论和证据各自记录。复审任务书和报告格式见 [review.md](review.md)。

### 套件闸门的两种流程

由 `engineering.config.json` 的 `modules.gate.reviewFlow` 决定。

- `pre-push`（默认）：`gate.mjs` 通过后由独立子代理复审，`review.mjs pass|fail --reviewer <名> --report <报告> --summary "<一句话>"` 登记；推送时核对静态检查、测试记录和复审记录，三者都绑定当前代码树。套件不提供合并入口，钩子拒绝直接 `gh pr merge`，合并按项目约定的入口。
- `pr`：`gate.mjs` 通过后即可推送，推送核对只要求静态检查和与当前代码一致的测试记录。CI 在 PR 最终提交上全部通过（每项检查成功、跳过或中性；一项都没有视为未通过）后按分档审查并登记，PR 未打开或 CI 未全过时拒绝登记：
  - 代码复审：`review.mjs pass|fail --pr <编号> --kind code --reviewer <名> --report <报告> --summary "<一句话>"`。
  - 一致性审：同上，`--kind consistency`；按分档可延期时用 `review.mjs defer --pr <编号> --kind consistency --reason "<理由>"`。
  - 合并：`merge.mjs <编号> [--method squash|merge|rebase]`。PR 打开、CI 全过、代码复审为 pass、一致性审为 pass 或延期、两份记录的提交都等于当前最终提交，才执行 `gh pr merge --match-head-commit`（默认 squash 并删除远端分支）；否则逐条列出原因，不合并。PR 又有新提交时记录过期，重新审查后再登记。
  - 只改文档的 PR 合并入口只核对 PR 打开与 CI 全过；PR 文件列表为空或达到 100 个（`gh` 可能截断）时按含代码处理。其余 PR 合并入口不判断风险档位：代码复审必需，能否延期一致性审由登记者按分档判断。
  - 需要 GitHub 远程、已登录的 `gh`，且 PR 上有 CI 检查；不满足的项目留在 `pre-push`。

## 预发、生产与事故回归

- 预发使用与生产一致的发布产物，按风险执行核心流程、冒烟、验收、回归、视觉、兼容、安全、性能与负载检查；压力测试在专项环境按需进行。修改或修复后做针对性的检查。记录不适用项及原因。
- 发布前准备并验证回滚方案、上一版本与数据迁移的兼容性、备份和恢复路径；镜像回滚不等于数据恢复。按项目授权部署，小范围灰度和健康检查通过后扩大，生产持续监控，异常按授权和预案处置。
- 用户验收的证据写进验收证据包（`docs/_templates/acceptance-pack.md`，放 `docs/acceptance/`），发布记录放 `docs/release/`。
- 事故或测试漏检须调查为何测试和 AI 审查未发现、是否缺少测试或安全检查、CI 是否需要调整。把问题转成稳定、可重复的回归用例，放入适当阶段；无法自动化时记录原因、责任人和可执行的专项检查并跟踪补齐。可将事故、相关 PR、修复和回滚整理成脱敏样例，持续评估审查能力。

## 文档与目录

位置和归属的规则是 R6，这里只补它没写的操作细节。

- 新建文件须满足以下之一：独立生命周期、独立被引用、独立时间点。推送核对会拦截不在允许位置、又没有理由的新文件；理由写在豁免表的 `newFiles` 里。
- 模板在 `docs/_templates/`，只读，复制后使用。巡检发现记录类旧文件被改会报错。
- 阶段目录默认是 `00-总览`（项目状态、决定与交接记录、实施交接与追踪矩阵）、`01-需求`、`02-原型`、`03-架构`、`04-开发`、`05-测试`、`06-发布`，可在 `layout.stages` 里改。已安装项目写在配置里的阶段不随同步改变，同步会给出升级提示。
- 大版本（例如 v2）才用新目录（如 `v2/`）；同一版本内不新建平行目录。
- 会话的临时目录（scratchpad）不算项目根目录之外的新建，不需要批准；用完清掉。

## 收工

R10 的展开。

1. 合并后删除远端与本地分支，清理工作树（`git worktree remove`）。
2. 列出本次新建的目录和文件（`git status`、`git diff --name-only --diff-filter=A <基准>`），逐个检查是否符合“文档与目录”节；不必留下的清理掉（R8）。
3. 更新阶段索引（`docs/README.md` 和所在阶段的 README）。
4. 经验提炼：怎样记录见 engineering-kit 的 [practices.md](../../engineering-kit/references/practices.md)。agent 总结的经验要升格为套件能力时，写成变更集，命令见 engineering-kit 技能第 4 节。
5. 汇报分四段，各有小标题，没有内容的写“无”：任务完成情况（做了什么、是否通过、检查和证据在哪里）、后续待办（谁做、依赖什么、何时做）、用户需知（已做的默认选择、已知限制、风险）、经验提炼。

## 巡检

- 机械检查：`node <项目>/scripts/engineering/gate/hygiene.mjs`。检查顶层目录白名单、禁用文件名片段（copy、final、bak 等）、死链、阶段索引、状态合法性、记录类只追加、重复内容、空目录、超期草稿、已合并分支与残留工作树。“已合并分支”按补丁等价判断，squash 合并后的分支需人工复核。
- 装了 ponytail 时可加 ponytail-audit（全仓质量）和 ponytail-debt（遗留的捷径）；它们同样只出报告。
- 巡检发现的问题怎样删除按 R8。
- 语义一致性审：由子代理只审增量（本次或本周期新增、修改的文档），找出规则与文档之间的矛盾、重复、过时。
- 周期：建议每周一次，或在大批合并之后。
